# Windows·iPad 통합 작업지시서 — 일반 집필 기능 확장

작성일: 2026-09-13

후속 상태: 사용자 「윈도우측 구현 시작」 요청에 따라 [Windows 로컬 구현·검사](windows-integrated-editor-implemented-2026-09-13.md)를 진행했다. 아래 “이번 요청은 지시서 작성”은 작성 당시 범위다. 후속 구현 요청도 설치·실제 서버 통신·관문/보류 변경 승인으로 확대하지 않는다.

## 목적과 적용 범위

기존 5단계를 **통합 구현 → 변경분 검사·실행 준비 → 양측 Staging 확인**의 3단계로 묶는다. 응답 유실 복구, 여러 문서 편집, 문서·폴더 관리, 자동 동기화를 모두 포함한다. 기능을 하나 완성할 때마다 설치·양측 감사·자료 교환을 반복하지 않는다.

**기존 복구 1·2차 실행안은 통합 실행안으로 대체하고, 구현·검사 증거만 재사용한다.** 기존 실행안과 증거 파일은 이력으로 보존한다. 기존 후보는 완료된 문서 하나에 고정되어 있으므로 새 시험 문서와 구조 작업을 지원하는 양측 통합 후보가 필요하다. 이전 **23회 요청 상한은 재사용하지 않으며**, 새 통합 흐름에 맞춰 요청 총량과 실행 시간 한도를 산정한다.

**이번 요청의 실행 범위는 이 작업지시서 작성이다.** 아래는 후속 구현을 위한 지시서이며, 지금 구현이나 설치·서버 통신을 실행했다는 뜻이 아니다. 과거 문서의 지시·승인을 새 권한으로 이어받지 않는다. 새 설치·실제 서버 조회/송수신·관문/보류 변경은 구체적인 실행 범위를 준비한 뒤 별도 승인 범위에서만 수행한다. prod 전환과 자동 충돌 병합은 제외한다.

## 유지할 기준

- [인계서](next-task-normal-editor-handoff-2026-09-13.md)와 [최종 감사](normal-editor-roundtrip-final-audit-2026-09-13.md)를 완료 기준으로 삼는다. 과거 문서의 revision 6 등은 현재 기준이 아니다.
- 양측 최종 revision 9 / UTF-8 393바이트 / 11줄 / 마지막 LF 포함. SHA-256: `570040e0bd94d5ff31c64799d549775ef74eb14503b7fa374f170ad7297b764f`. 완료된 정상 왕복과 종료 감사를 반복하지 않는다.
- 현재 미커밋 변경·설치물·본문·초안·큐·복구 기록·기존 증거를 보존한다. 초기화, 무단 덮어쓰기, reset/clean, 커밋·푸시를 하지 않는다.
- 기존 Windows 관문 복원·hold 상태와 iPad preferences·기존 관문 상태를 유지한다. 자동 동기화 구현만으로 실제 통신을 개방하지 않는다.
- 후속 확인은 기존 Staging 작품 안의 승인된 시험 문서·폴더로 한정한다. 완료된 기준 문서는 변경 시험 대상으로 쓰지 않는다. 여러 작품 지원은 이번 범위가 아니다.

참조 문서는 다음처럼 구분한다. 과거 구현·검사 근거로만 사용하며, 이번 사용자 보완 지시와 위 최종 완료 기준을 우선한다.

- Windows: `docs/windows-normal-editor-runtime-prepared-2026-09-13.md`(구현·격리 검사), `docs/normal-editor-roundtrip-final-audit-2026-09-13.md`(종료 감사).
- iPad: 「자유 편집 operation의 receipt 인터페이스」 — 보존 파일 `_evidence/windows-normal-editor-runtime-20260913/ipad-receipt-interface-d56827a879f1fb82a4bb1de3b370a81df90c7ecf3c5ed6d6d7fbe1582f4feb4d.md`(구현 대조), `ipad-normal-editor-roundtrip-result-2026-09-13.md` — 보존 파일 `_evidence/windows-normal-editor-execution-20260913/ipad-final-result-076c18fcc15c1eba8d970e4946df5a963216ca1918edf0371ff7e4c6056b2585.md`(담당자 최종 보고).
- 사용자가 이번에 언급한 기존 복구 1·2차 실행안의 정확한 파일명은 현재 로컬 자료에서 식별하지 못했다. 해당 실행안의 대체 관계는 위와 같이 적용하며, 참조 이름 보완을 위해 전체 자료를 다시 교환할 필요는 없다.

## 1단계 — 공통 규칙에 맞춰 양측 통합 구현

후속 구현을 시작하면 아래 네 기능을 같은 개발 묶음으로 진행한다. 내부 구현 순서는 **문서별 상태 분리 → 본문·구조 작업 연결 및 복구 → 자동 실행 연결**로 한다. 기존에 구현된 부분은 재사용하고 부족한 부분만 보완한다.

| 기능 | 양측 공통 작업 | Windows 측 | iPad 측 |
|---|---|---|---|
| 여러 문서 편집 | 문서 ID별 본문·초안·revision·저장 대기 작업 분리. 전환·재시작 때 미저장 글 보존 | 일반 편집기의 문서 선택·전환과 기존 저장·큐 연결 | 문서 목록·편집 전환과 기기 저장·큐 연결 |
| 문서·폴더 관리 | 생성·이름 변경·이동·정렬·삭제·복원을 동일한 ID·revision·순서 규칙으로 처리. 삭제와 미전송 편집의 충돌도 보존 | 기존 트리 UI와 구조 작업 연결 | 목록·트리 조작과 같은 구조 작업 연결 |
| 통신 실패 복구 | 응답 유실 시 원래 operation/batch의 receipt를 확인해 완료 판단. 조회 실패나 불일치 때 중복 쓰기·임의 완료 처리 금지. 부분 수신·후속 편집 보존 | 기존 receipt 조회·큐 복구 경로의 부족분 보완 | 동일 상황의 기기 복구 경로 보완 |
| 자동 동기화 | 저장 뒤 자동 송수신, 연결 회복·재시작 시 재개. 미저장 글을 덮어쓰지 않으며 충돌은 기준·로컬·원격을 보존하고 안내 | 일반 앱 실행·연결 회복에 연결 | 앱 복귀·연결 회복에 연결. OS가 허용하는 실행 시간에서 처리하고 중단 시 다음 복귀에 재개 |

공통 데이터 규칙은 문서 ID 유지, 서버 작품 ID와 기기 로컬 작품 ID 구분, UTF-8/LF 및 마지막 줄바꿈 유무 보존이다. 본문을 trim하거나 Unicode 정규화하지 않는다. 자동 실행도 기존 인증·대상 확인·관문·보류 조건을 따르며, 미확정 쓰기는 결과 확인 전 새 ID로 재전송하지 않는다.

수동·자동 실행의 중복을 막고 본문·구조 작업의 선후관계를 지킨다. 승인된 요청 총량 또는 실행 시간 한도를 소진하면 자동 실행을 멈춘다. 실행별 사용량·잔여 한도를 영속 보존하여 앱 재시작으로 한도를 초기화하지 않는다. 수동·자동 요청과 재시도·복구 조회를 같은 승인 실행의 한도로 관리한다.

API·데이터 형식·충돌 처리에 차이가 있을 때만 상대측과 맞춘다. 회신을 기다리는 동안 그 차이에 의존하지 않는 로컬 구현은 진행할 수 있다.

## 2단계 — 변경분 검사와 실행 준비를 한 번에 정리

구현 중 필요한 컴파일·국소 확인은 진행하되, 변경분과 영향받는 회귀 검사를 한 묶음으로 실행한다. 실패 수정 후에는 실패·영향 범위만 재검사한다. “검사 한 번”은 검사를 묶어 진행한다는 뜻이며 수정 검증 횟수를 제한하지 않는다. 기존 통과 검사는 변경 영향이 있을 때만 다시 실행한다.

- 문서 전환·재시작 후 본문과 초안이 올바른 문서에 남고 큐가 섞이지 않는지 확인한다.
- 구조 변경과 삭제·복원 뒤 ID·부모·정렬이 일관되고 미전송 본문이 유실되지 않는지 확인한다.
- 응답 유실·조회 거부·receipt 없음/불일치·부분 수신·동시 편집에서 중복 쓰기나 덮어쓰기가 없는지 확인한다.
- 자동 송수신·재시도·앱 복귀가 관문과 보류를 지키고, 충돌을 알리며 중단 위치에서 재개하는지 확인한다. 수동·자동 중복 방지, 본문·구조 작업 순서, 요청/시간 한도 도달 시 정지와 재시작 후 한도 유지도 확인한다.

각 측은 **변경점 / 검사 결과 / 차단 / 설치 필요 여부**만 짧게 공유한다. **양측 모두 실제 receipt SELECT는 미실행이고 권한/RLS는 미확인**으로 표시하며, 격리 검사 통과와 실제 서버 권한 확인을 구분한다. iPad는 실행 준비 시 서명 상태를 확인하고 필요한 경우에만 갱신·설치를 실행 범위에 넣는다.

이 결과를 바탕으로 시험 대상 ID, 양측 통합 후보, 필요한 설치, 서버 요청 종류·총량·실행 시간 한도와 양측 배분, 관문/보류 변경 필요 여부와 복원 방법, 계획된 장애의 예상 상태·복구 절차, 중단 조건을 **하나의 실행 범위**로 정리한다. 요청·시간 집계 기준과 한도 도달 후 종료·복원에 필요한 요청도 이 범위 안에 명시한다. 이전 23회 상한이나 버튼 횟수를 새 요청 한도로 대신하지 않는다. 실제 실행 승인은 이 구체적인 범위에 대해 한 번 받으며, 범위 안의 버튼마다 다시 묻지 않는다.

## 3단계 — 승인된 범위에서 양측 Staging 통합 확인

1. 준비된 양측 통합 후보를 승인된 범위에서 설치하고 지정 시험 문서·폴더로 여러 문서 편집과 구조 변경을 교차 확인한다. 완료 문서 하나에 고정된 기존 후보를 새 시험에 사용하지 않는다.
2. 같은 시험 흐름에서 자동 송수신·연결 중단 후 재개·앱 복귀·충돌 보존을 확인한다. 응답 유실 복구는 원래 batch의 실제 receipt 조회 권한과 결과 반영을 확인한다. 실패 사례를 만들기 위한 서버 쓰기나 통신 중단도 승인된 실행 범위에 포함되어야 한다.
3. 정상 결과는 중간 승인 없이 이어간다. **계획된 응답 유실·충돌 등 장애는 예상 상태와 일치하면 승인된 복구 절차를 계속하고, 예상 밖 오류·상태·요청 또는 대상 불일치에서 중단한다.** 복구도 승인된 요청·시간 한도 안에서 진행하며, 한도를 소진하면 자동 실행을 멈추고 정해진 종료 절차를 따른다. 임의 재클릭·재송신·범위 확대를 하지 않는다.
4. 종료 시 시험 대상 본문·revision·구조 일치, 의도한 충돌 보존, 설명되지 않는 대기/부분 반영 없음, 임시 변경 복원을 확인한다. 의도적으로 남긴 충돌·보류는 해결된 것으로 표시하지 않는다. 기존 완료 본문·증거는 유지한다.

완료 결과는 양측 각각 한 번만 정리한다. 별도의 반복 감사나 전체 과거 자료 재전송은 하지 않는다.

## iPad·Windows 간 교환 형식

같은 지시서를 양측 기준으로 사용한다. 직접 메시지 발송은 이번 요청에 포함되지 않는다.

> 변경점: 상대측에 영향을 주는 규칙·형식·동작만 1~3줄. 없으면 “공통 기준 일치”.  
> 검사/결과: 이번 변경 검사 또는 통합 확인의 통과·실패만 요약.  
> 차단: 상대측 조치나 별도 실행이 필요한 항목만. 없으면 “없음”.  
> 후보: 설치가 필요할 때만 버전·해시·설치 필요 사유.

큰 ZIP·전체 대화·기존 증거는 다시 보내지 않는다. 특정 실패 판단에 필요한 경우에만 관련 최소 기록을 추가한다.
