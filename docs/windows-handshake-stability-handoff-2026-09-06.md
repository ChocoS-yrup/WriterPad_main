# Windows 수정 결과와 iPad 공통 동작 확인서

작성일: 2026-09-06 KST

이 문서는 Windows에서 구현·검증한 동작을 iPad 측에 전달하기 위한 기준이다. 아래 공통 규칙에 대한 iPad의 구현 여부와 테스트 결과를 회신받아 양쪽 동작을 확정한다. iPad 구현이나 양쪽 합의가 이미 완료됐다는 뜻은 아니다.

## 1. 전달 기준

| 항목 | 값 |
|---|---|
| Windows 저장소 | `ChocoS-yrup/WriterPad_main` |
| 브랜치 | `feat/contract-handshake-closed-gate` |
| 수정 전 HEAD | `41b50f33697ddde16e04f03722f1b77c45eaaa0e` |
| 수정 코드 커밋 | `d92d26a92f1e5e1b2ada690853e33a9103796078` |
| 검증 서버 환경 | WriterPad Staging |
| 계약 version | `0.2.0` |
| protocol | `3` |
| canonical digest | `416c1b99edb9bda694731dee4b25688d9d82d1f32610aa23ddfda571ec3c7670` |
| 실제 작품의 계약 관문 | 열린 관문 0개 / 로컬 작품 15개 |

계약 파일·digest·allowlist·서버 설정·프로젝트 mode/epoch를 변경하지 않았다. 기존 AI 수정은 기준 HEAD에 포함돼 있으며 보존했다. 이번 변경은 프로토콜 적용 범위 확대, 폴더 이동, iPhone 지원을 포함하지 않는다.

**계약 관문과 전체 클라우드 연결은 별개다.** 관문이 닫히면 `CONTRACT_BATCH` 쓰기를 시작하지 않는다. 기존 일반 동기화는 자체 인증·작품·구조 검사를 통과하면 계속 가능하다. 닫힌 관문에서 ‘동기화 완료’가 나타났다고 계약 배치를 전송한 것으로 해석하면 안 된다.

## 3. 캐시 무효화와 자동 재조회 규칙

공통 규칙 C1: 핸드셰이크는 단순히 ‘이 작품을 조회했음’으로 캐시하지 않는다. 현재 사용자, 작품 ID, 로컬 작품 연결, 연결 세대, 계약 pin에 귀속시킨다. Windows는 저장소·서버 클라이언트 객체가 교체된 경우도 구분한다. Swift에서는 같은 의미의 세대 번호나 불변 요청 컨텍스트를 사용하면 된다.

공통 규칙 C2: 캐시를 버릴 때 조회 완료/조회 시도 기록과 재시도 기한도 함께 정리한다. 진행 중인 호출의 슬롯은 실제 종료 전까지 유지하되, 그 결과는 옛 세대의 것으로 취급한다.

| 사건 | Windows 동작 / iPad가 맞출 의미 |
|---|---|
| 앱 재실행 | 메모리 핸드셰이크를 새로 시작. DB의 과거 `contract_validated_at`만으로 전송 승인 금지 |
| 작품 열기·전환·연결 해제·재연결 | 작품 연결 세대 변경. 이전 캐시·조회 시도·대기 재시도 무효화. 현재 작품에서 필요한 조회 시작 |
| 로그인 성공 | 동일 계정이어도 새 인증 수명으로 처리. 핸드셰이크와 구조 기준을 다시 확인 |
| 로그아웃 없이 계정 변경 | 이전 사용자 응답을 새 사용자에게 적용하지 않음. 새 사용자 기준으로 재조회 |
| 로그아웃·확정된 인증 만료 | 캐시 무효화, 자동 인증/전송 차단. 이전 응답으로 로그인 상태 복원 금지 |
| 저장된 로그인 복원의 일시적 통신 실패 | 로그아웃으로 단정하지 않음. 복원 대기 → 백그라운드 복원 → 핸드셰이크·구조 재조회 |
| 계약 관문 닫기 | 즉시 전송 조건 무효화 및 캐시 제거. 이후 읽기 전용 핸드셰이크는 가능하지만 관문은 닫힘 유지 |
| 서버가 기존 계약 정보의 무효를 알림 | 해당 캐시 무효화. 오래된 성공 응답을 전송 승인에 재사용하지 않음 |

Windows가 캐시를 무효화하는 서버 오류 코드는 다음과 같다.

```text
AUTH_REQUIRED AUTH_EXPIRED FORBIDDEN CONTRACT_NOT_ALLOWED
CONTRACT_DIGEST_MISMATCH PROTOCOL_TOO_OLD CAPABILITY_MISMATCH
STALE_MIGRATION_EPOCH
```

공통 규칙 C3: 응답 수신 시 요청을 시작했던 컨텍스트와 현재 컨텍스트를 비교한다. 이전 작품·계정·연결의 성공, 실패, `unsupported` 응답 모두 새 상태에 적용하지 않는다. 특히 이전 실패가 새 세대의 ‘이미 조회함’을 설정해서는 안 된다.

Windows의 `fresh`는 **현재 컨텍스트에서 유효한 supported 응답**이라는 의미다. 고정 시간 TTL을 적용한 값이 아니다. DB의 관측 시각은 진단 정보이며 재시작 후 인증 근거가 아니다. 이미 유효한 응답이 있는 동일 컨텍스트에서는 매 주기 핸드셰이크를 반복하지 않는다. iPad의 백그라운드 복귀 시 TTL이나 강제 재조회 정책을 추가하려면 별도 합의가 필요하며, 세대 무효화 규칙을 대체할 수는 없다.

## 4. 핸드셰이크 응답 검증

공통 규칙 C4: 읽기 RPC는 `get_sync_handshake`이며, Windows는 `p_project_id`와 고정된 `p_contract_sha256`을 전달한다. supported로 승인하려면 아래 검사를 모두 통과해야 한다.

- `supported`가 true이고, 응답에 작품 ID가 있으면 요청 작품과 일치한다.
- `contract_version`, `canonical_contract_sha256`, `supported_protocol_versions`가 모두 존재한다. 누락 값을 클라이언트 기본값으로 채워 승인하지 않는다.
- version은 `0.2.0`, canonical digest와 server digest는 서로 같고 빌드 pin과 일치한다.
- `supported_protocol_versions`에 3이 있으며, `server_protocol_version`도 응답의 지원 집합에 속한다. 서버 버전 숫자가 3 이상이라는 조건만으로 승인하지 않는다.
- mode/epoch 조합, 서버 protocol, 필수 capabilities가 계약 호환성 검사를 통과한다.

`unsupported`나 잘못된 응답은 계약 전송 권한을 만들지 않는다. 핸드셰이크 성공만으로 로컬 계약 관문을 열거나 프로젝트 mode/epoch를 전환하지 않는다. 필수 capability와 와이어 형식은 [기존 계약 전달 문서](ipad-contract-client-handoff.md) 및 `sync_contract.py`를 따른다.

## 5. 일시적 실패와 재시도 규칙

공통 규칙 C5: 다음 실패는 서로 다른 상태로 처리한다.

| 분류 | 자동 처리 |
|---|---|
| timeout, 연결·DNS 오류, 알려진 전송 오류, 노출된 HTTP 429/5xx | 동일 컨텍스트에서 지연 재시도. 최초 실패를 조회 완료로 기록하지 않음 |
| 저장된 로그인 복원 중 위 통신 실패 | 저장된 세션을 통신 실패만으로 삭제하지 않음. 복원용 연결에서 재시도 |
| 확정된 인증 거절·인증 만료 | 로그인 필요 상태. 통신 복구 알림만으로 인증 차단을 해제하지 않음 |
| 계약 불일치, 권한 거절, 잘못된 구조·응답 | 해당 경로 차단. 오프라인 재시도 루프로 취급하거나 다른 쓰기 프로토콜로 우회하지 않음 |

오류가 인증 라이브러리로 감싸져 있으면 원인 예외도 확인한다. 단, 명시적인 계약 오류나 HTTP 400/401/403 거절을 내부의 오래된 timeout만 보고 일시적 통신 오류로 바꾸지 않는다.

공통 규칙 C6: Windows 재시도 간격은 **2 → 4 → 8 → 16 → 32 → 60초**, 이후 60초 상한이다. 총 시도 횟수를 6회로 제한한 것이 아니다. 기존 주기/복구 알림이 기한 이후 실제 작업을 시작하므로 정확히 그 초에 실행된다는 보장은 없다. 조회 성공 또는 컨텍스트 변경 시 해당 지연 상태를 초기화한다.

공통 규칙 C7: 핸드셰이크, 로그인 복원, 작품 pull 각각에서 중복 작업을 억제한다. 반복된 타이머·복구 알림은 진행 중인 동일 역할의 요청을 늘리지 않는다. 같은 배치의 동시 전송도 금지한다. iPad는 타이머 대신 연결 복구 이벤트를 사용해도 되지만 지연 기한과 중복 억제를 우회해서는 안 된다.

공통 규칙 C8: 자동 재시도에 따른 네트워크 대기는 집필 UI에서 수행하지 않는다. 구조를 아직 확인하지 못한 동안 원고는 로컬에 저장하고 전송을 대기시킨다. 대기 원고가 있다는 이유로 복구용 구조 조회까지 막아서는 안 된다. 복구 pull은 기존 로컬 미전송 변경 보호 규칙을 유지하면서 기준 구조를 먼저 확인한다.

## 6. 계약 배치 전송 차단 규칙

공통 규칙 C9: 새 배치와 이미 저장된 pending/retry 배치에 같은 검사를 적용한다. 아래 조건 중 하나라도 불충족이면 **아직 시작하지 않은 계약 쓰기 RPC는 0회**여야 한다. 이 규칙은 읽기 전용 핸드셰이크 RPC까지 금지한다는 뜻이 아니다.

1. 현재 작품의 로컬 계약 관문이 열려 있다.
2. 인증 차단·로그아웃 상태가 아니며 현재 사용자를 식별할 수 있다.
3. 요청 당시와 현재 사용자·작품 연결·저장소·서버 클라이언트·세대가 일치한다.
4. 현재 컨텍스트에 유효한 supported 핸드셰이크와 계약 호환성 정보가 있다.
5. 요청의 version/digest/protocol/capabilities/device ID, 작품 ID, mode/epoch가 현재 조건에 맞는다.
6. 종료·강제 오프라인 상태가 아니며, 일반 동기화의 구조 확인·작품 상태·직렬화 조건도 충족한다.

검사는 큐에 넣을 때 한 번으로 끝내지 않는다. 비동기 인증 대기, worker 실행 대기, RPC 객체 구성 중 상태가 달라질 수 있으므로 전송 시작 경계까지 재검사한다. Windows에서 계약 쓰기는 `atomic_structure_commit`과 계약 `document_commit` 경로다.

공통 규칙 C10: 관문 닫힘, 무효 핸드셰이크, 재조회 대기는 배치 삭제나 재생성의 이유가 아니다. `operation_id`, `batch_id`, payload 및 계약 메타데이터를 보존한다. 시도 이력이나 대기 상태는 기록할 수 있지만 요청을 다른 프로토콜로 변환하거나 다른 작품·계정에 붙여 보내지 않는다.

공통 규칙 C11: **전송 전 / 전송을 시작한 요청 / 서버 적용이 확인된 요청**을 구분한다.

- 전송 시작 전: 차단 조건이 생기면 시작하지 않고 같은 요청을 보존한다.
- 전송 시작 경계를 통과한 요청: 이후 관문을 닫아도 취소나 서버 롤백이 완료된 것으로 표시하지 않는다. Windows는 잠금 아래 전송 시작을 예약한다. 이 로컬 예약 자체는 실제 서버 수신·적용 증거가 아니다.
- 응답 수신: 원래 요청의 batch ID·digest 등 계약 응답을 검증하고, 원래 저장소에 영수증을 기록한다. 화면이 다른 작품·계정으로 바뀌었다면 새 화면에 그 완료를 적용하지 않는다.
- 응답 유실/결과 불명: 이미 적용됐을 가능성을 유지한다. 다시 전송할 때도 현재 관문 검사를 통과해야 하며, 동일 ID·payload로 서버의 멱등 처리를 사용한다. 유효한 완료 영수증이 저장돼 있으면 불필요한 재전송 없이 복구한다.

공통 규칙 C12: 관문은 자동으로 열리지 않는다. 명시적인 관문 열기에도 그 시점의 핸드셰이크가 필요하다. 양쪽 동작 확인을 위해 실제 작품의 관문이나 서버 allowlist를 먼저 열지 않는다.

## 7. 회귀 검사 결과

전체 관련 회귀 검사: **710개 실행 / 709개 통과 / 실패 0개 / 건너뜀 1개**. Windows 심볼릭 링크 생성 권한이 없어 기존 해당 테스트를 건너뛰었다. 신규 테스트는 핸드셰이크 안정화 32개, 실제 통신 장애 경로 재현 16개, 설정 경로 4개다. 커밋 전 이 52개도 재실행해 전부 통과했다.

통신 복구 수정 전 최초 재현은 4개 중 3개 실패, 구조 오류 차단 유지 검사 1개 통과였다. 수정 후 모두 통과했다. 다음 항목을 회귀 테스트로 보관했다.

## 8. 설치본 실사용 검증

Windows 설치본을 재빌드·교체했고 설치 경로에서 `--qt-import-smoke-test` 종료 코드 0을 확인했다. EXE SHA-256은 `3e8eea226d6c62dbebd5aec7f589729016ea313cc906d6c969c7d0d6d8540dce`다. 커밋 준비 시 소스 파일 끝의 빈 줄 하나만 정리했으며 실행 로직은 검증한 빌드와 같다.

사용자가 로그인 유지 상태로 종료한 뒤, 해당 프로그램에서 Staging HTTPS로 가는 연결만 임시 차단했다. 재실행한 ‘최종검증03’에서 입력과 로컬 저장을 확인했다. 아래 시각은 모두 **2026-09-06 KST**다.

| 사건 | 시각·결과 |
|---|---|
| 차단 전 마지막 핸드셰이크 | 06:21:39.756954 |
| 앱의 서버 연결 차단 | 06:23:11.312200 |
| 차단 중 | 로컬 저장 완료, offline, 전송 대기 1건 |
| 해제 직전 로컬 DB 확인 | 06:24:42에도 이전 핸드셰이크 시각 유지 |

수동 재시도·재로그인·작품 전환 없이 기다리도록 안내한 상태에서 자동 복구됐다. 근거는 로컬 핸드셰이크 메타데이터, 앱 진단 로그, 사용자 화면 확인이다. 임시 방화벽 규칙은 삭제 완료했다.

**실서버 계약 배치 전송 성공을 입증한 시험은 아니다.** 계약 batch ID는 없으며, 대기 1건은 기존 일반 동기화로 처리됐다. 서버 감사 로그를 별도로 조회하지 않았으므로 서버 측 중복 적용 0건까지 입증했다고 주장하지 않는다. 계약 배치의 차단·멱등성·늦은 응답 처리는 로컬 회귀 테스트로 검증했다.

## 9. iPad 측 회신 요청

아래 형식으로 결과를 회신해 양쪽 공통 규칙을 확정해 달라.

1. 검사한 iPad 저장소·브랜치·커밋·앱 빌드 및 계약 version/digest/protocol.
2. C1–C12 각각에 대해 `일치 / 수정 필요 / 미검증`과 해당 코드 위치·테스트 이름.
3. 같은 계정 재로그인, 계정 변경, 작품 전환, 백그라운드 복귀 때 캐시/세대/조회 시도 기록의 처리.
4. 지연 재시도 간격, 중복 요청 억제, 취소된 세대의 응답·SDK 인증 이벤트 처리 방식.
5. 전송 시작 경계, 전송 결과 불명 상태, 영수증 저장, 동일 ID 재시도 방식.
6. 닫힌 관문에서 원고 로컬 저장과 일반 동기화가 어떻게 표시되는지, 계약 쓰기 RPC 0회 검사 결과.
7. 미지원 범위와 Windows와 다른 동작. 실제 관문 개방·mode 전환이 필요하다고 판단되면 구현 확인과 별도의 시험 계획으로 제시.

iPad의 최신 구현은 이번 Windows 작업에서 검사하지 않았다. 특히 모바일 백그라운드 중단·재개와 프로세스 종료의 네트워크 수명은 iPad 측 검증이 필요하다. 양쪽 테스트 결과가 확인되기 전에는 계약 경로 전환이나 prod 전환이 완료됐다고 판정하지 않는다.

참조 구현: `handshake_lifecycle.py`, `network_recovery.py`, `sync_manager.py`, `sync_contract.py`. 테스트: `tests/test_handshake_stability.py`, `tests/test_network_recovery.py`, `tests/test_sync_contract_stage8.py`. 이 문서에는 비밀키·토큰·원고 본문을 포함하지 않았다.
