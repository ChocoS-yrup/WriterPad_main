# Windows 합성 원고 1개 초기 업로드 완료

사용자의 Windows 새 시험 작품 생성·초기 업로드 **“승인”**에 따라 진행했다. 실제 쓰기는 지정한 새 작품 하나에 한정했으며 iPad 실행 승인은 포함하지 않았다.

## 확정 대상

| 항목 | 결과 |
| --- | --- |
| 작품 | 본문수신검증 20260911 |
| 서버/Windows 작품 UUID | `9a78c51c-7de9-43a8-be54-d25a22d08a28` |
| 일반 원고 | `메인/원고/1권/1화.txt` 1개 |
| 원고 UUID | `502cdbe7-814c-42f8-8ed4-81c40cd94902` |
| 경로상 부모 ‘1권’ 폴더 UUID | `1de12e60-f998-48b9-aae9-7675b4b42fb9` |
| 본문 | UTF-8, BOM 없음, LF, 마지막 줄바꿈 포함, 93 bytes |
| 본문 SHA-256 | `cdfcc92e4b06906d9c54e11b4ad263cf913105fdff7669ac5b69b1f42bb7f96d` |
| 서버 문서 revision | 1 |
| 서버 원고 parent_folder_id / structure_revision | null / null |
| 서버 폴더 | 11개, 각 revision 1 |
| 내부 경로 정렬 문서 | 1개, revision 1 |
| UUID tree_orders | 0행 |

서버 부모/구조 필드는 실제 null이며 추정값을 넣지 않았다. 위 부모 UUID는 서버 폴더의 경로상 부모다. 최종 iPad `SyncV2LocalSnapshotApply.swift`는 본문 상대 경로의 계층을 확인하고 같은 경로의 폴더를 찾아 로컬 parent를 정한다. 이 경로의 소스 해시는 최종 후보 manifest와 대조했다. 사후 검사에서 **서버 필드 null 보존**과 **iPad 로컬 원고의 실제 부모 UUID**를 구분해야 한다. UUID 기반 구조·정렬 전환 성공으로 판정하지 않는다.

## 수행과 검증

- 설치 EXE는 검토 후보 SHA-256 `76e695051d83977a15b66892557cba13dc4eb95a6124d0710d503337193fb04d`와 일치했다. 후보의 동결 소스 90개 해시를 검증했다.
- Windows 앱이 종료된 상태에서 현재 파일 목록·해시와 DB/설정 사본을 보존했다. 원본 DB를 SQLite로 열어 검사하지 않고 별도 검사 사본을 사용했다.
- 동결된 정상 생성 함수로 실제 작품 폴더에 새 UUID를 발급했다. `권 만들기`의 원고 25개 생성 경로는 사용하지 않고 폴더 하나와 원고 하나만 생성했다. 격리 검증 UUID는 재사용하지 않았다.
- 앱 GUI나 전체 동기화 대기열을 실행하지 않았다. 동결 소스의 생성·저장·본문/정렬 직렬화·인증 함수와 서버의 기존 RPC를 사용하는 단일 작품 준비 스크립트로 처리했다. 따라서 Windows 일반 UI 자동 동기화 자체의 실기기 통과를 주장하지 않는다.
- 요청 계획을 고정한 뒤 HTTP 전송 직전 endpoint·RPC·전체 payload·순서를 검증했다. 계획된 요청 14개와 범위 밖 요청 5개의 허용/차단을 네트워크 없는 검사로 확인했다. 실제 요청은 프로젝트 등록 1, 폴더 생성 11, 일반 원고 생성 1, 내부 정렬 문서 생성 1이었다. 전역 대기열 drain이나 관문 변경을 하지 않았다.
- 기존 앱의 OS 사용자 인증 잠금과 세션 처리 경로를 사용했다. 동일 Staging 계정이 기존 지정 시험 작품의 소유자임을 확인했다. 자격증명은 공유 파일에 포함하지 않는다.
- 마지막 원고/정렬 저장은 2026-09-11 10:18:12 KST경 완료됐고 이어서 새 UUID의 projects/documents/folders/tree_orders를 조회했다. 실제 서버 본문 바이트·해시와 폴더 UUID/부모/이름을 대조했다. 정확한 요청 시각은 request-scope-log.json에 있다.
- Windows 새 원고와 내부 정렬 문서의 로컬 상태는 각각 revision 1 / synced, 작업 2개는 completed다. 새 폴더 baseline을 서버 결과로 반영했다.
- 기존 설치 폴더의 모든 파일은 전후 동일했다. 기존 DB 29개 테이블의 모든 기존 행은 보존됐다(sqlite_sequence 카운터 제외). AppData는 sync_v2.sqlite3만 변경됐으며 기존 보류 파일·device ID 등 다른 파일은 동일했다. 계약 송신 관문은 0개 열린 상태를 유지한다. Windows 앱은 끝까지 실행하지 않았다.

서버의 다른 모든 작품을 전수 재조회한 증거는 없다. 이번 송신이 새 UUID로만 제한됐다는 근거는 고정 계획과 HTTP 검증·기존 RPC의 대상 제한이다. iPad의 현재 상태도 새로 조회하지 않았다. 실제 DB·계정·기기 식별자·토큰은 제외하고 합성 자료와 필요한 결과만 전달한다.

## 다음 사용자 행동

Windows 준비는 완료됐으므로 다시 생성·업로드하지 않는다. 다음은 이 UUID **한 개**의 iPad 최초 본문 수신이다. 별도 승인 후 iPad 담당에게 승인된 실행 요청을 전달한다. 지금 iPad 앱이나 Windows 동기화 버튼을 조작할 필요는 없다.

다음 iPad 승인 제안 범위는 기존 후보의 오프라인 준비 → 동일 Staging 인증/목록 → 지정 UUID가 미가져옴인지 확인 → 최초 수신 한 번 → Wi-Fi를 끄고 1화 합성 본문 표시 확인 → 앱 완전 종료와 사후 바이트/보존 검사다. 실패 시 자동 재개·반복 수신하지 않는다. 원고 편집·실제 송신·관문 변경·설치·서명 갱신·prod 전환은 포함하지 않는다.

준비 시 예상 밖 프로세스 재등장 또는 등록/정책 변경이 확인되면 실행을 중단하고 현재 상태를 회신한다. 기존 iPad 프로필 만료 기록은 **2026-09-12 18:19:25 KST**이며 만료/보안 오류 시 자동 재설치·온라인 신뢰 복구를 하지 않는다.
