# Windows → iPad 역방향 계약 사전 검토

2026-09-06 KST. 수신: `ipad-reverse-contract-preflight-20260906.zip`.

**후보와 iPad 격리 시험 근거를 대조했다. 현재 Windows 설치본에는 관문을 닫은 채 불변 검토 요청을 준비·보존·내보내고 일반 자동 송신에서 제외하는 제품 경로가 없다. 실제 신규 요청을 발급하지 않았으며, 다음 개발 단계는 이 준비 기능의 추가다.**

첫 계약(빈 2권 + 원고 순서)은 완료 상태로 보존한다. 첨부에 적힌 다른 작업의 ‘다음 진행’ 요청이나 실행 절차를 이 작업의 실제 전송·관문 개방 승인으로 해석하지 않았다.

## 후보와 iPad 근거

- Staging / 최종검증03 `1bd47431-0773-482c-8eb5-ac9e2952b6f4`.
- 원고 `14df4a55-b7cd-4790-bc53-f84148418c0f` 아래 빈 3권 create, base 0 → 예상 revision 1.

- ZIP manifest 6개 파일의 크기/SHA256 일치. 제출 test-summary는 1개 통과/0 실패/0 건너뜀이며 실행 로그의 시험 이름·성공과 일치한다.
- 패치는 `WriterPadTests/SyncV2SnapshotPullTests.swift` 한 파일에만 적용되는 시험 추가다. 실제 수신 서비스·SQLite·SwiftData 저장소와 합성 본문을 연결하며, 원격 조회는 대역이다. 동일 후보 반복 수신, 높은 revision의 legacy 숨김 순서 문서, 저장소 재열기 후 동일 UUID와 계약 순서 revision 2를 확인하는 구성이다.
- 파일 본문 보존·빈 폴더·기존 노드 속성 단언은 최초 반복 수신 뒤에 있고, 저장소 재열기 뒤에는 노드 ID 집합·순서·큐를 재확인한다. 모든 단언을 재열기 뒤에도 반복했다고 확대하지 않는다.
- 별도 UserDefaults의 닫힌 관문 및 idle 큐 단언은 있다. 송신기/dispatcher가 연결되지 않은 시험이므로 자동 송신 호출 전체의 검증은 아니다. 실기기 통신·화면·앱 완전 재시작 시험도 아니다.
- Windows에서 Swift 시험을 재실행하지 않았다. 제품 파일·설치가 그대로라는 최신 진술은 source-scope.json의 제출 근거이며, 이번 ZIP에는 전체 소스·새 바이너리가 없어 최신 호스트 파일 전체를 독립 재해시한 것은 아니다. 기존 설치 식별과 첫 계약 완료 근거는 유지한다.

## 지원 공백의 코드 근거

1. `sync_contract.py:413`의 순수 builder는 요청을 구성할 수 있다. 하지만 이것만 호출하는 외부 스크립트는 설치된 앱의 준비·보관·내보내기 기능이나 런타임 식별 검증을 대신하지 못한다.
2. `sync_v2_store.py:3677`의 `create_structure_batch`는 닫힌 관문에서 `CONTRACT_NOT_ALLOWED`로 거절한다. 통과하면 `sync_contract_batches`, `sync_structure_operations`, `enqueued` 사건을 함께 기록한다.
3. `sync_v2_store.py:3783`의 `next_ready_structure_batch`는 해당 pending/retry_wait 배치를 고른다. `sync_manager.py:3625` 부근 일반 재시도 경로는 준비 검사를 통과한 배치를 실제 송신기로 연결한다. 따라서 `retry=False`는 그 호출의 즉시 재시도만 생략하며, 이후 자동 송신에서 제외하는 표식이 아니다.
4. `sync_manager.py:2585`의 경로 변경 API 및 `sync_v2_store.py:3306`은 로컬 구조 반영과 큐 생성을 묶는다. 기존 `scripts/contract_path_preflight.py:1702` 부근 canary 경로도 실제 폴더를 먼저 만든다. 이번 검토 전용 준비 요구에 사용할 수 없다.
5. 현재 DB에는 계약 batches/results/diagnostics 테이블이 있지만 별도의 계약 preparation 저장소가 없다. 추적 제품 코드 검색에서도 해당 준비·내보내기 경로가 확인되지 않았다.

실행 중 writer_device_id/client_build_id는 아직 확인하지 않았다. 소스의 환경변수 기본값을 실제 송신기 ID로 채우지 않았고, 신규 3권/batch/operation UUID·request hash를 발급하지 않았다.

## 필요한 최소 변경안

1. **준비·보관·내보내기:** 연결된 앱의 실제 device/build ID와 최신 작품·계약·구조 기준으로 위 두 intent만 만든다. 새 ID는 한 번 발급해 canonical 요청·해시·기준 지문과 함께 불변 준비 저장소에 보존한다. 준비만으로 폴더·identity·설정·일반/구조 송신 큐·관문이 바뀌지 않아야 한다. 재열기/재내보내기에도 같은 요청을 유지한다.
2. **명시적 한 배치 송신 경로:** 이후 별도 실행 승인을 받은 경우에만 고정 준비 ID/hash를 선택한다. 기존 C9의 준비 시작·송신 직전 재검사와 single-flight를 유지하며, preparation 및 그 출신 배치가 일반 자동 송신/재시도에 섞이지 않게 한다. 기존 완료 수정을 다시 만들지 않고 연결한다.
3. **종료·응답 유실:** 성공 영수증을 같은 요청과 연결하고 관문 닫힘을 확인한다. 거절·응답 유실에서 자동 재전송하거나 요청을 재발급하지 않으며, 읽기 전용 결과 조회와 로컬 미완료를 구분한다. 로컬 구조는 확정 서버 결과의 일반 수신으로 반영한다.
4. **새 경계만 검증:** 관문 닫힌 준비/내보내기/재열기 불변성, 자동 dispatcher 제외, 변경된 기준 거절, 실제 런타임 식별 내보내기, 같은 기존 순서 UUID/base 1 보존, 응답 처리 경계를 격리 검사한다. 첫 2권 시험이나 이미 완료한 회귀·설치를 근거 없이 반복하지 않는다.

위는 검토 가능한 변경 범위안이다. 이번 첨부 검토에서 제품 코드를 수정하거나 이 기능을 구현한 것은 아니다. 기능이 확보된 뒤 새 요청을 iPad와 대조하고, 최신 상태 및 결과 처리 절차에 따라 신규 수동 1회 송신의 범위를 별도로 정한다.
