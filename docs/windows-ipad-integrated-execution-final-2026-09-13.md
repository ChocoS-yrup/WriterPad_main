## 2. 생성 방법 — Windows 일반 화면, 실제 ID는 송신 전에 고정

별도 초기화 도구나 DB 직접 편집을 추가하지 않는다. **초안의 시험 UUID 5개는 사용하지 않는다.** 승인된 설치·오프라인 준비 중 Windows 일반 생성 UI가 발급한 ID를 한 번 기록하고, 이후 양측이 그 명세만 사용한다. iPad는 초기 항목을 만들지 않는다.

| 역할 | 처음 위치 | 생성 순서 |
|---|---|---|
| T | `메인/메모장/통합검증 20260913` | 1, 폴더 |
| A | `T/A` | 2, 폴더 |
| B | `T/B` | 3, 폴더 |
| R | `T/A/왕복.txt` | 4, 문서 |
| E | `T/A/빈문서.txt` | 5, 문서 |

메모장 ID `95b8e4d0-1d8d-4af5-b121-0888d0157661`와 정렬 ID `9ca39b36-aad6-5347-97b9-ff00c9234aea`만 기존 고정값이다. 메모장 정렬에는 T를 **끝에 한 번 추가**하고 기존 형제 상대 순서를 유지한다. 이후 메모장 정렬은 변경하지 않는다. T/A/B 정렬 ID는 실제 부모 ID로 `UUIDv5(서버 작품 ID, "tree-order:" + 부모 ID)`를 다시 계산한다.

S0 설치 전 기존 설치물·본문·데이터의 유효한 백업은 재사용하고 이후 바뀐 파일만 추가 보존한다. 새 후보는 1절 해시를 대조하여 설치하며, 과거 증거를 덮어쓰지 않는다. 설치 경로는 Windows `D:\안티그래비티\scratch\집필프로그램\작가님 힘내세요.exe`다. 앱 종료·현재 상태 보존 뒤 교체하고 기존 원고/DB를 이관하거나 초기화하지 않는다.

오프라인 준비 시 양측 자동 동기화는 꺼 둔다. Windows는 자동저장도 잠시 끄고, 위 5개를 생성한 뒤 R에 W0를 붙여넣어 한 번 저장한다. E는 생성된 빈 본문 그대로 둔다. R↔E 전환 후 앱을 한 번 정상 종료·재시작하여 두 본문과 대기 11개가 유지되는지 확인한다. 네트워크 실행 범위를 아직 연결하지 않는다.

Windows 앱 종료 후 전용 `integrated-editor-20260913/workspace.sqlite3`와 존재하는 WAL/SHM을 새 비공개 증거 폴더에 파일 복사한다. **복제본만** 읽어 `state`의 노드·정렬·jobs를 확인하고 `test-targets.json`을 기록한다. 원본 SQLite 연결이나 SQL UPDATE는 사용하지 않는다. 명세에는 T/A/B/R/E의 실제 ID·부모·이름, 정렬 4개, 메모장 전후 자식 순서, 본문 해시, 대기 작업 종류/ID/순서, 복제 파일 해시를 넣는다. 세션·토큰·다른 원고는 교환하지 않는다.

통신 전 조건은 새 시험 항목이 정확히 5개, 생성 5 + 정렬 5 + 본문 1 = **대기 11개**, 메모장 정렬 작업 1개, 송신 batch/사용 요청 0개, R=W0, E=0바이트다. 기존 seed 항목의 추가 변경·동명 항목·다른 대기가 있으면 보존 후 중단한다. Windows 실행 설정에는 실제 허용 ID를 넣는다. **iPad의 실제 시험 ID·명세 해시는 별도 명세로 보존·대조한다. 실행 JSON에는 실행 ID·계정·만료·한도·자동·checkpoint를 결합한다.** 양측 별도 명세의 대상과 해시가 일치한 뒤에만 최초 송수신으로 넘어간다. 승인 이후 이 명세 기록은 정해진 생성 절차의 결과이며, 항목 추가나 범위 확대가 아니다.

## 3. 본문과 기대값

아래 `\n`은 실제 LF 한 글자다. 백슬래시와 n 두 글자를 입력하지 않는다. 마지막 LF도 보존한다. 본문별 UTF-8 바이트 수·SHA-256은 [로컬 산정 기록](../_evidence/windows-integrated-editor-coordination-20260913/execution-plan-v2/plan-calculation.json)에 있다.

| 이름 | 정확한 문자열 |
|---|---|
| W0 | `Windows 통합 집필\n문서 전환 확인 😀\n` |
| I1 | `iPad 통합 집필\n문서 전환 확인 😀\n` |
| E 임시 | `빈 본문 확인\n` |
| W2 | `Windows 수신 후 저장\n양측 정상 대조 완료 😀\n` |
| 마지막 Windows 쓰기 | `Windows 충돌 기준\n` |
| 마지막 iPad 초안 | `iPad 보존 초안\n` |

빈 본문은 UTF-8 0바이트, SHA-256 `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`다. 공백·개행을 보충하거나 삭제로 해석하지 않는다. E의 새 빈 문서 수신과, iPad에서 E 임시 본문을 저장한 뒤 전부 지워 다시 저장하는 동작을 모두 확인한다. 중간 본문은 큐/쓰기 기록으로 구분하고 최종 수신 본문은 0바이트로 대조한다.

## 4. 실행 순서 — 설치 한 묶음, 기기 확인 한 묶음

아래는 최종안 승인 **후** 실행할 순서다. S 표시는 기존 1~7 진행 단계 번호와 별개인 시험 구간이다.

| 구간 | 실행 측과 동작 | 상대 수신 뒤 기대 상태 |
|---|---|---|
| S0 | 양측 설치·오프라인 준비, Windows가 위 방법으로 ID 명세 생성 | T=[A,B], A=[R,E], R=W0, E=빈 본문. 아직 서버 반영 없음 |
| S1 | Windows 자동 10초 간격으로 11개 큐 처리 → 자동 끄기 → Windows 수신 1회 → iPad 첫 수신·아래 복구 | 양측 동일 ID/본문. T=[A,B], A=[R,E], B는 빈 폴더 |
| S2 | iPad R=I1 저장 후 ‘자동 재개’, 첫 쓰기·복구 4호출을 완료한다. 자동이 꺼진 상태에서 E 임시→빈 본문 2회 저장, A를 `A수정`으로 이름 변경, R·E를 B로 이동, B=[E,R] 정렬을 모은 뒤 ‘자동 재개’ 1호출로 송신한다. ‘자동 일시정지’ 후 실행 완료를 확인하고 Windows 수신 | T=[A수정,B], A수정=[], B=[E,R], R=I1, E=0바이트 |
| S3 | iPad E만 삭제·송신 완료 → B 삭제·송신 완료 → Windows 수신 | B/R/E 모두 삭제. E는 B 삭제 전 별도 삭제 그룹. T=[A수정] |
| S4 | 같은 iPad에서 B를 T로 복원·송신 완료 → Windows 수신 | T=[A수정,B], B=[R], R=I1. E는 삭제 상태 유지. 복원은 목적지 끝에 추가하며 원래 순서 자동 복원을 요구하지 않음 |
| S5 | Windows R=W2 저장·송신 1회 → Windows 수신 1회 → iPad 최종 정상 수신 1회 | R 본문·revision·구조 일치, E 삭제 상태와 0바이트 보존 확인. 양측 예상 밖 대기/부분 반영 없음 |
| S6 | 양측 자동 끔. 동일 W2 기준에서 서로 다른 마지막 본문을 저장. Windows가 먼저 1회 송신 → iPad가 1회 송수신으로 충돌 관찰 | 서버/Windows는 마지막 Windows 본문. iPad에는 기준 W2·iPad 초안·원격 Windows 본문 및 의도된 대기 보존. iPad 송신 전 비교 충돌도 합격이며 409를 필수로 하지 않음 |
| S7 | 양측 자동 끄기·로컬 기록 보존·앱 정상 종료 | HTTP 0회. 충돌 뒤 iPad 일반 수신 없음. 서버 시험 자료 정리 삭제 없음 |

**양방향 수신 대기 규칙:** 복합 구조 변경 중 상대편 자동 수신과 수동 송수신을 멈춘다. 송신 측 큐 완료·미확정 batch 없음 확인 뒤 상대가 수신한다. S3 삭제 상태를 실제로 받은 뒤 S4 복원으로 넘어간다. 삭제·복원 최종 상태만 보고 원격 삭제가 검증됐다고 기록하지 않는다.

iPad는 ‘자동 일시정지’ 직전에 예약된 호출 1회가 남을 수 있다. **자동 꺼짐과 진행 중 호출 완료를 모두 확인한 뒤 S3으로 넘어간다.** 이 호출이 발생하면 빈 자동 최대 6회에 포함한다. Windows도 자동 체크 해제 뒤 진행 중 작업 완료를 확인하고 상대 수신으로 넘어간다.

자동은 S1 Windows와 S2 iPad에서만 사용한다. 양측 동시에 켜지 않는다. Windows 자동은 초기 11개 송신 후 끄고, iPad 자동은 처음 쓰기 및 복구 후 남은 S2 작업을 처리하는 구간에서만 사용한다. 계획된 중단에서 자동이 꺼지면 명시된 복구 버튼으로 재개한다. S3 이후는 수동으로 진행한다. 빈 자동 주기는 Windows 최대 4회, iPad 최대 6회로 산정했으며 초과 시 추가 주기를 허용하지 않는다. 백그라운드 진입·복귀도 실행/요청 기록에 포함한다.

## 5. iPad 계획된 중단·재시작

iPad 최초 실행 JSON 설정값은 `automatic:false`, `pollingSeconds:10`, `maximumRequests:520`, `maximumWrites:26`, `maximumAuthentication:16`, `checkpoint:"all"`이다. 실행 JSON에는 실행 ID·계정·절대 만료·한도·자동·checkpoint를 결합하고, 실제 시험 ID·명세 해시는 S0의 별도 명세로 보존·대조한다. 이 문장의 설정값은 설명이며 현재 실행 JSON을 작성하거나 적용한 것이 아니다.

각 지점 첫 도달에서 한 번씩 중단하며, 중간에 실행 ID/checkpoint/한도를 바꾸지 않는다. S2에서 R 저장 후 ‘자동 재개’, 계획된 중단 후에는 아래 ‘송수신·복구’를 사용한다.

| 순서 | 지점 | 재개와 예상 요청 |
|---|---|---|
| 1, S1 | `afterOriginalApply`: 첫 신규 TXT 적용 뒤 baseline 전 | 보존 snapshot 재적용, 준비 RPC 2회·새 snapshot GET 0회 |
| 2, S2 첫 쓰기 | `beforeHTTP`: frozen, 원래 POST 0회 | 준비 2 + 재비교 GET 3 후 원래 POST |
| 3, 같은 쓰기 | `afterCommitResponse`: httpStarted, 응답 미저장 | 준비 2 + 원래 batch receipt SELECT 최대 2회. POST 재전송 없음 |
| 4, receipt 저장 직후 | `afterStoredResponse`: responseStored | 준비 2 후 로컬 완료. POST 재전송 없음 |

각 중단에서 상태 기록을 보존하고 **정상 종료·같은 설정 재시작 1회**, 총 4회로 제한한다. 재개는 ‘송수신·복구’만 사용하며 별도 ‘연결 준비’는 추가하지 않는다. 이는 영속 중단·정상 재시작 검증이며, 실제 패킷 유실이나 프로세스 강제 종료 시험으로 보고하지 않는다.

receipt는 원래 batch의 계정/작품/요청/응답 해시와 결과를 대조한다. 권한 거부·누락·불일치면 보존 후 중단한다. 정책 변경·새 batch·POST 재호출로 우회하지 않는다. 계획된 상태와 일치하는 중단은 위 복구까지 이어가며, 예상 밖 오류/불완전 snapshot에서는 멈춘다.

## 6. 확정한 요청량·시간 제안

**단계별 N은 쓰기 RPC 수, C는 중단 후 재개를 포함한 송수신 호출 수**다. 버튼 수와 같은 뜻이 아니다. iPad 담당자 코드 산정은 S2=7, S3=5, S4=3, 합계 **15개 쓰기 RPC**다. 실제 서버 측정값이 아니며 추가 저장·재시도 없이 아래 지정 동작을 수행하는 조건이다. 기존 쓰기 한도 26/보수 예산은 유지하되 여유로 작업을 추가하지 않는다.

| 구간 | Windows N / C | iPad 코드 산정 N / C |
|---|---|---|
| S1 | 11 / 12 | 0 / 2 |
| S2 | 0 / 1 | 7 / 5 (N 상한 12) |
| S3 | 0 / 1 | 5 / 2 (N 상한 8) |
| S4 | 0 / 1 | 3 / 1 (N 상한 6) |
| S5 | 1 / 2 | 0 / 1 |
| S6 | 1 / 1 | 0 / 1 |
| 합계, 빈 자동 주기 제외 | **13 / 18** | **15 / 12 (N 상한 26)** |

Windows 초기 11개는 동결 후보 저장 API를 가상 자료에 적용하여 계산했다. 1주기당 쓰기 8요청 또는 수신 7요청으로 정상 **13×8 + 5×7 = 139요청**이다(Auth 포함). 빈 자동 최대 4주기는 28요청이므로 167요청, 총량 배분은 **200회**다.

iPad 보수식 `10N + 5C + 3B + 2L + 2P + A + E`에 N≤26, C≤18(빈 자동 6 포함), B=1, L=1, P=0, Auth A≤16, 기타 조회/중단 여유 E≤80을 넣으면 **451회**다. 배분은 **520회**, 양측 총량은 **720회** 제안이다. E와 잔여량은 기존 구간 안의 소요 여유이며 새로운 쓰기·장애 시험·로그인·정리 작업을 허용하지 않는다. 실패한 시도도 사용량에 포함하고 양측 잔여량을 서로 이전하지 않는다.

S5 정상 대조에 들어갈 때 Windows 최소 60회, iPad 최소 80회를 남긴다. 마지막 정상 수신·충돌 관찰 비용을 이 안에서 사용한다. 잔여량/시간이 부족하면 S6을 시작하지 않고 미실행으로 기록한다. 하드 한도 이후 추가 수신이나 종료용 요청을 보내지 않는다.

| 항목 | Windows | iPad |
|---|---|---|
| 전체 HTTP 배분 | 200 | 520 |
| 쓰기 상한 | 13, 계획·기록 관리 | 26, 하드 차단 (지정 작업 산정 15) |
| Auth 상한 | 30, 계획·기록 관리 (정상 18·빈 주기 최대 4 포함) | 16, 하드 차단 |
| 자동 주기/구간 | 10초 / S1만 | 10초 / S2만, 자동 재개·자동 일시정지 |
| 공통 실행 시간 | 양측 동일 T0부터 90분, `max_seconds=5400` | 동일 절대 만료 |

**강제 수준을 구분한다.** Windows 현재 후보가 매 요청 전 영속 강제하는 것은 전체 HTTP/시간/대상 범위다. 쓰기/Auth별 별도 하드 카운터나 구간별 자동 차단 기능이 있다고 주장하지 않는다. 위 쓰기·Auth·빈 주기 상한은 작업표/기록 확인으로 관리하는 계획 한도다. iPad는 담당자 확인상 전체 HTTP·시간·쓰기·Auth를 모두 하드 차단하며 단계별 호출·빈 자동 횟수는 계획·기록으로 관리한다. Auth 16회 안의 완료를 보장하지 않는다. 소진 시 복구/정상 확인이 남아 있어도 중단한다. Windows에도 유형별 하드 차단이 구현됐다고 설명하지 않으며 이 차이로 제품 변경을 추가하지 않는다.

**제안 T0는 2026-09-13 11:00:00 KST = 02:00:00 UTC(Unix 1789264800), 절대 만료는 12:30:00 KST = 03:30:00 UTC(Unix 1789270200)**다. 설치·첫 기기 실행을 포함한 S0~S7을 이 90분 안에 수행한다. 늦게 시작하거나 앱을 재시작해도 만료를 갱신하지 않는다. 실행 시간 변경은 사용자와 시각만 다시 맞추며 제품 검사나 자료 대조를 반복하지 않는다.

Windows 실행 범위의 `max_requests=200`, `max_seconds=5400`, `expires_at=1789270200`, `automatic=true`(S1에서 자동 사용을 허용하는 범위 값)를 사용하되 UI 자동 체크는 S0에서 꺼 둔다. iPad JSON의 `automatic:false`는 초기 자동 상태이며 S2 버튼으로만 재개한다. 서로 다른 필드 의미를 맞추려고 JSON 값을 일괄 변경하지 않는다.

S0의 실제 시험 ID·명세 해시는 양측 별도 명세로 보존·대조한다. Windows 실행 범위에는 실제 허용 ID·기존 계정/기기 ID를 결합하고 보호 파일 해시는 기존 wrapper에 기록한다. iPad 실행 JSON에는 실행 ID·계정·만료·한도·자동·checkpoint를 결합한다. 계정은 지정 Staging 작품의 기존 소유 계정이어야 하며 새 계정 로그인/토큰 갱신 조작/다른 기기 ID로 교체하는 절차를 추가하지 않는다. Windows의 허용 노드는 T/A/B/R/E, 정렬은 메모장/T/A/B뿐이다. 원고·DB·WAL/SHM·device·hold 보호 파일 값을 기록하고 매 요청 전 기존 검사에 따른다.

설명된 실제 실행 범위 파일은 사용자 승인 후 S0에서 생성·결합한다. `reviewed-execution.json`을 지금 생성하거나 기존 관문/hold를 수정하지 않았다. 기존 설정이 있다면 바이트 보존 후 비교하며 다른 실행을 덮어쓰지 않는다. S7에서는 원래 설정과 새 시험 전용 상태를 구분해 보존·마감하고, 완료된 실행을 자동 재개하지 않도록 자동을 끈 채 종료한다.

## 7. 현재 후보로 확인하지 못하는 항목

- iPad는 구조 중간 불완전 snapshot을 저장하면 같은 snapshot만 재적용한다. 새 snapshot으로 자동 회복하는 기능은 이번 수신 대기 절차로 **검증되거나 구현되는 것이 아니다**. 이를 필수 기능 완료로 삼으려면 iPad 보완이 필요하다.
- Windows 후보에는 iPad와 같은 선택형 영속 장애 주입 지점이 없다. 이번 계획에 Windows의 확정적인 응답 유실·실제 receipt SELECT/RLS 검증을 끼워 넣지 않는다. iPad receipt 성공을 Windows 실제 조회 성공으로 확대하지 않는다. **Windows 실서버 receipt 권한은 이 실행 후에도 별도 미확인일 수 있다.** 강제 종료·통신 차단이나 DB 상태 편집으로 장애를 만들지 않는다.
- 마지막 실제 충돌 보존 관찰 측은 iPad 한쪽이다. Windows 자체 충돌·복구의 기존 격리 검사 결과는 재사용하되, 이번에 양측 실기기 충돌을 각각 확인했다고 보고하지 않는다.
- Windows 전용 저장소 검증이며 기존 일반 프로젝트 트리 전체 전환·상시 무제한 자동 동기화·prod 준비 완료를 의미하지 않는다.

따라서 이번 실행은 현재 후보의 지정된 교차 검증이다. 위 미확인/미구현 항목까지 포함한 전체 기능 완료 선언과 구분한다.

## 8. 준비 완료·승인 경계와 증거

iPad 수치·설정 확인은 [사용자 회신 전사](../_evidence/windows-integrated-editor-coordination-20260913/execution-plan-final/ipad-numeric-confirmation.md)에 보존했다. 이전 질문 두 개는 해소됐으며 같은 회신·ZIP·검사를 다시 요구하지 않는다. 최신 전달 자료는 [최종 실행 요약](ipad-integrated-execution-final-brief-2026-09-13.md)이다. 직접 메시지 발송은 하지 않았다.

**사용자에게 승인받을 범위는 위 후보 양측 설치, S0 한정 오프라인 생성·설정 결합, 지정 Staging 작품의 S1~S6 송수신/계획된 복구·충돌, S7 로컬 종료이며 시간·요청·대상은 위 한도다.** 정상 상태는 버튼마다 재승인을 받지 않고 이어간다. 예상 밖 오류·대상/계정/본문 불일치·한도 소진에서는 현재 기록을 보존하고 중단한다. 이 문서만으로 실행을 승인한 것으로 간주하지 않는다.

이번에 수행한 것은 회신 원문 보존, 코드 읽기, 가상 저장소로 초기 큐 수 계산, 문서 작성이다. 제품 검사 재실행·설치·실서버 요청·실제 본문/DB/관문/hold/preferences 변경은 없다. 근거는 `_evidence/windows-integrated-editor-coordination-20260913/execution-plan-v2/`에 보존했다. iPad 수신 원문 SHA-256은 `edfac5ad6901d8aa3f2778a91296c08f290243f08f8bc61017b0ba82feb76b78`이다.
