# 일반 편집·자동저장 다음 단계 준비

후속 상태: 사용자 요청으로 화면·저장/단발 송신 연결·격리 검증 1~3번을 완료했다. 현재 결과는 [Windows 구현 및 검증 완료 기록](windows-general-editor-runtime-prepared-2026-09-13.md)을 따른다. 아래 내용은 그 이전의 조사·범위 제안 기록이다.

상태: Windows 독립 준비와 격리 확인 완료. 확대 실행 후보는 아직 준비 중이며 설치·실제 송수신 승인을 요청할 단계가 아니다. 이번 사용자 요청은 다음 준비 진행으로 적용했고, 완료된 왕복 실행 승인을 새 revision 쓰기에 확대하지 않았다.

## 이번 변경과 확인

일반 저장의 `WritingProjectManager.write_text_file`은 Windows의 기본 텍스트 쓰기 때문에 입력 LF를 CRLF로 변환했다. 송신 큐는 입력 문자열의 UTF-8을 사용하므로 파일 바이트와 큐 본문이 달라졌다. `newline=""`를 지정해 입력 개행을 그대로 기록하도록 수정했다. 이미 저장된 파일은 재작성하지 않으며, 명시적으로 CRLF가 포함된 입력도 그대로 보존한다. fsync·원자적 교체·실패 시 기존 파일 보존은 유지한다. 설치 후보의 같은 소스와 비교한 추가 변경은 이 한 지점이다.

- 수정 전 신규 검사 4개 중 LF·CRLF 바이트 대조 2개 실패를 재현했다.
- 수정 후 신규 검사 4개 통과: LF, 명시적 CRLF, 빈 본문·끝 개행 없음, 교체 실패 시 기존 본문 보존.
- 최종 감사 복사본에서 추가 시나리오 4개 통과: 관문 닫힘 저장, 관문 열림 저장, 유휴 자동저장, 동일 본문 재저장.
- 실제 제품 파일 저장·업로드 진입·큐·보류 검사·자동저장 컨트롤러 메서드를 사용했다. 관문 열림은 복사본의 시험 조건이며 실제 권한 구현이 아니다.
- 저장 후 디스크와 큐 내용 일치, 서버 기준 revision 3 유지, 저장소 재열기 후 operation ID 유지, 송신 보류 유지, 프로젝트 행·타 작품 문서 행 보존을 확인했다. 동일 본문은 새 큐 항목 0개였다.
- 일반 앱 전체 화면, Auth, 실제 dispatcher·수신 적용·백업 worker는 실행하지 않았다. 최소 manager 객체로 해당 메서드를 연결한 검사이므로 일반 앱 전체 통과로 표현하지 않는다.

증거: [격리 결과](../_evidence/windows-general-editor-preparation-20260913/20260912T164614686611Z/result.json). 완료 감사 사본의 해시는 관찰 전후 동일했고 실제 설치 폴더·AppData·서버에는 접근해 변경하지 않았다. 이전 검사 전체와 완료 왕복을 반복하지 않았다.

## 실행 전 반드시 연결할 차이

|현재 코드 경로|관측과 필요한 준비|
|---|---|
|`mode_writing.py:manual_save`, `writing_controller.py:sync_file`|일반 저장은 파일 저장 후 `upload_content_async`로 큐에 넣는다. 다음 후보는 실제 편집 이벤트와 이 경로를 사용해야 한다.|
|`sync_v2_store.py:_insert_document_operation`|관문 닫힘이면 ID_BASED 작품도 `LEGACY_EPOCH_0` 항목을 생성한다. 이는 현재 관문 설계의 분기이며 이번에 전역 변경하지 않았다. 관문 닫힌 설치 앱에서 먼저 편집하는 순서는 사용할 수 없다.|
|`sync_manager.py:retry_pending_syncs`|전역 보류는 송신을 막지만, 해제하면 일반 재시도·고아 작업 복구·후속 수신으로 범위가 넓어진다. 보류를 유지하고 대상 operation의 제한된 송신만 연결해야 한다.|
|`main.py:GENERAL_VALIDATION_ONLY`|설치 앱은 완료된 고정 본문 전용 화면이다. 플래그만 끄면 일반 시작·자동 복원까지 실행하므로 새 편집 제한 후보가 필요하다.|

Windows 후보 구현 순서는 다음과 같다. 지정 문서만 편집 가능하게 열고 초기 자동 송수신을 억제한다. 편집 저장 직전 새 계정·문서 기준 확인과 저장 권한을 확보하고, undo를 먼저 보존한 임시 관문 안에서 기존 저장·계약 큐 생성을 수행한다. 관문을 복원한 뒤에도 생성된 immutable operation을 유지하고, 승인된 단일 HTTP 경로에서만 송신한다. 실제 enqueue 권한과 후속 송신 권한을 각각 검사하며 전역 hold는 계속 유지한다. 실패·시간 초과·화면 이탈 시 로컬 저장 및 큐 성공 여부를 기록하고 이미 시도한 요청을 다시 만들지 않는다. 새로운 편집 중 앱 종료·응답 유실 재개는 별도 시나리오로 검증하기 전 실제 시험에 포함하지 않는다.

## 다음 실행 범위 제안

`general-editor-20260913-v1`. 같은 일반 시험 작품·문서를 revision 3에서 이어 쓰며 생성·폴더·정렬 변경은 없다. 정확한 본문과 해시는 [기계 판독 제안](../_evidence/windows-general-editor-preparation-20260913/proposed-scope.json)에 고정했다. 이것은 아직 양측 합의나 실행 승인이 아니다.

|순서|실제 편집 경로로 확인할 작업|예상 결과|
|---|---|---|
|1 Windows|일반 편집기에 `Windows 일반 편집 검증 20260913` 한 줄 추가, 수동 저장 후 제한 송신 1회|revision 4 / 197바이트|
|2 iPad|revision 4 수신, 일반 편집기에 `iPad 일반 편집 검증 20260913` 한 줄 추가·저장 후 제한 송신 1회|revision 5 / 232바이트|
|3 Windows|revision 5 수신, 일반 편집기에 `Windows 자동저장 검증 20260913` 한 줄 추가, 유휴 자동저장 확인 후 제한 송신 1회|revision 6 / 269바이트 / 8줄|
|4 iPad·양측|최종 수신·본문 대조, 종료 및 이번 변경만 복원|대기열·임시 권한 종료 감사|

모든 추가 줄 뒤 LF 1개를 포함한다. Windows 자동저장은 로컬 유휴 저장을 뜻하며 무제한 자동 송신·Realtime 활성화를 뜻하지 않는다. 제안 쓰기 예산은 Windows 문서 update 2회, iPad update 1회, 구조 쓰기·lease 0회다. Auth·handshake·조회 횟수는 실제 연결 후보를 준비하면서 확정한다.

다음 완료 조건: Windows 편집·저장·관문·단발 송신 연결 및 격리 검증, iPad 동일 범위 구현 가능 여부/정확한 UI 확인, 양측 후보와 설치·백업·요청 상한·종료 복원을 한 범위로 고정한 뒤 새 실행 범위를 한 번 승인받는다. 준비 중에는 사용자가 누를 버튼이 없다. prod 전환은 포함하지 않는다.
