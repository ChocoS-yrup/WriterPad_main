# iPad 일반 동기화 제한 후보 검토와 Windows 준비 범위

첨부는 일반 시험 작품에 대한 추가 제한을 연결한 **준비용 검토 후보**로 수용한다. 일반 동기화 실기기 실행 준비가 끝난 것으로 판정하지 않는다. 이번 사용자 메시지는 자료 전달이며, 첨부의 “다음 진행”·설치 승인 절차는 과거 기록 및 제안이다. 실제 설치·서버 요청·송신·관문/hold 변경의 새 승인으로 사용하지 않았다.

## 검토한 증거

- 입력 ZIP SHA-256: `eb88e1ff6975b2094526c03663ffc8bc9f11a82054e3f571239855b2d809c282`. manifest 7파일/ZIP 8항목의 정확한 구성·크기·SHA·CRC를 확인했다.
- 소스 목록 230파일의 digest 계산값 `82ffa053c6d40fc1c9848557c8472cd03e9627be25e96235848b057f117ea5cb`가 보고와 일치한다. 변경 파일 목록과 patch 15개가 일치하며, 새 xcconfig와 GeneralSyncValidationScope 전체 내용을 patch에서 복원해 각각의 소스 해시도 확인했다.
- 83개 서로 다른 검사 이름과 10개 신규 검사의 집합, 로그별 통과 건수가 일치한다. 실행 결과는 iPad 보고이며 Windows에서 Swift 검사나 기존 검사를 재실행하지 않았다.
- 전체 소스·앱 바이너리는 첨부에 없다. 이전 patch 기준 digest는 `be0b2af5d89a386f12c3dc138fbebe9c4144439d8d94924d8edd109efc92f57a`이며, 230개 소스 전체를 여기서 복원·재빌드한 것으로 표현하지 않는다. 향후 실제 실행 후보를 고정할 때 최종 소스와 설치 식별 근거를 함께 묶으면 된다. 준비 단계마다 동일 검토 자료를 재요청하지 않는다.

Windows의 이미 확보한 종료 후 감사 사본에서 일반 시험은 문서 1행(정렬 제어 문서), 폴더 11행, UUID 정렬 12행이다. 일반 본문은 0개다. 계약 관문은 닫혀 있고 hold는 보존됐다. 이는 이전 보존 사본의 기준이며 오늘 서버 상태를 새로 조회한 결과가 아니다. 예전 문서의 Windows LEGACY/0 관측을 현재 기준으로 재사용하지 않는다.

정렬 제어 문서 UUID는 `6cbe47cd-67e5-5e27-8dbf-f3ae59255d52`, revision 1, SHA-256 `e290f19f8c47350c5b9b6e7314aadea1477508174b770860040148280517e1f6`다. 이를 새 합성 본문으로 덮어쓰지 않는다. 완료된 LEGACY 본문의 UUID·revision 3을 일반 시험의 기준으로 복사하지 않는다.

## 구현 대조 결과

| 경계 | iPad patch에서 확인한 내용 | Windows에서 이어 준비할 내용 |
|---|---|---|
| 작품 선택 | AppEnvironment가 제한된 dispatcherScope 전달 | 기존 manager의 현재 작품 문맥과 별개로 시험 전체 수명에 고정된 대상 제한 필요 |
| 수신·저장 | requireApplication에 local/server 짝 검사, recorder 및 SQLite enqueue에 제한 | 실제 수신/적용/큐 진입에서 계정·binding·문서·baseline 변동을 다시 검사 |
| lease | acquire/renew/release/inspect와 캐시 토큰 접근에 문서 제한 | 일반 ID_BASED 프로토콜에서 필요한 lease 동작부터 확정. LEGACY RPC 목록을 복사하지 않음 |
| HTTP | SDK session에 scope 고정, 직접 계약 HTTP에도 검사 | 기존 BodyHTTPTransport는 고정 LEGACY 본문용. 일반 계약 request와 결과에 맞는 별도 제한 및 주입 경로 필요 |
| 권한 | scope는 추가 제한이며 기존 인증/송신 권한을 발급하지 않음 | 양쪽 모두 새 전경 권한과 계정·binding·만료·이탈 취소를 실제 실행 UI에 연결 |
| 자동 처리 | 제한 후보는 Realtime 및 전체 복구/자동 재시도 제외 | hold 해제만으로 기존 retry/recovery가 작동하지 않도록 실행 범위를 명시적으로 격리 |

현재 Windows `general_test_gate.py`는 실제 대상의 준비·관문·보류 제어를 제공하지만, 고정 문서·RPC 예산을 가진 일반 검증 실행 권한을 대신하지 않는다. `sync_manager.py`에는 hold 검사 뒤 일반 재시도 및 stranded operation 복구 경로가 있다. 따라서 기존 hold를 단순 해제하고 시험을 시작하는 방식은 이번 준비 결과가 아니다. 실제 hold 파일과 관문 값은 변경하지 않았다.

iPad RPC fingerprint는 method·URL·본문의 바이트 일치를 검사하지만 횟수 예산·계정 권한·취소를 대신하지 않는다. 세션에 scope를 고정한 점은 TaskLocal 문맥이 사라진 뒤에도 제한을 유지한다. `sync_batch_results`는 현재 HTTP 목록에서 제외돼 있으므로 응답 유실 복구를 지원한다고 표현하면 안 된다. 이 한계는 첨부가 이미 명시했다.

## 다음 준비 순서와 완료 조건

1. **Windows — 새 시험 기준 설계.** 기존 ID_BASED metadata/폴더/정렬 기준에서 별도 합성 본문의 UUID·부모·이름·본문 바이트·hash·revision 진행을 문서로 고정한다. 현재 실제 일반 본문은 없으므로 생성 단계와 이후 편집 왕복 단계를 구분한다. UUID 충돌·서버 기준 확인은 이후 승인된 읽기 단계에서 수행하며, 준비 중 서버에 문서를 만들지 않는다.
2. **Windows — 실행 경계 코딩·격리 검증.** 실제 ID_BASED 계약 생성/본문 경로, scoped dispatcher와 최종 HTTP에 선택 작품·operation·계정·binding·전경 수명·RPC 예산을 연결한다. 기존 LEGACY 후보의 대상 상수만 바꾸지 않는다. 실제 경로의 잘못된 작품/계정/변경된 baseline/취소/중복 호출/불확실 응답을 합성 SQLite·파일·모의 HTTP로 검증한다. 완료된 본문 왕복이나 과거 검사 전체를 반복하지 않는다.
3. **iPad — 같은 기준의 전경 일반 검증 UI 준비.** 서로 다른 local/server UUID 짝을 유지하고 import/body의 동등 UUID 조건을 무조건 완화하지 않는다. Windows와 동일하게 계정·binding·화면 수명·만료·요청별 예산을 연결한다. 새로운 구조 생성 또는 본문 수정 단계에 실제 필요한 요청만 검토 목록에 넣는다. 현재 빈 RPC 목록을 일괄 개방하지 않는다.
4. **양쪽 — 최종 실행 범위 한 번 제시.** 정확한 후보 해시, 초기 생성 및 방향별 수신/송신 순서, 각 호출 횟수, 백업·설치·오프라인 관찰·감사, 필요한 관문/hold 변경과 최종 잠금 상태를 준비한다. 이 구체적인 범위를 승인받은 뒤 실행하며, 같은 범위의 버튼마다 재승인을 요구하지 않는다. 응답 유실은 보존 후 중단하고 자동 재전송/복구로 넘기지 않는다.

이번 첨부만으로 실제 설치할 후보나 송신 순서는 확정하지 않았다. 원격 데이터가 아직 없는 일반 본문의 초기 생성은 별도 고려가 필요한 작업이다. 기존 완료 본문 3줄→5줄 시험을 재사용해 일반 경로 검증을 대체하지 않는다.

후보에 보고된 기존 프로파일 만료는 2026-09-12 18:19:25 KST다. 실제 설치 시점에 유효성을 확인하고, 만료 시에는 기존 해시를 유효한 설치 후보처럼 재사용하지 말고 새 서명 후보를 실행 범위에 반영한다. 이번 검토에서는 프로파일을 갱신하지 않았다.

현재 사용자가 누를 버튼은 없다. 제품 코드·미커밋 변경·실기기 데이터·기존 증거를 보존했으며 새 서버 조회, 설치, 송신, 관문/hold 변경, prod 전환은 수행하지 않았다. 검토 기록과 Windows 보존 기준 요약은 `_evidence/ipad-general-sync-boundary-review-20260912/`에 저장했다.
