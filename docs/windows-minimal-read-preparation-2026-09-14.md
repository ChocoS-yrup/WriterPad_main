# Windows 최소 조회 준비안

2026-09-14. 사용자 요청은 **준비안 작성**이다. 이번에 기존 코드·대상 제안만 오프라인으로 읽었으며 제품 수정·재검사·설치·실제 HTTP·로그인 갱신·관문/hold 변경을 하지 않았다. 아래 횟수와 시간은 검토할 제안이지 실행 승인이나 실행 JSON이 아니다.

## 목적과 다음 판단 지점

기존 Staging 작품의 현재 계정 가시 범위에서 작품/계약, 공유 부모와 정렬, 기존 보호 영역의 변화, 새 UUID 후보의 충돌 여부를 확인할 최소 읽기 범위를 정한다. **첫 단계는 관찰 자료를 수집하고 차이를 보고하는 데서 끝난다.** 기존 앱으로 수신 적용하거나 신규 트리를 생성하지 않는다.

Windows J02 구현·최종 53개 결과는 보존한다. iPad J04 고유 49개 통과는 전달 보고로 접수했으며 오류 해제 조건 차이는 유지한다. J05의 저장 단계와 J07의 직접 backend 경계도 필드를 강제로 통일하지 않는다. 이 준비안을 위해 해당 검사를 반복하지 않는다.

## 제안하는 최소 요청 묶음

전제: 별도로 확정한 새 읽기 범위와 유효한 기존 사용자 세션이 있어야 한다. 자동 동기화는 사용하지 않는다. 순차 실행하고 다음 단계 전에 직전 결과를 검증한다.

| 순서 | 요청 | 횟수 | 확인 목적 |
| --- | --- | ---: | --- |
| Q1 | GET `/auth/v1/user` | 1 | 실제 subject가 기대 account와 같은지 확인 |
| Q2 | POST `/rest/v1/rpc/get_sync_handshake` | 1 | 지정 작품의 계약·capability·ID_BASED/epoch1 확인. 본문/구조 쓰기 RPC와 구분 |
| Q3 | GET `/rest/v1/projects` | 1 | 지정 작품 1행, owner/name/삭제 상태 확인 |
| Q4 | GET `/rest/v1/project_sync_settings` | 1 | 지정 작품 설정 1행, mode/epoch 확인 |
| Q5 | GET `/rest/v1/documents` | 1 | 지정 작품에서 보이는 전체 문서 행과 실제 본문/metadata 확보 |
| Q6 | GET `/rest/v1/folders` | 1 | 지정 작품에서 보이는 전체 폴더·부모 관계 확보 |
| Q7 | GET `/rest/v1/tree_orders` | 1 | 지정 작품에서 보이는 전체 정렬과 공유 부모 children/revision 확보 |

Q2 body는 기존 계약 경로의 `p_project_id`와 `p_contract_sha256` 두 필드만 사용하도록 계획한다. Q3~Q7은 각각 `project_id=eq.<고정 server project>`, `select=*`, `limit=10000`, `Prefer: count=exact`를 제안한다. 기존 클라이언트의 허용 조회와 같은 범위다. 다른 작품·전체 계정 목록·receipt 테이블·스토리지 목록을 추가하지 않는다.

**기본 상한 제안: 총 HTTP 7회**, 구성은 account 조회 1회·handshake 1회·테이블 GET 5회다. 토큰 발급/갱신 0회, 문서/구조 쓰기 0회, 자동 주기 0회, 재시도·자동 페이지 추가 0회다. POST인 Q2도 HTTP 1회로 차감하며 문서/구조 쓰기 횟수와 혼동하지 않는다. 과거 실행의 사용량을 이 새 분류로 다시 계산하지 않는다.

시간 제안은 사용자와 실행 시각을 확정한 뒤 **전체 벽시계 180초, 요청별 단계 timeout 15초**다. 15초는 현재 httpx 설정과 같은 연결/읽기 등 단계 timeout 기준이며 요청 전체의 절대 제한이라고 보지 않는다. 새 수집기가 전체 180초의 deadline을 별도로 강제해야 한다. 구체 시작 시각·절대 만료·새 실행 식별자는 아직 만들지 않았다. 초과하면 중단하며 연장하거나 다시 시작하지 않는다.

10000은 요청 limit이지 모든 서버 행이 전달된다는 보장이 아니다. count가 없거나 반환 길이와 다르면 잘림/불완전으로 중단한다. 더 많은 페이지가 필요하면 필요한 범위만 따로 보고하고, 기본 7회 안에서 임의 추가하지 않는다.

## 왜 별도 조회 수집기가 필요한가

현재 `IntegratedNetwork.cycle(receive_only=True)`도 `store.materialize()`와 `accept_snapshot()`을 실행해 로컬 상태·TXT·감사 기록을 바꾼다. `network_factory()`는 기존 설치 위치와 AppData 실행 설정/세션에 연결된다. 따라서 **기존 설치 앱의 수신 버튼이나 종료 run을 재사용하는 방법은 이 준비안에 맞지 않는다.**

실제 조회 전에 새 경로의 독립 읽기 수집기를 오프라인에서 구현·검증해야 한다. 이번 요청에서는 구현하지 않았다. 수집기에 필요한 범위는 다음과 같다.

- endpoint/account/project와 위 7개 요청만 고정한다. 본문/구조 commit, receipt 조회, 로그인 갱신은 제공하지 않는다.
- 별도 새 감사 파일에서 HTTP 시도를 전송 전에 예약하고 실패·중단 후 반환하지 않는다. 과거 DB·run·설정에 연결하거나 새 카운터를 이관하지 않는다.
- 실제 서버 답변 원본은 새 격리 결과 폴더에 저장한다. 파싱/검증한 결과도 기존 앱 store나 원고 경로에 적용하지 않는다.
- 반복·redirect·추가 페이지·시간 연장을 차단하고, 명시한 전체 deadline 및 부분 수집 중단을 처리한다.
- 토큰은 화면·로그·ZIP에 넣지 않는다. 현재 세션의 존재·유효성을 이번 준비안 작성에서 읽거나 갱신하지 않았다. 마지막 과거 토큰의 2026-09-13 만료 기록을 현재 로그인 상태로 간주하지 않는다.

향후 유효 세션이 없거나 401 등이 나오면 중단한다. 로그인 갱신이 필요하다는 사실과 필요한 별도 범위를 보고하며 이 7회 계획에 몰래 더하지 않는다. 보유 로그인과 실제 인증 갱신은 별개다.

## 수집 후 오프라인 확인 및 판정 한계

1. raw documents/folders/tree_orders에서 모든 후보 UUID를 종류에 관계없이 대조하고, 새 정렬 UUID와 같은 parent의 정렬 충돌도 확인한다. 활성/삭제 행 모두 비교하고 공유 부모 아래 이름/경로 충돌도 확인한다.
2. 기존 17개 node와 15개 order의 ID·부모·revision/srev·삭제·정렬 순서 및 기존 문서 UTF-8 바이트/끝LF/SHA를 비교한다. 보호 원고 rev9/393바이트, R rev9/srev4/22바이트, E 삭제/rev5/srev6/0바이트와 이전 T/A/B 정렬을 기준으로 **차이를 보고**한다. 달라진 값으로 과거 원본을 덮어쓰지 않는다.
3. documents 원문은 별도 비공개 원본 파일로 보존하고, 전달본에는 우선 metadata와 해시만 넣는다. 보유 특수 metadata도 수집 원본에서 누락하지 않고 일반 원고와 별도로 식별한다. 원고 본문을 채팅에 출력하지 않는다.
4. 부모 그래프·활성 자식/정렬 관계·중복 ID·같은 revision의 다른 본문 등 모순을 확인한다. 불완전하거나 중간 상태로 보이면 추가 수신으로 자동 수리하지 않는다.

**Q3~Q7은 서로 다른 시점의 순차 읽기다.** 한 묶음이 내부적으로 맞아도 원자적 snapshot이나 조회 이후 무변경을 보장하지 않는다. count 일치는 해당 계정에 보이는 해당 테이블 응답의 범위 확인이다. RLS 때문에 보이지 않는 행까지 포함한 전역 완전성·UUID 비존재의 증명은 아니다. ‘없음’ 결과는 지정 계정·작품·조회 시점의 가시 범위에서 발견되지 않았다는 뜻으로 보고한다. 충돌 없는 실제 생성의 보장으로 확대하지 않는다.

기존 `complete=false` 파일을 true로 바꾸지 않는다. 새 산출물에는 테이블별 count 일치·계정 가시 범위·요청 시각 구간·일관성 검사 결과를 따로 기록한다. 아직 생성하지 않은 항목의 revision도 null 그대로다. 원자적/최신 기준이나 생성 직전 정렬 재확인이 필요하면 **이번 읽기 완료 후 별도 범위**로 제안한다. 두 번째 전체 조회도 자동으로 수행하지 않는다.

## 중단 조건과 산출물

subject/작품/계약 불일치, 만료·401/403·429·5xx·연결 실패·timeout, count 누락/잘림, JSON/metadata 오류, 보호 대상 변화, 새 후보 충돌, 그래프/정렬 모순이 드러나면 해당 지점에서 멈춘다. 정상 결과만 다음 순서로 진행한다. 오류가 있으면 이미 받은 부분 결과와 사용한 횟수를 보존해 보고한다. 대체 계정·service-role·다른 작품·새 UUID로 자동 우회하지 않는다.

후속 실제 읽기 산출물은 새 폴더의 원본 응답·각 파일 SHA-256·요청별 예약/완료/실패 기록·표별 count·metadata/order export·기존 기준 대비 차이·가시 범위 후보 충돌 결과·미확인 목록이다. 기존 DB·WAL/SHM·원고·설치물·53건 결과와 iPad 충돌/18·19바이트 원본 2개·종료 run의 사용량/만료는 그대로 보존한다.

이 첫 읽기는 Windows 실제 receipt SELECT/RLS 성공, Windows 실기기 자체 충돌, iPad 중간 snapshot 회복, 새로운 생성/초기 수신을 시험하는 단계가 아니다. 생성·서명·설치·iPad bootstrap·최초 수신·공유 부모 정렬 변경 비용도 여기에 포함하지 않는다.

## 사용자에게 필요한 다음 행동

**지금은 이 준비안을 iPad 측에 전달하고, iPad의 로컬 준비안을 받아 Windows에 보내면 된다.** iPad와 Windows는 계획 정리를 병행할 수 있다. 앱 실행·로그인·설치 버튼 조작은 지금 필요 없다.

전달 문구:

> Windows 최소 조회 준비안입니다. 기본안은 account 확인 1회, handshake 1회, 작품 내 5개 테이블 조회로 총 7회이며 아직 실행 승인이 아닙니다. 순차 조회/RLS 가시 범위의 한계를 유지하고 기존 complete=false·null revision은 바꾸지 않습니다. iPad의 별도 local project·bootstrap adapter·서명 관련 로컬 준비안과 대조해 누락 조건이나 차이만 알려 주세요. 이번에는 계획 검토만 하며 구현·재검사·설치·실제 서버/로그인/관문·hold 변경은 하지 않습니다.

양측 준비안이 모이면 Windows가 필요한 오프라인 수집기 구현 범위와 실제 실행 전 필수 조건을 한 묶음으로 정리한다. 그 구현이 완료되기 전에는 사용자에게 실제 조회 실행을 요청하지 않는다. 실행 가능 산출물·대상·횟수·시간이 모두 구체화된 뒤 실제 동작 승인 단계를 별도로 둔다.
