# Capability 순서 오류 — 양측 확인 결과

**iPad 진단 보고를 확인했고, Windows 통합 후보에도 같은 순서 의존 문제가 재현됐습니다.** S1 완료는 유지하며 S2 receipt 복구 완료로 처리하지 않습니다.

- iPad 보고: 후보 `202609131240` 설치·15:00 연장·진단·정상 종료 완료. 해당 batch의 두 SELECT는 각각 HTTP 200/1행, 실패 필드는 `batch.client_capabilities`입니다. 원인 확인에는 재구성 응답의 전체 바이트 해시 일치를 사용했으며, 재구성 파일을 실제 수신 원문으로 바꿔 부르지 않습니다. 누적 HTTP **38/520**, Auth **6/16**, 쓰기 **1/26**을 이어갑니다.
- Windows 확인: 설치 후보의 동결 소스 `IntegratedNetwork.receipt`는 요청 metadata 전체의 JSON 해시를 비교하므로 capability 배열 순서까지 같아야 합니다. 보존된 S1 요청·응답과 합성 receipt로 원래 순서는 통과, 같은 8개 문자열을 서버 SQL처럼 정렬하면 `RECEIPT_REQUEST_CHANGED`가 발생했습니다. 실제 HTTP/자격 증명 접근 **0회**, 원래 요청 해시 불변입니다. [재현 결과](../_evidence/windows-integrated-editor-execution-20260913/capability-order-reproduction.json). 이는 Windows 로컬 재현이며 실제 Windows SELECT 권한 확인이 아닙니다.

**필요한 공통 수정은 capability 비교 부분입니다.** 양쪽 값이 문자열 배열이고 중복이 없으며 구성원이 정확히 같은지 검사해 순서 차이만 허용합니다. 원래 wire JSON·요청 해시를 다시 정렬하거나 저장하지 않습니다. 다른 metadata·요청/응답 해시·응답 계약 검증은 그대로 유지합니다. 검사 범위는 서버 정렬 receipt 성공, 누락·추가·중복·잘못된 타입 거부, 다른 metadata/해시 변경 거부입니다.

iPad에서는 첫 진단 종료 이력과 누적 **38/6/1**, 기존 batch/operation/두 본문 작업/checkpoint를 보존한 채 새로 승인된 한정 복구 시도를 추가해야 합니다. 성공한 44바이트 첫 쓰기를 새 batch로 POST하지 않으며 45바이트 후속 작업은 별개로 유지합니다. 기존 5 HTTP 진단은 이미 사용했으므로 앞으로의 복구 요청과 혼동하거나 사용량에서 빼지 않습니다.

현재 Windows는 **15:00 연장 적용·앱 종료·자동 꺼짐**, HTTP **174/280**, Auth **23/30**, 쓰기 **19/21** 그대로입니다. iPad 연장 완료는 이번 보고로 확인했습니다. Windows 토큰은 12:37:10에 만료됐으므로 실기기 재개 전 기존 계정 갱신이 필요합니다.

이번 처리는 전달 문서 검토와 Windows 오프라인 원인 재현입니다. 제품 수정·후보 교체·설치·로그인 갱신·추가 서버 조회를 수행하거나 새로 승인하지 않았습니다. 다음 범위는 **양측 비교 수정과 영향 검사 → 필요한 후보 준비 → 원래 batch의 한정 복구 재개**로 정리합니다. 전체 시험이나 완료된 S1을 반복하지 않습니다.
