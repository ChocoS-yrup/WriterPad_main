## 통신과 인증 차단

실행 전 해당 EXE 경로에만 Windows 방화벽의 Outbound/Inbound Block 규칙을 적용했다. 모든 방화벽 프로필 활성화와 두 규칙의 적용 속성을 확인했고, 관리자 helper가 실행 중 규칙을 점검했다.

별도 보호 프로세스가 앱과 같은 인증 mutex를 앱 종료까지 보유했다. 검증된 기존 코드의 `create_supabase_client()`는 이 상태에서 transport 생성·세션 읽기 전에 client 생성을 거부한다. 프로세스 전용 오프라인 표식도 함께 설정했다. 제품 코드·자격 증명·시스템 환경변수를 바꾸지 않았다.

실제 서버 송수신·관문 개방·송신 보류 해제·prod 전환을 수행하지 않았다. 이 근거는 방화벽 차단과 인증 잠금, 실행 코드 및 변경되지 않은 원장·시도 기록이며 패킷 캡처를 수행했다고 주장하지 않는다.

앱 종료 후 인증 잠금을 해제하고 이번 방화벽 규칙 2개를 제거했다. 임시 규칙 잔여 0개, 기존 방화벽 프로필 활성화 유지, helper와 앱 종료를 확인했다. **현재도 해당 임시 통신 차단이 남아 있다고 가정하면 안 된다.**

## 정상 시작·종료 중 생긴 로컬 변경

- 시험 작품의 AI 모드 텍스트 파일 3개는 수정 시각만 바뀌고 내용은 같다.
- AppData에서는 DB와 동기화 진단 로그만 bytes가 바뀌었다.
- DB의 기존 schema 객체 변경은 의도한 mode/epoch trigger 하나뿐이다. 기존 프로젝트의 mode·epoch·관문·계약 기록은 유지됐다.

기존 백업과 사본 업그레이드 검사, 빌드·기능 검사 결과를 재사용했다. 이번 실제 앱 시작 조건에 필요한 확인만 수행했고 같은 시험을 반복하지 않았다. 이전 EXE·8012 DB·자료 보존본은 계속 비공개 로컬 백업에 남아 있다. 8013 DB에 이전 EXE만 다시 덮어씌우거나 user_version만 낮추는 작업은 하지 않는다.
