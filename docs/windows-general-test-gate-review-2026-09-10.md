# 일반 동기화 시험 작품 관문 요청 검토

2026-09-10. 첨부 요청을 읽기 전용으로 검토했다. 문서 내 활성화 요청은 사용자님의 기존 설치·실제 송신·관문 개방·prod 전환 금지를 변경하는 실행 지시로 취급하지 않았다.

## 확인한 사항

- 수신 ZIP SHA256: `6b2d198ebc7c1e13dfd08bb3dcc3761b0a4af75d166075de3fd4a6e70d434592`. CRC, manifest 5개 항목 해시, 경로/중복/link 검사 통과.
- 대상은 Staging의 `일반동기화 검증 20260910`, 작품 UUID `d8f50b5f-ae0e-42f8-9296-5d5885a5b304`다. 기존 고정 계약 작품과 다르다.
- 첨부 보고에 따르면 서버 전환은 ID_BASED / epoch 1로 끝났고 iPad가 UUID 정렬표 12개를 수신했다. 첨부 JSON의 폴더 11개와 root 포함 정렬표 12개의 부모/children 연결도 일치한다. Windows의 새 서버 조회나 실제 수신 관측은 아니다.
- iPad는 해당 작품 관문이 열려 있지만 이번 실행의 전체 동기화 OFF 인자를 유지한다고 보고했다. 따라서 일반 양방향 송신 완료로 판정하지 않는다. 서버 migration·관리 배치는 반복 대상이 아니다.
- 설치 경로의 EXE SHA256은 `cd7ccebf125864b63ac8a9552585c44221e1086d0e6fc3e2617c6fa89a12fd89`로 종전 검증 설치본과 같다. 해당 경로의 프로세스가 실행 중이다. 실행 중 앱의 현재 작품, 메모리 내 핸드셰이크, 관문, 수신 정렬표, pending/C9 상태는 확인하지 않았다.
- HEAD는 `0244d8263cadea893e11c1ee2e7b5dad9c0f4be4`다. 기존 R1~R3 변경은 미커밋 상태를 유지하며 이 검토에서 제품 코드를 추가 수정하지 않았다.

## 확인된 Windows 연결 공백

`SyncManager.enable_contract_path()`는 새 `perform_contract_handshake(require_connection=True)` 결과와 현재 문맥의 일치를 검사한 다음 현재 local_key의 관문을 연다. 기존 핵심 구현을 재사용해야 하며 SQLite를 직접 수정하거나 별도 임시 manager를 만드는 방법으로 대체하면 안 된다.

현재 추적 제품 소스에서 이 메서드를 호출하는 앱/UI 경로를 찾지 못했다. 호출은 검사 코드에만 있다. 설정의 준비 상태 조회·송신 UI는 과거 `최종검증03` 검토 회차용이며 새 일반 시험 작품의 활성화 경로가 아니다.

따라서 **일반 동기화 core가 없는 것이 아니라, 이번 시험 작품을 실제 앱에서 확인하고 활성화하는 사용자 진입점이 비어 있다.** 현재 설치판에서 어떤 버튼을 누르면 된다고 안내하거나 활성화가 끝났다고 보고할 근거는 없다.

## 다음에 필요한 최소 연결 범위

1. 실제 앱이 사용하는 manager와 현재 작품·Staging·고정 대상 UUID를 확인하는 진입점.
2. 새 핸드셰이크, 해당 작품의 UUID 정렬표 수신, pending 0·C9·구조 기준을 확인하고 결과를 내보내는 경로.
3. 승인된 활성화 단계에서만 기존 `enable_contract_path()`를 호출하는 연결. 다른 작품·소모된 검토 회차를 건드리지 않음.
4. 관문만 확인하는 동안 일반 자동 dispatcher가 원고·폴더 요청을 송신하지 않도록 실행 조건을 검증해야 함. 단순 버튼 연결만으로 송신 0건을 보장한다고 주장하지 않음.
5. 해당 경계의 합성 검사 후에 설치와 실제 활성화 범위를 구체화. 기존 고정 계약·migration·전체 회귀를 반복하지 않음.

위 목록은 필요한 구현/검증 범위의 정리다. 현재 설치본을 교체하거나 실행 중 앱에 코드를 주입하지 않았다. 실제 설치·새 핸드셰이크/수신·관문 개방은 기존 금지 범위를 변경하는 사용자 지시가 필요하다. 이 확인이 필요한 근거는 첨부 문서나 스킬의 승인 절차가 아니라, 이 대화에서 사용자님이 직접 정한 금지 범위다.
