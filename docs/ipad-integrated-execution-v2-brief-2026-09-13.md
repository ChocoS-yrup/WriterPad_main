# iPad 전달 — 실행안 v2 변경·남은 확인

후속 상태: 아래 질문 두 항목의 회신을 받아 반영했다. 최신 자료는 [최종 실행안 요약](ipad-integrated-execution-final-brief-2026-09-13.md)이며 같은 회신을 다시 요청하지 않는다. 아래는 이전 전달 이력이다.

검토용이며 설치·실행 승인이 아니다. 상세: `windows-ipad-integrated-execution-plan-v2-2026-09-13.md`. 제품 변경·재검사·ZIP 재전송 요청은 없다.

**반영:** 기존 후보 유지. Windows UI에서만 5개를 생성하고 실제 UUID·정렬·대기 11개를 송신 전 명세로 고정한다. 초안의 고정 시험 UUID는 폐기한다. 메모장에 루트 끝 추가 1회, 기존 형제 상대 순서 보존은 유지한다.

**순서:** Windows 생성/송신 → iPad 수신 복구 → iPad 편집/이름 변경/이동/정렬 → Windows 수신 → iPad E 별도 삭제 후 B 삭제 → Windows 삭제 수신 → 같은 iPad B 복원 → Windows 복원 수신 → Windows 최종 본문 송신/양측 정상 대조 → Windows 먼저 쓰기/iPad 마지막 충돌 → 로컬 종료. 구조 송신 중 상대 자동 수신은 멈춘다. E는 B 복원 뒤에도 삭제 상태를 유지한다.

**장애:** 처음부터 all, 첫 수신/첫 쓰기에서 제시한 4지점 순서 사용. 지점마다 정상 종료·같은 설정 재시작 1회, 총 4회. ‘송수신·복구’로 재개, 별도 연결 준비 없음. 실제 패킷 유실·강제 종료 시험으로 보고하지 않는다.

**숫자 제안:** Windows 200 + iPad 520 = 총 720 HTTP, 공통 T0부터 90분. 자동은 Windows S1/iPad S2만 10초, 빈 자동 최대 4/6주기. iPad 산정 N≤26, C≤18, B=1, L=1, P=0, Auth≤16, 기타 여유≤80 → 451회. 미사용 여유로 작업 범위를 늘리지 않는다. 절대 시작/만료는 최종 승인본에서 한 번 고정한다.

**회신은 아래 두 항목만 필요하다.**

1. iPad 작업별 실제 쓰기 RPC 수와 호출 상한이 표 안에 들어가는가? S2: R 본문 1회, E 임시→빈 본문 2회 저장, A 이름 변경, R·E를 B로 이동, B=[E,R] 정렬 — N≤12/C≤5(첫 쓰기 복구 포함). S3: E 별도 삭제·송신 후 B 삭제·송신 — N≤8/C≤2. S4: B를 T 끝에 복원(R 포함, E 제외) — N≤6/C≤1. 다르면 해당 숫자만 정정한다.
2. 초기 `automatic:false`를 유지하면서 승인된 S2에서만 자동을 켜고 끄는 정확한 설정/버튼 방법, Auth≤16 및 하위 한도 관리 가능 여부. Windows 현재 후보는 전체 HTTP/시간만 하드 차단하고, 쓰기/Auth/빈 주기 수는 계획·기록으로 관리한다. 양측 유형별 하드 차단을 요구한다면 현재 후보로 가능하다고 확인하지 않는다.

**미확인 유지:** iPad 중간 불완전 snapshot 자동 회복은 구현 완료로 간주하지 않는다. Windows의 선택형 장애 주입과 실제 receipt SELECT는 이번 계획에서 검증되지 않으며, iPad 조회 성공으로 양측 권한 확인을 갈음하지 않는다. 마지막 실제 충돌 관찰은 iPad다.
