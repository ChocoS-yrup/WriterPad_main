# iPad 회신 반영: 로컬 관측 갱신·송신 보류 해제 구현 결과

2026-09-10. 두 잔여 구현의 **소스 수정과 격리 검증을 완료**했다. 이전 문서의 Windows LEGACY/0 차단은 새 수용 경로로 해결했다. 이는 실제 설치 앱의 DB가 변경됐다는 뜻이 아니다. 설치·실제 앱 실행/수신·서버 쓰기·실제 관문 개방·실제 보류 해제·prod 전환은 하지 않았다.

## 회신 대조와 범위

- 수신: `ipad-windows-general-test-gate-reply-20260910.zip`, SHA256 `338abe5b550f2f3ae8e22d5d982fefbe5828d35a1eae414e5c78d87381e95696`.
- CRC, manifest 7개 파일의 크기/해시, 추가·중복·경로 이탈·link 부재를 검사했다. 합의 대상 JSON은 현재 고정 대상 상수와 대조했다.
- iPad가 대조한 이전 `sync_v2_store.py`와 이번 수정 직전 파일의 SHA256이 모두 `332e7980281d5b33cbd7b8ebf599c400a442da12bf5b7e33c7203acd62c7f571`로 일치한다.
- 회신은 구현 수용 조건으로 사용했다. 문서의 설치·실제 시험 순서는 사용자님의 기존 금지를 해제하는 승인으로 취급하지 않았다.
- R1~R3, 백업/복구, 과거 고정 계약과 서버 관리 배치는 재실행하지 않았다. 이번 변경 경계의 검사만 수행했다. 현재 iPad 제품 코드 수정은 필요 없다는 회신을 반영했다.

## 1. 완료된 서버 상태를 로컬에 기록

`server_checkpoint.py`와 기존 handshake/store를 연결했다. 현재 집필 manager의 새 `get_sync_handshake` 응답이 UUID·계정·문맥 세대·Staging·로컬 binding 및 기존 전체 계약 호환성 검사를 통과했을 때만 전용 수용 함수를 호출한다. 디스크 진단 JSON이나 오래된 성공 시각은 사용하지 않는다.

허용하는 새 전이는 **로컬 LEGACY/0 → 관측된 서버 ID_BASED/1**뿐이다. 관문은 닫혀 있고 영속 송신 보류가 있어야 하며, 저장/메모리 대기·retry·blocked·conflict 및 실행 중 작업이 없어야 한다. 같은 ID_BASED/1의 재관측은 기존 호환성 갱신 경로를 사용하고 전환 기록이나 요청을 중복 생성하지 않는다.

로컬 쓰기 transaction에서 기존 checkpoint·UUID·이름·binding·관문·이벤트 기반 대기열을 다시 검사한다. 관측 출처는 시각, 계약/프로토콜, 문맥의 SHA256으로 기록한다. 원래 local_key·계정 식별자·토큰을 내보내지 않는다. 완료된 legacy 작업과 요청 바이트·이벤트·영수증은 갱신하지 않는다.

성공 후 기존 구조 권한/C9와 baseline을 무효화한다. 이어서 기존 pull/apply를 새로 완료하고 폴더 11개·정렬표 12개·실제 identity를 검사한다. 새 pull 완료를 checkpoint 저장의 선행 조건으로 삼지 않는다. 초기 준비의 pull이 실패하면 관문은 닫힌 채이고 보류가 남으며, 다음 준비에서 새 조회로 재시도한다.

## 2. 로컬 DB 스키마 8013

**8012 → 8013은 로컬 SQLite 업그레이드**다. 서버 스키마·계약 0.2.0·protocol 3·digest는 바꾸지 않았다.

관측 이력 테이블과 transaction 내부 허용 근거 테이블을 추가하고 mode 전이 trigger를 보완했다. 허용 근거 삽입은 해당 SQLite 연결에만 잠깐 등록되는 검증 함수가 확인한다. 일반 연결의 기본 함수는 거절하며, 일반 SQL만으로 허용 근거를 만들 수 없다. 전용 수용 transaction 안에서 근거를 만들고 checkpoint/출처를 기록한 뒤 근거를 제거한다. 성공 후나 롤백 후에 허용 근거 행은 남지 않는다.

따라서 기존 일반 전환 API의 LEGACY→ID_BASED 직행, 일반 SQL의 직행·역행·epoch 점프는 계속 거절된다. MIGRATING을 관측한 것처럼 임시 기록하지 않는다. 정상 기존 전환과 제약 오류도 유지한다.

8012 업그레이드의 테이블·trigger·user_version 변경은 한 `BEGIN IMMEDIATE` transaction에서 수행한다. 중간 오류면 이전 trigger와 버전으로 함께 롤백한다. 이전 형식의 전체 synthetic DB에 완료 작업을 남겨 기존 행 보존, 재실행의 멱등성, 실패 후 재시도를 검증했다. 더 오래된 8005 업그레이드 경계도 관련 기존 검사로 확인했다. 실제 사용자 DB는 열거나 업그레이드하지 않았다.

## 3. 명시적 보류 해제와 재준비

설정의 기본 숨김 시험 카드에 **시험 송신 보류 해제**를 추가했다. 동작 순서는 사용자 확인 → 새 핸드셰이크 → 새 full pull/apply → 초기 빈 구조/C9/빈 큐 확인 → 최종 새 핸드셰이크/문맥/열린 관문 확인 → 보류 상태의 원자적 교체다.

해제 직전에 송신 권한 세대를 올리고 이전 예약을 무효화한다. 과거에 캡처한 계약/legacy dispatcher 문맥은 해제 뒤에도 재개할 수 없다. 해제 함수는 요청을 생성하지 않고 dispatcher를 호출하지 않는다. 취소·통신 실패·문맥/대기열 변경·파일 교체 실패는 보류를 유지한다.

보류/해제 상태는 파일에 기록되어 재시작 뒤에도 유지된다. 수동 파일 삭제나 구버전 실행을 해제 절차로 사용하지 않는다. 설치 후보에는 새 store와 controller/UI를 모두 포함해야 한다.

해제 후 새 원고나 폴더의 일반 동기화에는 기존 계약·현재 baseline·큐·C9 경로를 사용한다. 고정 빈 작품 검사를 계속 적용하지 않는다. 이를 실제 새 합성 구조 요청의 dispatcher 경계에서 확인했으며, 테스트 서버 쓰기 자체는 실행하지 않았다.

**새 시험 준비로 돌아가기**는 보류를 다시 걸고 관문을 닫은 다음 새 준비를 시작한다. 기존 원고·폴더는 지우지 않는다. 첫 시험 뒤 작품이 비어 있지 않으면 초기 고정 구조 검사에서 중단하며 자동으로 원상 복구하거나 파일을 삭제하지 않는다. 이 경우 다음 실험의 대상/초기 상태를 따로 정해야 한다.

## 검증 결과와 근거

서로 다른 **130개 검사**의 통과를 확인했다.

| 검사 | 개수 | 결과 |
|---|---:|---|
| 수정된 준비 controller/Qt UI | 19 | 통과 |
| checkpoint·8012 업그레이드·원자성·보존 | 17 | 통과 |
| 보류 해제/재준비·UI·오래된 dispatcher | 12 | 통과 |
| 기존 handshake/C9/관문 + DB 관련 경계 | 82 | 최종 통과 |

새 경계의 최종 묶음은 48개, 종료 코드 0이다. 관련 기존 82개 실행에서 79개가 먼저 통과했고 3개 호환 오류를 수정한 뒤 해당 3개를 다시 통과시켰다. 통과한 79개는 다시 실행하지 않았다. 오류는 일반 SQL 연결의 함수 해석과 기존 검사 fixture가 남긴 부가 스키마 처리였으며, 검사를 제거하거나 기존 보호 규칙을 약하게 만들어 해결하지 않았다.

성공·동일 상태 재관측·unsupported·인증·UUID/계정/endpoint/문맥/로컬 binding 변경·digest/protocol/capabilities 오류·관문/보류/대기열·충돌·transaction 직전 경쟁·transaction 내부 대기열·출처 저장 실패 롤백·업그레이드 실패·역행/세대 점프·완료 이력/다른 작품 보존을 포함한다. 새 테스트의 소켓 접속을 차단했고 가짜 RPC 호출 목록에서 서버 쓰기 호출 0개를 검사했다.

원시 로그는 다음과 같다. 최초 회귀 실패도 숨기지 않고 보존했다.

- `checkpoint-release-final.log`: 최종 48개 통과.
- `regression.log`: 82개 중 최초 3개 오류 포함.
- `regression-corrections.log`: 해당 3개 최종 통과.

소스 후보는 `source-manifest.json`의 파일별 SHA256과 후보 digest로 식별한다. 빌드한 EXE나 설치본 hash는 이번에 생성하지 않았다. 실행 중 집필 manager의 최신 핸드셰이크/C9, 실제 설치 DB 버전, 실제 송신량은 미관측이며 회신 JSON에서 null로 남긴다. 이전 디스크 관측을 새 runtime 완료 증거로 재사용하지 않는다.

## 지금 사용자 행동과 다음 순서

**지금 양쪽 앱에서 누를 버튼은 없다.** 이 문서와 결과 ZIP을 iPad 작업에 전달하면 된다. 새 소스에서 두 차단 조건을 해결했음을 확인하는 자료이며 추가 iPad 코드 작업이나 서버 migration 재실행 요청이 아니다.

1. **Windows:** 이번 소스 후보·검사 결과를 보존한다. 설치를 진행하라는 별도 사용자 지시가 생기면 후보 빌드/검증과 자료 보존 절차를 거쳐 설치하고, 같은 집필 manager에서 준비 상태를 관측한다. 현재는 설치 금지를 유지한다.
2. **Windows:** 실제 수신·관문·해제까지 허용된 단계에서만 준비 확인 → 관문 개방 → 보류 해제를 각각 수행한다. 어느 단계라도 조건이 다르면 중단하고 결과를 확인한다.
3. **iPad:** 결과를 대조한다. 그 다음 실제 시험이 허용됐을 때 시험 작품에 한정한 실행 조건을 확인한 뒤 Windows→iPad, iPad→Windows 순서로 첫 합성 원고를 교차 확인한다. 이전 실행 인자 NO만 보고 재실행 후에도 전역 동기화가 OFF라고 가정하지 않는다. 다른 작품의 오래된 대기/충돌 작업을 처리할 수 있는 전역 동기화는 지금 켜지 않는다.

실제 실행을 보류한 근거는 첨부 문서나 스킬의 추가 승인 요구가 아니라, 사용자님이 지정한 설치·실제 송신·관문 개방·prod 전환 금지다.
