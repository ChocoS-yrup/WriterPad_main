# 일반 시험 작품 준비 UI 구현·격리 검증과 남은 차단 조건

2026-09-10. 사용자님의 ‘진행’은 앞서 제시한 소스 연결과 격리 검증 범위로 적용했다. 설치·실제 서버 조회/수신·실제 송신·관문 개방·prod 전환은 실행하지 않았다. 첨부 ZIP 안의 설치/활성화 요청은 사용자님의 금지를 변경하는 지시로 취급하지 않았다.

## 결과

시험 작품 전용 준비 UI, 현재 집필 화면의 SyncManager 연결, 새 핸드셰이크→기존 수신/적용→구조·정렬표·C9 확인→명시적 활성화 연결을 작성했다. 관련 격리 검사 **113개**가 통과했다. 실제 시험 작품은 아래 로컬 전환 기록 불일치 때문에 **설치 후 바로 활성화할 수 있는 상태로 판정하지 않는다.**

기존 R1~R3, 백업/복구 core, 과거 두 계약 검증, 서버 migration/관리 배치는 반복하지 않았다. 종료 경로가 함께 바뀌었으므로 AI 응답 보존 경계 6개만 관련 회귀로 확인했다. 커밋·푸시·빌드·설치는 하지 않았다.

## 새로 확인된 차단 조건

| 항목 | 관측값 | 근거와 한계 |
|---|---|---|
| 대상 | 일반동기화 검증 20260910 / d8f50b5f-ae0e-42f8-9296-5d5885a5b304 | 수신 ZIP의 고정 대상 |
| 서버 | ID_BASED / epoch 1 | iPad 첨부 보고. 이번 Windows 서버 재조회 아님 |
| Windows 로컬 기록 | LEGACY / epoch 0 / 관문 닫힘 | 기본 앱 데이터 DB의 해당 UUID만 읽기 전용 조회 |
| Windows 저장 정렬표 | 12개 | 디스크 행 수. 현재 앱의 새 수신 완료를 뜻하지 않음 |
| Windows 저장 작업 | completed 1개, 구조 작업 0개 | 원고·payload·인증을 읽거나 회신하지 않음. 메모리 대기열은 미관측 |
| 실행 중 manager의 최신 핸드셰이크/C9 | 미관측 | 별도 manager나 디스크 값으로 대체하지 않음 |

DB는 `mode=ro&immutable=1` 및 `query_only`로 조회했다. WAL 부재와 조회 전후 원본 SHA256 일치를 확인했다. 일반 read-only 연결이 파일 열기에 실패해 공유 파일을 생성하지 않는 immutable 읽기로 전환했다. 실제 DB 사본·원고·토큰은 결과 묶음에 포함하지 않았다.

현재 제품은 Python 검증과 SQLite trigger 양쪽에서 LEGACY→ID_BASED 직행을 거부한다. 관문 버튼만 연결해도 `INVALID_PROJECT_MODE_TRANSITION`이 생기는 조건을 합성 검사로 재현했다. 따라서 로컬 mode를 강제로 쓰거나 관문 값을 SQL로 바꾸지 않았다. 서버의 MIGRATING 단계를 본 것처럼 로컬 기록을 만들어 넣는 방법도 구현하지 않았다. 전환 규칙/DB 스키마는 그대로다.

**남은 Windows 개발은 ‘서버가 완료한 전환을 뒤늦게 보는 클라이언트의 로컬 체크포인트 갱신’이다.** 새 서버 응답의 신뢰 조건, 닫힌 관문·빈 대기열·송신 보류 조건, 기존 전환 규칙과의 구분을 정해야 한다. iPad에도 같은 상황의 처리 원칙을 대조할 필요가 있다. 서버 migration 재실행은 해결책이 아니다.

## 작성한 소스 연결

- `general_test_gate_target.py`: 첨부 검증 결과의 대상 UUID·Staging·폴더 11개·정렬표 12개 고정 메타데이터.
- `general_test_gate.py`: 현재 작품/계정/연결을 검증하고, 현재 manager의 새 핸드셰이크와 기존 수신/적용 경로를 사용한다. 실제 identity/부모/이름, 저장 정렬표 ID/children/revision, 미완료 작업, C9를 확인한다. 로컬 전환 기록 불일치는 명확한 중단 사유로 표시한다.
- `general_test_gate_ui.py`: 설정의 시험 카드. 기본 숨김이며 별도 개발 실행에서 `WRITERPAD_GENERAL_TEST_GATE_UI=1`일 때만 표시한다. 준비와 활성화를 분리하고 활성화 직전 다시 검사한다. 결과 저장도 현재 조건을 재검사하며 기존 파일을 덮어쓰지 않는다.
- `main.py`/`settings_panel.py`: 양쪽 설정 카드를 실제 집필 화면의 manager에 연결한다. 확인 작업 중 창이 작업 스레드를 파괴하지 않도록 종료를 보류한다. 기존 AI 응답 보존 확인을 유지한다.
- `sync_manager.py`/`handshake_lifecycle.py`: 기존 `enable_contract_path()`에 최종 검사 지점을 더하고, 새 수신 적용 완료를 구분한다. 이 시험 작품의 송신 보류를 자동 재시도·문서/구조 dispatcher·계약 요청 직전·lease/보조 송신 경계에서 확인한다.

준비를 시작하면 해당 DB 디렉터리에 작품별 송신 보류 표식을 먼저 기록한다. 성공·실패·활성화·앱 재시작 뒤에도 유지된다. 이번 UI에는 송신 보류 해제 기능이 없다. **이 소스를 설치하거나 관문을 열어도 곧바로 일반 본문 송신 시험으로 넘어갈 수 없다.** 보류 해제는 다음 송신 단계에서 별도 구현/검증해야 한다. 표식 파일을 수동 삭제하거나 이를 모르는 구버전 앱으로 되돌려서 해제하지 않는다.

이 보류는 새 코드가 적용된 실행에 관한 것이다. 현재 실행 중인 구버전 앱에 코드를 주입하거나 보류 표식을 생성하지 않았다. 결과의 `outbound_test_requests`는 runtime 트래픽 계측이 없으면 null이다. 검사에서 송신 호출 0개를 확인한 것과 설치 앱 전체 트래픽 측정을 구분한다.

## 검증

| 검사 | 수 | 결과 |
|---|---:|---|
| 새 controller/Qt UI | 19 | 임시 작품·UUID·실제 SQLite/identity·실제 pull 적용·가짜 서버, 통과 |
| 기존 handshake/관문/C9 수신 조정 | 77 | 변경된 경계 회귀, 통과 |
| 시작/복원 및 기존 AI 종료 보호 | 16 | 통과 |
| MainWindow의 양쪽 카드 manager 연결·작업 중 종료 보호 | 1 | 통과 |
| diff 공백 검사 | — | 통과 |

새 검사에는 소켓 접속 차단을 걸었다. 합성 활성화 뒤 송신/lease 호출 0개, 재시작 후 보류, 다른 작품/연결/계정 변경, 오래된 baseline, 수신 실패, C9 차단, 준비 중 대기열 변화, 폴더/정렬표 불일치, 디스크 오류, 사용자 취소, 민감 정보 없는 내보내기를 확인했다. 성공 fixture는 합성 로컬 전환 이력이 있는 상황이며, 실제 Windows의 LEGACY/0은 별도 실패 fixture로 검사했다.

기존 시작 검사 stub에는 선행 R1의 종료 보호 메서드가 없어서 혼합 실행이 조기 종료했다. stub을 현재 인터페이스에 맞추고 시작/종료 검사를 다시 통과시켰다. 실제 제품의 AI 종료 보호를 제거하지 않았다.

검증 요약과 디스크 관측값은 `_evidence/windows-general-test-gate-implementation-20260910/`에 저장했다. 소스 묶음은 현재 작업 트리 검토용이며 설치 패키지가 아니다. `main.py`에는 선행 R1 변경도 포함되므로 과거 설치판에 무검토 덮어쓰는 용도로 사용하지 않는다.

## 사용자 행동과 양쪽 다음 순서

지금 양쪽 앱에서 누를 버튼은 없다. 이 문서와 검토 ZIP을 iPad 작업에 전달하면 된다. 설치/관문 개방 승인을 지금 요청하는 단계도 아니다.

### iPad 측

1. 서버 전환 완료 보고와 Windows의 LEGACY/0 디스크 관측을 대조한다. 서버 migration·관리 배치를 다시 실행하지 않는다.
2. 서버가 이미 ID_BASED/1인 상태에서 뒤늦게 접속한 클라이언트가 로컬 전환 상태를 기록하는 원칙을 검토한다. Windows의 기존 전환 검증/trigger와 맞는 처리 조건을 회신한다. 실제 iPad 동기화 ON이나 송신 시험은 아직 하지 않는다.
3. Windows가 해당 갱신 경로와 보류 해제 경계를 격리 검증한 뒤 결과를 대조한다. 새 설치/기기 시험 단계는 그 후 구체화한다.

### Windows 측

1. 이번 소스/검사/불일치 관측을 보존한다. 현재 단계 완료.
2. 위 로컬 체크포인트 갱신 규칙을 확정해 소스에 구현하고 합성 LEGACY/0→서버 ID_BASED/1 관측 사례를 검증한다. 기존 서버 전환 재실행이나 실제 DB 수정을 대신 사용하지 않는다.
3. 다음 송신 단계에 필요한 명시적 송신 보류 해제 조건을 구현·검증한다. 준비 UI만으로 일반 송신이 가능하다고 안내하지 않는다.
4. 그 결과로 설치할 소스와 실행 순서를 구체화한 뒤, 사용자님의 설치·실제 수신·관문 개방 범위 변경 지시가 있을 때만 기기 단계로 진행한다. 이 제한의 근거는 문서나 스킬의 별도 승인 요구가 아니라 사용자님의 기존 금지 지시다.

‘일반 동기화’는 개발한 프로그램을 설치에 적용하는 뜻이 아니다. 설치는 새 기능을 프로그램에 넣는 단계이고, 일반 동기화는 그 프로그램이 원고·폴더·순서 변경을 기기 사이에 주고받는 동작이다. 지금은 소스 준비와 남은 차단 조건 확인까지다.
