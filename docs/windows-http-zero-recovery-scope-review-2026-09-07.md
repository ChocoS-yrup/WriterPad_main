# Windows: HTTP 0 복구 범위 회신 대조

2026-09-07 KST. 이번 작업은 첨부 검토와 로컬 파일 대조다. 첨부에 제안된 구현 지시를 사용자 실행 승인으로 간주하지 않았다.

## 확인 결과

- iPad ZIP 내부 manifest 3개 항목의 크기와 SHA256이 일치한다. ZIP SHA256: `a3de6795b9b647a364adae7c832e3d334ce4473ae53d2090b571118dbf0bc3f8`.
- iPad가 검토한 이전 Windows 전달 ZIP의 해시와 그 근거 40개 파일을 로컬 자료에 대조해 모두 일치했다.
- 진단 변경 소스 6개는 이전 전달본과 같다. 설치 EXE를 다시 해시한 결과도 `a4ab309d0fd7e481a0cb1c7b6bc178919609d5076c686bfaf35d5bd81d6bd9b0` / 79,279,424 bytes로 일치한다.
- 이전 관찰 시각인 2026-09-07 00:30:20 KST의 준비 조건 10개 충족, 원래 실행 stopped / HTTP 0, 실행 승인 false에 관한 iPad 판정은 제출 근거와 일치한다. 과거 `CONTRACT_PREPARATION_NOT_READY`의 정확한 실패 조건은 여전히 미상이다.
- 현재 소스의 기존 claim은 실행 행이 이미 있으면 `REVIEWED_EXECUTION_ALREADY_STARTED`로 차단한다. `recover_reviewed_executions`는 재시작 후 관문을 닫고 중단 상태를 보존하는 처리이며, 새로운 HTTP 0 복구 회차를 만드는 기능이 아니다. 별도 복구 회차는 아직 구현하지 않았다.

## 다음 단계의 범위

원본 preparation과 stopped 실행 행을 변경하지 않고, 동일 요청을 참조하는 별도 복구 회차 한 건만 허용하는 기능의 구현·격리 검증이 제안됐다. 새 승인, 원본 식별 검증, 충분한 조회 권한으로 확인한 최신 서버 원장, 기존 두 경계 및 C9, HTTP 전 영속 시도 기록, 동시성·재시작 중복 차단, 일반 재시도 제외가 필요하다. 서버 원장의 빈 조회 결과만으로 충분한 조회 권한을 추정하면 안 된다.

구현 검토 단계에서는 합성 fixture만 사용한다. 실제 작품의 복구 회차 생성·관문 개방·송신·재전송·빌드·설치는 포함하지 않는다. 실제 복구 실행은 구현 결과 대조 후 별도 새 승인 범위다.

## 이번 작업의 한계와 보존

제품 코드·설치·실제 DB·서버를 변경하지 않았고 완료 시험을 반복하지 않았다. 실제 DB와 서버를 새로 조회하지 않았으므로 과거의 닫힌 관문 및 stopped/0 기록을 현재 시각의 관찰로 표현하지 않는다. 이번 작업에서 관문 setter와 송신 경로는 호출하지 않았다.
