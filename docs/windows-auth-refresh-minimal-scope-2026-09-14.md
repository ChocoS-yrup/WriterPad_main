# 기존 계정 로그인 갱신 1회 — 최소 범위와 GUI 안내

2026-09-14. 사용자 요청은 범위·절차 정리만이다. 소스와 과거 기록만 읽었다. 앱/GUI 실행, 실제 인증 갱신, credential store 접근, 서버 요청, 설치·관문 변경, 검사는 하지 않았다.

**최소 방안은 기존 계정의 저장된 refresh token으로 인증 요청 1회만 보내는 별도 호출이다. 현재 GUI에서 로그인 버튼을 누르는 방식은 이 범위를 보장하지 않는다.** 새 GUI를 만드는 것은 최소 방안에 포함하지 않는다. 갱신 전용 호출부는 아직 준비되지 않았으므로 이번 문서는 실행 승인이 아니다.

**1. 기존 화면·스크립트에서 확인한 사실**

| 경로 | 확인 결과 | 이번 범위에 대한 판단 |
| --- | --- | --- |

| --- | --- |
| 실행 사용자 | CHOCOSYRUP\xiix1, SID S-1-5-21-2542480074-635446901-4096835241-1001, 빈 profile |
| 대상 | https://mhpnszcorfzrvhyondxr.supabase.co |
| 기대 account | e487c6ea-1c2b-4a90-821e-91e8547106de |

| 추가 HTTP | account GET, handshake, Q1~Q7 조회, receipt, 문서/구조 요청 모두 0회 |

이 요청은 refresh token을 읽고 새 세션을 저장하므로, 앞서 승인된 access 전용 조회와 권한이 다르다. **03:30~06:00의 독립 조회 1회 승인에 이 인증 갱신을 추가하지 않는다.** 실패한 조회 run `64896904-d883-4549-8d9e-3c53cadb6cb8`과 과거 종료 통합 run 모두 그대로 둔다.

사용자 계정/profile·설정 pin·보존 pin을 확인하고 동일 credential lease를 획득해야 한다. lease를 다른 앱이 보유하면 그 자리에서 중단한다. 앱을 강제로 닫거나 잠금을 지우지 않는다. 이전 실행과 연결되지 않은 새 인증 ID와 신규 감사 폴더에서 한 번만 진행한다.

기존 access의 sub/issuer는 로컬 일치 확인용이며 서버 인증 성공의 증거로 확대하지 않는다. 만료된 access라는 이유만으로 refresh 시도까지 자동 금지하지는 않되, 대상 계정을 구별할 수 없거나 저장된 refresh가 없으면 요청 전에 중단한다. 이번에 실제 저장 항목 존재를 읽어 확인한 것은 아니다.

**3. 응답·세션 저장 조건과 실패 처리**

응답 200과 유효한 JSON, 기대 account와 일치하는 user.id 및 새 access의 sub/issuer, 새 access/refresh의 형태와 충분한 만료 시간을 확인한 뒤 저장한다. 이후 별도의 `/user` 요청으로 확인하는 동작은 이 1회 범위에 넣지 않는다. 새 token의 실제 원문·응답 body 전체는 로그·파일·ZIP·채팅에 남기지 않는다. 응답의 계정 ID, 유효기간, 검증·저장 결과와 비밀정보 없는 상태만 기록한다.

저장 직전 기존 쌍이 다른 프로세스에 의해 바뀌지 않았는지 확인하고, 저장 후 새 쌍이 읽히는지 로컬에서 확인한다. Windows의 두 credential 항목 저장은 한 번의 원자적 교체라고 가정할 수 없다. 갱신 요청 성공 뒤 저장 실패·일부 저장·검증 실패가 나면 **불확실한 세션 상태**로 중단하고 자동으로 과거 토큰을 복원하거나 갱신 요청을 반복하지 않는다. 서버에서 refresh가 회전했을 수 있기 때문이다. 이 경계는 후속 호출부 구현·오프라인 검사에서 다뤄야 한다.

HTTP 거부·timeout·응답 유실·계정 불일치·사용자 취소에도 추가 요청은 하지 않는다. refresh 거부를 이메일/비밀번호 로그인으로 자동 전환하지 않는다. 그 경우에만 별도의 수동 재로그인 범위와 안전한 입력 화면을 준비해야 한다. 비밀번호나 토큰을 채팅으로 보내도록 요청하지 않는다.

기존 원고/DB/WAL/SHM/설치물/관문/hold, iPad 원본 2개와 모든 종료 실행의 사용량·만료는 그대로 보존한다. 새 인증 감사에 이전 실행의 사용량을 이관하지 않는다. 30초 deadline은 HTTP 구간 제한이며 동기 credential 저장이 OS에서 정확히 그 시각에 강제 중단된다는 뜻은 아니다.

**4. GUI 절차 — 현재 누를 로그인 버튼은 없음**

현재 설치된 통합 편집 화면에는 이 작업용 갱신 버튼이 없고 일반 로그인 버튼은 추가 동기화를 시작한다. 따라서 **지금 사용자가 앱을 열거나 이메일·비밀번호를 입력할 단계가 아니다.** GUI 화면을 실제로 열어 확인하거나 자동 조작하지 않았다. 이 안내는 확인한 소스 기준이다.

최소 방안을 선택하면 GUI 조작 없이 다음 순서로 진행할 수 있다.

1. Windows가 독립 인증 호출부를 오프라인으로 준비한다. 사용자 작업은 후속 구현 지시이며 앱을 조작할 필요가 없다.
2. 구현과 신규 영향 검사 후, 인증 요청 1회·세션 쌍 읽기/저장·결과 기록의 구체적 승인안을 사용자에게 보여 준다.
3. 사용자가 그 범위를 한 번 승인하면 xiix1 문맥에서 한 번 실행한다. 요청 단계마다 다시 묻지 않는다. 이 단계까지 현재 승인된 것은 아니다.
4. 성공이면 “갱신 완료 / 신규 인증 HTTP 1회 / 동일 계정 / 로컬 저장 확인 / 만료 시각”만 짧게 보고한다. 실패면 정지 이유와 후속 조치를 제시한다.
5. 성공하더라도 독립 조회는 자동 실행하지 않는다. 이미 종료된 조회 run을 재사용하지 않고 새 조회 1회 범위를 별도로 정한다. iPad는 그 조회 결과가 나올 때까지 대기한다.

사용자가 반드시 GUI에서 갱신을 시작하길 원한다면 갱신 전용 작은 창이 별도로 필요하다. 현재 존재하는 화면처럼 버튼 이름·클릭 순서를 만들어 안내하지 않는다. 추가 창은 별도 구현 선택 사항이며 최소 방안에는 포함하지 않았다.
