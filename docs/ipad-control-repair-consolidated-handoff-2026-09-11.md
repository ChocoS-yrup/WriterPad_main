# iPad 전달용 통합 인계 — UUID 교정 완료·해시 보완 종결

이 문서는 2026-09-11 Windows 실제 교정 결과와 iPad 해시 보완 회신을 합친 최신 안내다. 첨부한 이전 원본 ZIP은 이력 보존용이다. 원본 ZIP 안의 “해시 보완 요청/확인 대기” 문구는 이번 확인으로 종결됐으며, 다시 요청할 필요가 없다.

## 1. 완료된 사항 — 반복하지 않음

**서버와 Windows 실제 UUID 교정 완료.** 사용자 `교정 승인`에 따라 지정 Staging 시험 작품만 교정했고 별도 읽기 및 장부 대조로 결과를 확인했다.

| 항목 | 확정 기준 |
|---|---|
| 작품 | 본문수신검증 20260911 |
| project UUID | `9a78c51c-7de9-43a8-be54-d25a22d08a28` |
| Staging | `https://mhpnszcorfzrvhyondxr.supabase.co` |
| 내부 문서 경로 | `__antigravity__/tree-order.json` |
| 올바른 UUID | `ef6e1de1-a3d0-5959-96be-58f87a683cc0` |
| 제거된 잘못된 UUID | `6df5660a-c1ae-492f-bb1d-26b582508074` |
| 서버 내부 문서 | 올바른 UUID의 live 1행, revision 1, 385 bytes |
| 잘못된 UUID 서버 문서/버전 | 각각 0행, tombstone 없음 |
| 일반 원고 | `메인/원고/1권/1화.txt`, UUID `502cdbe7-814c-42f8-8ed4-81c40cd94902`, revision 1, 93 bytes |
| 폴더 | 11개, 기존 UUID·부모·이름·revision 1 보존 |
| UUID tree_orders | 0행 |

서버 documents/document_versions의 document_id 두 필드와 Windows sync_documents/완료 sync_operations의 document_id 두 필드만 변경됐다. 원고·정렬 content·프로젝트/폴더 UUID·version_id·operation_id·작성 시각·완료 상태는 보존했다. 서버의 다른 13개 public 테이블 지문이 같고, Windows의 30개 테이블은 지정 두 필드 이외의 행/스키마가 같다. integrity 정상, FK 위반 0이며 원래 보호 트리거·송신 잠금·관문 설정도 보존됐다. 설치나 일반 원고 송신을 수행하지 않았다.

**시험 요약 해시 보완도 종결.** `xcresult_summary_sha256`가 비공개 원시 요약 해시를 가리켰지만 공유용 축약 파일이라는 구분이 빠져 있었다.

| 파일 | 크기 | SHA-256 |
|---|---:|---|
| 비공개 원시 요약 | 996 bytes | `fbc6a3a25b1f07e8a975cab1e4817c2db11a9a74998fefb15cd95b75160b36f8` |
| 공유용 xcresult-summary.json | 187 bytes | `4ececc09d81115712823139c6525d54e5be489fd0f00e8e6ca72bef8be29855f` |

Windows는 공유 파일이 이전 회신과 바이트 단위로 같고, 별도 정정본의 변경이 해시 참조/설명 필드에 한정되며 기존 시험 결과·소스 해시는 그대로임을 확인했다. 원시 996바이트 파일은 비공개이므로 원시→공유 변환 재현은 iPad 측의 보존 자료 검증 보고로 확인했다. 이를 Windows에서 직접 재현했다고 보고하지 않는다. **시험 2개 통과/실패 0 결과는 유지되며 추가 빌드·시험·해시 확인 회신은 필요 없다.**

Windows 교정 복사본 검증 8건, FK 모델 검증 5건, 이미 완료된 초기 가져오기/오프라인 바인더 관찰도 다시 수행하지 않는다.

## 2. iPad에서 남은 실행 — 같은 journal로 한 번 재개

**이번 통합 전달 요청과 이전 Windows 교정 승인은 iPad 실제 재개 승인이 아니다.** iPad 작업은 아래 준비→1회 재개→오프라인 관찰→사후 보존을 하나의 구체적 범위로 사용자에게 안내하고 한 번 승인받는다. 필요한 기기 상태 확인 외에 별도의 Windows 사전 검토 왕복을 추가하지 않는다.

1. **준비:** 이 ZIP manifest와 `target-baseline.json`의 교정 기준을 확인한다. iPad의 미저장 자료 유무, 종료·오프라인·USB/관찰 준비, 기존 후보·서명 유효성·정책·동일 계정을 확인한다. 기기 작업과 백업은 그 실행 범위의 승인 후 수행한다. 보존된 서명 만료 기록은 2026-09-12 18:19:25 KST이며 실행 전 유효성을 확인한다. 만료/신뢰 오류가 있으면 자동 재설치·재서명하지 않는다.
2. **같은 수신 기록 유지:** `본문수신검증 20260911`의 동일 project UUID·로컬 이름·journal transaction·owner를 유지한다. 새 작품 생성, UUID 재발급, 수동 binding 재부착, 기존 journal/owner 삭제를 하지 않는다. 앱 실행은 기존 후보로 진행하고 자동 마지막 작품 열기를 피한다. 예상 밖 프로세스 상태라면 반복 실행/종료하지 않는다.
3. **재개 한 번:** 송신 잠금과 동일 Staging/계정을 확인하고 수신 준비를 한다. 대상 행이 같은 UUID의 중단 상태인지 확인한 뒤 가져오기 재개를 한 번만 누른다. 재개 전 상태가 기준과 다르거나 오류가 나오면 재시도하지 않고 보존한다.
4. **성공 후 사용자 관찰:** Wi-Fi·셀룰러를 끈 뒤 아래 3줄을 편집 없이 확인한다. 원고 저장/편집이나 동기화 버튼을 추가로 누르지 않는다.

```text
본문 수신 검증 20260911
이 문서는 동기화 시험용 합성 원고입니다.
끝.
```

5. **종료 후 사후 검증:** 앱을 완전히 종료하고 오프라인을 확인한 뒤 새 보존본에서 journal 0, 공개 작품/binding 각 1, 올바른 내부 baseline 1, 대상 미완료 큐 0, 일반 원고와 폴더 11개 보존을 확인한다. 본문 93 bytes/SHA `cdfcc92e4b06906d9c54e11b4ad263cf913105fdff7669ac5b69b1f42bb7f96d`, 정렬 385 bytes/SHA `1cfe9438a3ff000c3af3b5593f973554b2966e9fd8c29e704e73143fda27b5be`, revision 1이 기준이다. 기존 다른 작품·큐·설정·송신 잠금도 보존돼야 한다.

## 3. 기존 오류 marker는 그대로 보존

예상 잔존 파일:
`Documents/본문수신검증 20260911/집필모드/.writerpad-sync-merge-6df5660a-c1ae-492f-bb1d-26b582508074.json`

812 bytes, SHA `f0e332c548a99431ce1f2f00a4037c73b30c83610bd3c4266a988574b96a1ceb`가 이전 보존 기준이다. 합성 시험상 정상 재개 후에도 이 파일은 남으며 성공을 막지 않는다. 정리를 재개의 선행 조건으로 만들거나 이번 범위에서 삭제하지 않는다. 다른 marker나 journal/owner도 건드리지 않는다.

## 4. 사용자에게 안내할 행동과 최종 회신

- 지금: 통합 ZIP을 iPad 작업에 전달하고 앱은 종료·오프라인 상태로 유지한다. Windows에서 더 누를 버튼은 없다.
- iPad 작업의 실행 범위 안내 후: 위 한 번의 재개와 관찰·사후 보존 범위를 승인한다.
- 실행 중: 요청받은 기기 준비, 대상 재개 1회, 본문 3줄 확인, 완전 종료만 순서대로 진행한다.
- 결과 회신: 성공 여부와 오류 원문, 재개 횟수, 같은 journal/project/owner 유지, 본문/정렬/폴더/큐 검증, 기존 marker 잔존, 종료·오프라인 상태를 하나의 ZIP으로 정리한다. 추가 회신에는 계정/기기 식별자·토큰·원시 DB·프로필을 넣지 않는다.

이 단계에서도 신규 설치·재서명·원고 송신·송신 관문 개방·전역 동기화 활성화·prod 전환은 포함하지 않는다. 실제 iPad 재개 성공은 아직 확인하지 않았으며, 앱 전체 완성과도 구분한다.
