## 최신 사용자 결정

“일단 staging 상태에서 아이패드와 윈도우측 개발이 모두 완료되고나면 서버이전하자.”

서울 prod 전환은 보류한다. 현재 작업 환경은 Staging으로 유지하고, 양쪽 앱에서 합의한 개발 범위와 필요한 검증을 마친 뒤 서버 이전을 다시 진행한다. Staging 비활성화도 그때까지 보류한다. prod는 사용자가 재활성화한 상태이며 이번 결정으로 다시 비활성화하지 않았다.

양쪽 서버의 파일은 모두 테스트용이다. Staging 파일과 원본 준비·두 중단 기록·성공 기록은 보존한다. 실제 자료 전체 이전을 현재 필수 작업으로 잡지 않는다.

## 다음 작업 순서

1. 현재 HEAD와 최신 기능 대조 보고를 읽는다. 0244d82의 CI는 성공 확인을 마쳤다. 이후 소스 변경이나 새 실패가 없다면 동일 조회·검사를 반복하지 않는다.
2. iPad 측에 서버 이전 보류 결정을 전달하고, 현재 합의한 출시 범위에서 남은 구현·검증 항목을 받는다. Windows의 기존 완료 근거와 대조해 이미 끝난 항목을 제외한다.
3. 새 계약 구조 쓰기를 포함해 무엇을 개발 완료로 볼지 양쪽 범위를 맞춘다. ‘모두 완료’를 끝없는 기능 추가나 전체 시험 반복으로 해석하지 않는다. 남은 항목별 구현 상태·격리 검증·실기기 확인 필요 여부를 구분한다.
4. 실제 남은 수정과 그에 필요한 검증만 진행한다. 기존 제한에 따라 관문은 닫아 두고, 새 실제 계약 송신·재전송·회차 생성은 이번 서버 이전 보류 결정만으로 실행하지 않는다.
5. 양쪽 합의 범위의 완료 근거가 모이면 서울 prod 이전 준비를 재개한다. 그때 계정과 prod에서 시작할 작품 범위를 정하고, 두 기기의 prod 사용 확인 뒤 Staging 비활성화 시점을 안내한다.
