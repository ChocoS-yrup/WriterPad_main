# iPad C9 구현 회신 대조 — 남은 공통 정책

후속: 아래 Windows 세 항목은 로컬 구현·회귀 검증을 완료했다. 최신 결과는 [Windows 계약 전송 보완 결과](windows-contract-send-policy-implementation-2026-09-06.md)를 따른다. 아래 내용은 수정 전 대조 기록이다.

2026-09-06 KST. 입력 문서는 `ipad-c9-and-recovery-implementation-2026-09-06.md`다. Windows는 HEAD `a3eaa8b97dc9769ad313ac3fe579d0b1443849a9` 위 C4·C5·C9 미커밋 수정 상태를 읽고 격리된 대역으로 확인했다. 제품 코드는 변경하지 않았다.

**판정: iPad는 C9 보완과 복구 진단 구현을 보고했다. 다만 새 iPad 정책과 Windows 사이에 아래 차이가 남아 있으므로, 전체 일치와 실제 계약 전송 준비 완료는 아직 확정하지 않는다.**

## 확인된 보고와 증거 한계

- iPad 보고 수치: 총 957개 / 통과 956 / 실패 0 / 건너뜀 1. Debug 기기용 빌드 성공. 이번 Windows 검토에서 재실행한 수치가 아니다.
- iPad 변경은 `bb40d22` 위 미커밋 작업 트리이며, 기존 설치본에는 반영되지 않았다. 새 실행 바이너리 SHA-256은 `426fc13fa198fd1a5e71c3ae2969b8953aea6ad80f4341dd1c34936243ff0e88`로 보고됐다.
- 제품+테스트 diff SHA-256은 `e955f146482d53632f074736326948973981f0ea66ab86bbaa037e0f55321a28`로 보고됐다. 이번 첨부에는 해당 diff와 연결된 evidence JSON이 없으므로 새 Swift 구현을 독립적으로 검증하거나 이 hash를 재계산하지 못했다.
- 문서상 구조 미확인·차단, queue blocked/conflict, 로컬 작품 삭제 수명, 서버 상태, 늦은 응답을 최종 전송 승인에 연결했다. 복구 진단은 개인정보/원고 없이 사건별 시각과 호출 수명을 기록하도록 추가됐다.
- 30초~2분 지연의 원인은 여전히 미확정이다. 새 진단 빌드의 실기기 설치·재현 결과는 아직 없다.

## 남은 차이

| 항목 | iPad 구현 보고 | Windows 현재 확인 | 정렬 제안 |
|---|---|---|---|
| 계약 전송 전 작품 상태 조회 | 수동 전송마다 새 `get_project_status` 읽기 | 현재 사용자/작품/연결에서 확인한 상태를 재사용. 전송마다 새 조회는 하지 않음 | 계약 쓰기 경로에서만 매 전송 준비 시 새 조회를 요구하고, 읽기 대기 뒤 모든 관문을 재검사 |
| 작품 상태 응답의 ID·실패 처리 | 응답 UUID 일치 필요. 조회 실패·누락·비활성은 거절 | `state`를 검사하지만 응답 project_id는 검사하지 않음. 기존 호환 조회 경로도 있음 | 계약 전용 상태 조회에서 UUID 문자열·요청 작품 일치를 필수로 하고 실패를 다른 조회/기본 active로 승인하지 않음. 일반 동기화 호환 경로와 분리 |
| queue 차단 후 해소 | 중간 blocked/conflict가 해소돼도 옛 전송 증명 재사용 금지 | 최종 blocked/conflict 개수는 검사하지만 중간 queue 상태 전이를 승인 세대에 기록하지 않음 | 차단/충돌의 발생과 해소를 기록하는 상태 세대를 연결. 옛 준비 요청은 중단하고 동일 배치를 새 승인으로 재시도 |

Windows 대역 재현 결과:

1. `get_project_status` 응답이 `{state: active}`이고 project_id가 없어도 active로 수락했다.
2. 응답 project_id가 다른 작품이어도 state가 active면 수락했다.
3. RPC 구성 중 실제 임시 DB 작업을 blocked로 만들었다가 retry로 해소하자 대상 계약 배치의 모의 execute가 1회 시작됐다.

이는 임시 저장소·대역 안의 결과다. 실제 서버 호출이나 실제 작품 관문 조작은 없었다. 1·2는 이미 보완한 C4의 **핸드셰이크 응답** 검사와 별개인 **작품 상태 응답** 검사다. 3은 구조/작품 상태의 변경 세대 검사가 아니라 **대기열 차단/해소 이력**에 관한 추가 차이다.

Windows의 기존 754개 검사 결과는 유지되지만 이 추가 정책 조건까지 통과했다는 뜻은 아니다. 위 정책을 맞출 때 각 재현을 전송 0회/잘못된 상태 응답 거절을 기대하는 상시 회귀 시험으로 추가해야 한다.

## 다음 순서

1. Windows: 위 세 항목을 계약 전송 경로에서 보완하고 회귀 검증한다. 기존 AI·집필 변경, 일반 동기화, 불변 배치 및 이미 시작한 요청의 영수증 처리는 보존한다.
2. iPad: 이번 미커밋 제품·테스트 diff와 문서에 연결된 검증 JSON을 전달해 소스와 보고 수치를 연결한다. 이 자료가 없는 동안 iPad 쪽 새 구현의 평가는 문서 기준으로 표시한다.
3. 양쪽 대조 후 검증한 소스를 커밋/빌드 식별자로 고정하고, 재빌드·설치 뒤 닫힌 관문에서 실기기 복구 진단을 수집한다.
4. 그 결과를 확인한 다음 별도 Staging 작품의 폴더 1개 + tree_order 1개 계약 시험을 결정한다. 실제 관문 개방과 서버 설정 변경은 이번 검토에 포함하지 않는다.

**사용자가 지금 할 일:** Windows에는 “계약 전송마다 작품 상태를 새로 조회하고 응답 작품 ID를 검사해줘. 대기열 차단 후 해소돼도 이전 전송 승인을 재사용하지 않도록 보완해줘”라고 요청한다. iPad 측에는 이번 제품·테스트 diff와 검증 evidence JSON을 함께 전달해 달라고 요청한다. 지금 앱을 조작하거나 통신 장애 시험을 반복할 필요는 없다.
