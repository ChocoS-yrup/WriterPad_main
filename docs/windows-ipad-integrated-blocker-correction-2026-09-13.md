# 실제 시험 명세 차단 보완안 — 승인 범위 변경 제안

**후속 승인:** 사용자가 이 보완안에 「승인」으로 응답했다. 추가 8쓰기, Windows 쓰기 상한 21·HTTP 280·양측 HTTP 800을 승인받았다. 화면 조작은 기존 사용자 선호대로 사용자가 수행하고, 이후 새 명세를 확인한다. 아래 ‘승인 전’은 제안 작성 당시 기록이며 실제 조작·송수신 완료를 뜻하지 않는다. 절대 만료 12:30 KST는 유지한다.

2026-09-13. 사용자 전달 iPad 차단 보고를 검토하고 **복제본·동결 후보·mock transport만으로 보완 절차를 확인**했다. 실제 앱·큐·명세·서버는 변경하지 않았다. 기존 Windows 실행 승인은 유지하되 아래 추가 쓰기/한도 변경은 아직 승인 전이다. 기존 S1은 차단 해소 전 보류한다.

## 확인한 차단

1. **이름:** 동결 `build_document_commit_request`의 실제 직렬화 결과는 `name:"왕복"` / `name:"빈문서"`다. `.txt`를 자동 부착하지 않으며 wire에 `relative_path` 필드는 없다. 서버가 경로를 계산한다. 따라서 현재 명세를 iPad가 수신할 수 있다고 확인할 근거가 없다. 앞선 ‘실제 이름 그대로 사용’ 안내를 정정한다.
2. **B 정렬:** 현재 큐에 B 정렬 작업이 없다. 보존된 `private.apply_structure_intent.sql`의 폴더 분기는 폴더만 생성하고 반환하며, 정렬 생성은 별도 `tree_order/reorder` 분기다. 이 과거 SQL 자료를 현재 서버 정의의 재조회로 해석하지 않으며, 자동 생성에 기대지 않고 명시적 정렬 쓰기를 준비한다.

iPad 후보 `202609130843` 설치 완료·앱 종료·실행 JSON 미결합·인증/서버 요청 0회 보고와 기존 명세 SHA-256 일치는 확인됐다. 실제 이름 호환/첫 수신 준비 완료는 아직 확인되지 않았다.

## 수정할 화면 작업 — 승인 후 사용자가 4회 조작

자동 동기화는 계속 끈다. `메인/메모장/통합검증 20260913` 아래 기존 항목을 사용한다.

1. A의 `왕복`을 **`왕복.txt`**로 이름 변경한다.
2. A의 `빈문서`를 **`빈문서.txt`**로 이름 변경한다.
3. `빈문서.txt`를 **B로 이동**한다.
4. 같은 `빈문서.txt`를 **A로 다시 이동**한다.

새 항목 생성·삭제·본문 재저장·큐 초기화는 추가하지 않는다. 최종 배치는 T=[A,B], A=[R,E], B=[]로 원래 작업표와 같고, ID 5개·R/E 본문은 유지한다. 조작 후 예상 대기 **19개 · 충돌 0개**다. 앱 종료 후 복제본에서 이를 확인하고 새 명세를 별도 파일로 내보낸다. 현재 `test-targets.json`과 체크섬·기존 증거는 덮어쓰지 않는다.

대기 19개의 구성은 기존 11개 + 이름 변경 2개 + 이동 2개 + 이동에 따른 정렬 4개다. 최초 11개는 내용/순서를 그대로 보존하고, 뒤에 8개가 붙는다. B 정렬은 E가 들어간 상태를 첫 생성으로 보내고, E가 나간 빈 상태를 다음 revision으로 보낸다.

## 송신 결과의 기대값과 근거 범위

- 동결 후보를 이용한 복제본 시험에서 19개 쓰기 직렬화·mock 반영·후속 수신이 통과했다. B 정렬 `c225e5a6-4d1a-5e23-969c-60a48332bd18`은 **base 0 → revision 1, children=[E] → revision 2, children=[]**가 된다. 실제 서버 결과가 아니라 승인 후 확인할 기대값이다.
- 최종 메타데이터에서 유도되는 경로는 `메인/메모장/통합검증 20260913/A/왕복.txt`, `메인/메모장/통합검증 20260913/A/빈문서.txt`다. Windows wire에 경로를 임의 추가하지 않는다. 이 경로는 아직 관측한 서버 `relative_path`가 아니다. iPad 첫 수신의 실제 경로 검사와 B 정렬 기준 수신까지 성공해야 차단을 실검증으로 해소했다고 기록한다.
- **iPad는 S1 19개 전부 송신 완료·미확정 batch 없음·Windows 후속 수신 완료 신호 전에는 수신하지 않는다.** 앞부분의 원래 생성 요청은 확장자가 없는 이름을 담고 있으므로 중간 수신을 허용하지 않는다. 이후 이름 변경까지 완료된 상태만 받는다.
- S2~S7 작업 순서는 유지한다. S2 iPad의 기존 산정 7쓰기/5호출, S3 5쓰기/2호출, S4 3쓰기/1호출 조건을 변경하지 않는다. B 정렬 실제 기준이 수신되지 않으면 S2를 시작하지 않는다.
