# 작가님 힘내세요 검토 — 2026-09-05

개인 웹소설 집필, Apple 기기와 Windows 간 전환, Windows AI 초안·검교정을 기준으로 검토했다. 판매·공개 배포 기능은 평가 기준에서 제외했다. 제품 코드는 수정하지 않았다.

## 종합 판단

제작 방향은 목적에 맞는다. 원고·설정집·캐릭터·메모, 분할 편집, 글자 수, 검색·추출, 한글 조합 처리, 로컬 저장과 서버 동기화의 분리가 집필에 필요한 기반을 제공한다. 다만 Windows 집필 모드와 AI 보조 모드의 저장 안전성에는 차이가 크다. 다음 기능 추가보다 AI 모드 저장·작업 수명 관리의 보완이 우선이다.

## 확인한 결함과 사용 목적의 미충족 부분

### 1. [P1] AI 모드 자동저장 신호가 연결되지 않는다 — 재현 확인

- `editor_panel.py:43`에서 5초 유휴 타이머를 만들고 `editor_panel.py:188`에서 `autoSaveRequested`를 발생시킨다.
- `mode_assistant.py:222` 부근의 패널 연결에는 수동 저장 등만 있고 자동저장 연결이 없다.
- 임시 프로젝트로 실제 AssistantModeWidget을 생성했다. 초안 패널의 신호 수신자 수는 0이었고, 입력 후 5.2초가 지나도 해당 초안 파일을 읽은 결과는 빈 문자열이었다.
- 탭·화 전환이나 수동 저장으로 보존될 수 있지만, 그 전에 비정상 종료하면 입력 내용을 잃는다. AI 결과 적용에서 호출하는 `trigger_autosave()`도 같은 영향을 받는다.
- 수정 방향: 패널의 단계와 화수를 고정해 원고를 저장하는 슬롯을 연결하고, 저장 성공 후에만 저장 상태를 갱신한다. 현재 선택된 화수만 읽는 연결은 분할 편집에서 다른 화에 저장할 수 있으므로 피해야 한다.

### 2. [P1] AI 생성 중 취소가 작업을 종료하지 않고, 늦은 결과가 다른 화에 기록된다 — 경로 재현 확인

- `ai_panel.py:138`의 취소는 `closeRequested`를 발생시킨다.
- 연결된 `assistant_workflow.py:155`의 `hide_ai_panel()`은 화면을 숨기고 화수 이동을 풀며 `is_working=False`로 바꾼다. 실행 중인 워커를 중단하거나 결과를 무효화하지 않는다.
- `assistant_workflow.py:410`의 결과 저장은 요청 당시 화수가 아니라 응답 시점의 `self.current_chapter`를 사용한다.
- 대역 워커를 사용한 재현에서 취소 후 중단·대기 호출은 없었으며, 1화 요청의 늦은 결과가 `save_ai_response('초안', 2, ...)`로 전달됐다. 실제 유료 API는 호출하지 않았다.
- 이는 AI 응답 기록의 화수 혼동이다. 이 재현만으로 원고 본문이 자동 덮어쓰기됐다고 주장하지 않는다. 새 요청까지 시작하면 이전 워커와 새 작업의 상태도 섞일 수 있다.
- 수정 방향: 요청 ID, 프로젝트, 화수, 단계, 모델을 요청 시작 때 보관한다. 취소된 요청의 콜백은 무시하고, 화면 표시 상태와 워커 실행 상태를 분리한다.

### 3. [P1] AI 모드 파일 저장 실패가 기존 원고를 비울 수 있다 — 장애 주입 재현 확인

- `project_manager.py:250`의 `save_chapter_text()`는 대상 파일을 `open(path, 'w')`로 직접 연다. 파일을 여는 순간 기존 내용이 잘린다.
- 임시 원고를 먼저 저장한 후 쓰기 단계에 OSError를 주입했다. 예외 발생 후 기존 파일 크기는 0바이트였다.
- `QMutex`는 동시 접근을 막지만 실패한 쓰기를 복구하지 않는다.
- 집필 모드의 `project_manager_writing.py:160`에는 이미 임시 파일 쓰기 → flush/fsync → os.replace 방식이 있다. AI 모드에도 같은 보존 원칙을 적용하는 것이 적절하다.

### 4. [P2 / 요구 범위] 확인한 Apple 작업 브랜치는 iPhone을 포함하지 않는다

- Apple 저장소의 `b993845e8ff8aa3e84a966ac842ba877f0a5fe8a`에서 Xcode 프로젝트를 확인했다.
- 앱 Debug/Release 설정은 `TARGETED_DEVICE_FAMILY = 2`이며 `SUPPORTS_MACCATALYST = YES`다. iPad와 Mac Catalyst 경로가 있고, iPhone 대상인 1은 포함되지 않았다.
- 근거: [Xcode 프로젝트](https://github.com/ChocoS-yrup/Writerpad/blob/b993845e8ff8aa3e84a966ac842ba877f0a5fe8a/WriterPad.xcodeproj/project.pbxproj#L1155), [Apple 설정 정의](https://developer.apple.com/documentation/xcode/build-settings-reference).
- iOS가 iPhone 사용을 뜻한다면 요구사항이 남아 있다. 대상 추가와 함께 작은 화면의 바인더·키보드·선택·분할 화면을 확인해야 한다. Mac Catalyst 설정이 있다는 사실을 Mac에서의 실사용 검증 완료로 간주하지 않았다.

## GitHub 교차 작업에 대한 평가

Apple 구현이 로컬 Windows 폴더에 없다는 이유로 미구현이라고 판단하지 않았다. GitHub에서 두 저장소의 브랜치, PR 설명, 인수인계 문서를 확인했다.

- Windows: `feat/contract-handshake-closed-gate`, `0417330b7e1b4832c5edaedf930cad0903cce24c`. 로컬 HEAD와 원격 브랜치 SHA가 같았다.
- Apple: `codex/ipad-unified-contract-canary-integration`, `b993845e8ff8aa3e84a966ac842ba877f0a5fe8a`. 8월 30일까지의 초기 진입·pull 성능 보완 커밋을 확인했다. 이것이 현재 설치된 앱과 같은 빌드인지는 확인하지 않았다.
- [Apple PR #18](https://github.com/ChocoS-yrup/Writerpad/pull/18)에는 Windows와의 계약 해석 교차 검토, 삭제와 이름 변경 충돌, 실기기 검증06·07 기록이 있다. 해당 테스트 수치는 작성자의 기록이며 이번 검토에서 다시 실행한 수치가 아니다.
- [교차 작업 문서](https://github.com/ChocoS-yrup/Writerpad/blob/b993845e8ff8aa3e84a966ac842ba877f0a5fe8a/Docs/CrossPlatformSyncGitWorkflow.md)는 정확한 커밋·계약 SHA·시험 ID를 인계하도록 정한다. 이 방향은 적절하다.
- 실제 작업 진척은 양쪽 모두 main보다 앞선 브랜치에 있다. 따라서 main이나 열린 PR만으로 설치 앱의 완성도를 판단할 수 없다. 개인 사용에서는 ‘현재 Windows 빌드 SHA / Apple 빌드 SHA / 서버 마이그레이션 / 마지막 기기 왕복 시험 결과’를 한 곳에서 확인할 수 있으면 충분하다.

## 목적에 맞춘 개선 우선순위

1. AI 모드 자동저장, 실패 시 원본 보존, 요청 취소와 결과 귀속을 먼저 고친다.
2. 실제 사용하는 두 빌드 조합으로 한글 조합 중 앱 전환, 오프라인 집필 후 다른 기기 편집, 삭제·복원, 동시 이름 변경, 강제 종료 후 복구를 확인한다. 기존 계약과 시험 자산을 재사용한다.
3. 검교정은 현재의 평가·대화 기능 위에 원문/수정안 비교와 변경별 적용을 제공하면 목적에 더 직접적으로 맞는다. 현재 `apply_ai_result()`의 일반 경로는 결과를 끝에 덧붙이는 방식이다. 초안·평가에는 쓸 수 있지만 교정본 반영에는 수작업이 남는다.
4. 원고의 기준본은 집필 모드로 정하고, AI에 보낸 문서와 결과 적용 대상이 명확하게 보이도록 한다. 현재 두 모드는 서로 다른 저장 경로를 사용하며 모드 간 전달은 텍스트 추가 방식이다.
5. 백업 코어와 복원 시험은 갖춰져 있다. 확인한 화면에서는 파일 이력 복원과 백업 폴더 열기가 중심이므로, 작품 전체를 독립 위치에 백업하고 복원하는 실제 사용 절차를 간단하게 정리하는 편이 좋다.

개인 사용이므로 회원·협업 권한·결제·배포 체계를 확장할 필요는 없다. 유지보수에서는 저장 경로를 공통화하고, 약 1만 2천 줄인 `sync_manager.py`의 책임을 필요할 때 나누는 정도가 우선이다. 전체 재작성은 권하지 않는다.

## 검증 범위와 결과

- Python 3.11.9, PyQt6 offscreen 환경. 프로젝트와 동기화 데이터 위치를 임시 폴더로 지정하고 자격 증명 읽기·쓰기를 대역 처리했다. 실제 AI 생성·실서버 동기화는 실행하지 않았다.
- 기존 9개 테스트 모듈에서 475개 실행: 472 통과, 1 실패, 2 건너뜀. [로그](../_review_test_results.txt).
- 실패 항목은 `tests.test_sync_state.SyncManagerStateTestCase.test_trashed_project_status_stops_retry_and_preserves_queue`다. 같은 항목을 단독 실행하면 통과했고, `tests.test_sync_state` 모듈 전체를 별도 프로세스로 실행해도 49개 모두 통과했다. 실행 순서에 따른 공유 상태 간섭 가능성이 있으며, 제품 결함으로 확정하지 않았다. [분리 실행 로그](../_review_syncstate_isolated.txt).
- 최초 시험의 강제 오프라인 설정과 임시 현재 디렉터리는 일부 기존 테스트의 전제와 충돌했다. 해당 설정을 바로잡아 재실행한 결과만 위 집계에 사용했다.
- AI 자동저장 누락, 취소 후 결과 귀속, 저장 실패 시 파일 비움은 별도의 임시 데이터 재현으로 확인했다. 기존 테스트가 대부분 통과해도 이 연결 누락까지 검증된 것은 아니다.
- Apple 실기기 실행, Mac 빌드, 설치된 Windows exe와 소스의 동일성, 현재 Supabase 배포 상태, 실제 모델 응답 품질은 이번 검토의 검증 범위에 포함되지 않았다.
