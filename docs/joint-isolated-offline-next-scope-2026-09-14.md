# 양측 준비안 대조와 다음 오프라인 구현 범위

2026-09-14. Windows 최소 조회 준비안과 사용자가 전달한 iPad 로컬 준비안을 대조했다. 이번 작업은 문서 검토·범위 정리이며, 아래 구현 제안은 아직 실행하지 않았다. 실제 설치·서버 요청·로그인 갱신·관문/hold 변경·서명은 허용하지 않는다.

## 대조 결론

- **J02:** 양측이 수용한 UI 자동 수신 대기·HTTP 0·빈 주기 차감 0 기준을 유지한다. 과거 제안 JSON에 남은 Windows 초안 차이를 현재 미해결 문제로 다시 올리지 않는다.
- **J04 Windows 확인:** iPad의 신규 실패 주입 2개를 포함한 최종 고유 49개 통과는 전달 보고로 확인했다. Windows는 preserve 성공, iPad는 다음 변경 입력의 draft 기록 성공으로 오류를 해제한다. iPad의 TXT 자동저장 성공만으로는 오류가 해제되지 않는 차이를 수용·기록한다. 원래 clean 상태의 실패 주입과 실패 후 자동저장으로 clean이 된 상태도 같은 검사로 부르지 않는다. iPad 준비안의 ‘Windows 후속 확인 대기’에 대한 회신은 이 항목이다. 추가 구현·재검사로 차이를 없애지 않는다.
- **J05/J07:** 저장 source와 Windows local content/job은 같은 필드 상태가 아니다. UI 초안 가드를 직접 backend나 초기화 경로의 보장으로 확대하지 않는다.
- **초기 기준본:** Windows의 제안·과거 17 node/15 order·향후 7회 조회 결과를 자동으로 iPad의 초기 baseline으로 승격하지 않는다. 실제 생성 전 후보 revision은 계속 null이다.

## 다음 한 묶음 — 병행 가능한 오프라인 구현 제안

| 담당 | 구현할 범위 | 완료를 확인할 범위 |
| --- | --- | --- |
| Windows | 기존 앱/store와 독립된 읽기 수집기. 고정 계정·작품과 Q1~Q7 allowlist, 별도 사용량 기록, 시도 전 차감, 전체 deadline, raw 응답 보관, count/대상/계약 확인, metadata·정렬·차이 보고. 기존 DB나 TXT로 수신 적용하지 않음 | MockTransport와 새 합성 경로에서 정상 7회, 대상/계약 불일치·401·잘림·timeout·중단 보존·추가 요청 차단을 변경/영향 검사 한 묶음으로 확인. 실제 세션을 읽거나 network_factory/cycle을 실행하지 않음 |
| iPad | 별도 local identity/저장소의 결합 경계, Windows 제안 reader와 **합성 입력 전용** 초기 수신 적용·재개 adapter. 기존 합성 저장소와 실제 검증용 저장소를 구분. 보유 자료·제안·관찰 자료·검증된 기준본을 다른 상태로 표현 | 임시 합성 ID/파일만으로 잘못된 결합·부분 초기화·재시작·본문/정렬/해시 불일치와 기존 자료 보존을 한 묶음으로 확인. 실제 검증 local UUID 발급·앱 결합·서명·설치는 제외 |

양측은 위 구현을 동시에 진행할 수 있다. 실제 값이 필요한 자리는 미확정으로 남기고 합성 fixture로 계약을 검증한다. 기능을 검증하려고 기존 run·원본·기기 저장소를 재사용하지 않는다. 새 수집기용 미래 실행 범위를 기존 종료 실행과 혼동하지 않도록 구분한다.

## 먼저 고정할 자료 연결 경계

Windows 수집기는 **응답 관찰 묶음**을 출력한다. 요청별 순서/시각/성공·실패/전송 전 예약, endpoint·account·project·계약, 표 이름·count·raw 파일 참조와 원래 바이트 SHA, metadata/orders 대조 결과를 담는다. 토큰/세션 비밀정보는 내보내지 않는다. 실제 원고를 포함한 raw 파일은 비공개 보관 자료이며 metadata 전달본과 구분한다.

읽기 수집기의 출력 형식 명세는 Windows 구현 때 함께 작성한다. iPad는 실제 Windows 출력의 정확한 필드가 확정되기 전 독자 형식을 호환됐다고 표시하지 않는다. 그동안 기존 제안 reader와 내부 합성 입력의 검증/적용 계층을 구현할 수 있다. 출력 형식이 전달되면 누락·매핑 차이만 좁혀 확인한다. 기존 검토기를 느슨하게 하거나 complete/revision을 보정해서 통과시키지 않는다.

관찰 묶음에는 계정 가시 범위·테이블별 count·순차 조회의 시각 구간을 표시한다. 성공해도 단일 시점 snapshot·RLS 밖 행의 비존재·생성 후 기준본을 뜻하지 않는다. iPad가 검증된 baseline으로 받아들이는 조건은 별도 입력 계약으로 남긴다. 적용 준비가 안 된 자료를 받으면 보관/대조까지만 하고 편집·송신을 열지 않는다.

## 실제 단계의 순서 — 아직 실행하지 않음

1. 양측 오프라인 구현·영향 검사와 입력 형식 대조를 마친다.
2. Windows 최소 조회를 별도 대상·계정·7회 제안·시간·실행 식별자로 구체화하고 실제 동작 승인을 받는다. 로그인 갱신이 필요하면 별도 범위로 다룬다.
3. 승인된 Windows 관찰 자료를 검토해 생성 주체·최신 부모 정렬·필요 범위와 실제 생성 비용을 확정한다. **생성 주체는 Windows를 제안**하되 아직 생성 구현/실행을 승인하거나 완료한 것은 아니다. 동일 트리의 양측 중복 생성을 피하기 위한 단일 담당 제안이다.
4. 승인된 생성이 완료된 다음 실제 수신 기준본을 검증하고 iPad 초기 수신을 진행하는 순서를 별도로 정한다. 생성 직전 재확인·초기 수신의 Auth/HTTP는 Windows 첫 7회 조회에 포함하지 않는다. 서로 다른 승인 단계 사이의 오래된 조회를 최신값으로 재사용하지 않는다.
5. iPad 서명 후보는 확정된 기능/소스와 새 App ID의 유효 서명 조건이 갖춰진 뒤 준비한다. 서명·설치·실기기 실행은 현재 오프라인 구현 범위 밖이다.

현재 원격 대상 complete=false, 신규 revision null, 실제 iPad local project 미확정 상태를 유지한다. 과거 Windows 53개/iPad 49개 검사 결과와 기존 충돌·18/19바이트 미송신 원본·종료 사용량/만료·설치물·증거는 보존하며 이번 검토에서 다시 검사하지 않았다.
