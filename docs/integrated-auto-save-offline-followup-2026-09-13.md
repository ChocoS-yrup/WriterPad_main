# 자동 수신 한도와 저장 경계 — 오프라인 후속 구현

2026-09-13. 현재 요청의 「진행」에 따라 제안한 코드 구현과 오프라인 변경·영향 검사를 완료했다. 이전 통합 실행의 승인·만료·사용량은 이력으로만 취급했다. 이 문서는 새 설치나 실제 서버 실행의 승인이 아니다.

## 구현과 범위

- `integrated_editor_sync.py`: 자동 실행 정책 검사와 빈 자동 주기 예약을 인증 호출 앞에 연결했다. AutoSync는 마지막 허용 주기를 마친 뒤 영속 정지 사유를 읽어 꺼진다.
- `integrated_editor_store.py`: 새 정책이 있는 새 run에만 `empty_cycles_used`, `automatic_stop`을 만든다. 사용량 차감과 마지막 주기의 자동 꺼짐을 기존 감사 트랜잭션에 함께 기록한다. 기존 run에는 카운터를 추가하거나 사용량·만료를 초기화하지 않는다.
- `integrated_editor_ui.py`: 한도에 도달한 실행은 체크박스·재연결·재시작으로 자동을 다시 켤 수 없다. 정지 안내와 저장 결과·오류를 함께 보여 준다. 입력 경로를 표시하는 전용 SmartTextEdit 하위 클래스를 사용하며 공용 `text_editor.py`는 수정하지 않았다.
- 저장 진단은 입력과 실제 저장 경계를 구분한다. 붙여넣기, Enter, 일반 키, IME, 기타 텍스트 변경과 자동저장 타이머, 저장 버튼, 저장 단축키, 문서 전환을 식별하고 본문 전후 UTF-8 바이트 수·끝LF 여부·SHA-256·실제 변경 여부를 기록한다. 새 진단 필드에 본문 자체를 추가하지 않는다. 최신 진단은 state에, 이전 경계는 기존 감사 이벤트에 남는다. 원격 본문으로 교체되면 입력 출처는 `remote_snapshot`으로 표시한다.

## Windows 로컬 정책 v1

새 실행 범위의 선택 필드 `automatic_policy`는 정확히 `version: 1`과 `max_empty_cycles: 0 이상의 정수`로 구성한다. 실제 허용량을 정한 실행 JSON은 만들지 않았다. 기존 승인 필드·wire metadata·build ID는 변경하지 않았다.

- **빈 주기**: dispatch lock을 확보하고, 송신 또는 receipt 복구 batch 없이 시작하는 자동 수신 시도다. 원격 변경 발견 여부와 무관하게 센다. 원격이 비었는지 알아보려고 추가 조회하지 않는다.
- **차감**: 인증 포함 첫 HTTP 전에 영속 예약한다. 실패·응답 오류·불완전 snapshot·프로세스 중단에도 반환하지 않는다. 예약 후 첫 HTTP 전에 중단돼도 사용한 것으로 남기는 보수적 정책이다.
- **제외**: 타이머 대기, 비활성·오프라인 상태, dispatch busy, 실제 시작 전 권한/충돌 차단, 송신 및 receipt 복구 batch가 있는 자동 주기. 기존 전체 HTTP·시간 제한은 이 경우에도 적용한다.
- **종료**: N번째 빈 주기는 기존 HTTP·시간·권한 한도 내에서 응답 적용까지 허용한다. 예약 시 자동 정지를 함께 기록하며 N+1번째부터는 모든 자동 동기화를 HTTP 전에 차단한다. 허용량 0이면 처음부터 차단한다.
- **범위**: 기기의 해당 run 누적량이며 연속 횟수나 단계별 초기화가 아니다. 수신 성공·수동 실행·재시작·foreground 복귀·체크박스 재활성화로 되돌리지 않는다. 정책 없는 이전 형식의 자동 실행과 손상된 카운터는 차단한다. 동일 run의 승인 변경은 기존 `EXECUTION_SCOPE_CHANGED`로 거부한다.
- **수동 경로**: 자동 한도는 수동 요청의 기존 승인·HTTP·시간 검사를 대체하지 않는다. 수동으로 자동 차감량을 돌려받지 않으며, 이 코드가 새로운 실제 수동 실행 권한을 주지 않는다.

이 정책은 이번 Windows 로컬 구현의 명시적 정의다. 과거 iPad 보고 주기 수를 이 규칙으로 재계산하거나 호환 판정하지 않았다. iPad에는 향후 같은 사전 예약·누적 보존·재시작 차단 의미를 맞춰야 하며, 필드나 구현이 이미 호환된다고 주장하지 않는다. Auth·쓰기별 하드 한도는 이번 범위에 포함하지 않았다.

## 저장 원인 확인의 현재 결론

합성 Qt 입력에서 ‘끝LF 없는 붙여넣기 → 자동저장 → Enter → 저장 버튼’은 서로 다른 두 본문 작업으로 남고, 같은 내용의 저장 단축키는 추가 본문 작업을 만들지 않았다. 각 경계를 진단으로 구분했다. 저장·본문·원래 요청을 병합하거나 끝LF를 보정하지 않았다.

이는 가능한 입력 순서의 재현이며 과거 Windows 58→59바이트 및 iPad 17→18→0바이트의 실제 UI 원인을 확정하는 증거는 아니다. 기존 기록에는 이 진단이 없으므로 당시 원인은 미확정이다. IME나 플랫폼의 지연 이벤트는 실제 관찰된 경로까지만 해석해야 한다.

## 검증·보존

- 기존 13개 tracked dirty와 나머지 미추적 자료를 유지했다. 설치·원본 DB 연결·종료 실행 설정·로그인·관문/hold·prod는 변경하지 않았다. iPad 충돌 및 미송신 원본 2개도 조작하지 않았다.

다음 판단 지점은 이 정책을 iPad에 맞출 범위와 저장 경계 재현 범위다. Windows 실제 receipt SELECT/RLS·실기기 자체 충돌 및 iPad 중간 snapshot 회복은 여전히 별도 미확인 항목이다. 새 설치·실행이 필요하면 먼저 새 대상·횟수·시간을 구체화한다.
