# 통신 차단 시작 준비 — 실제 앱 실행은 승인 대기

후속 상태: 명시적 승인 후 통신 차단 상태의 새 앱 시작과 원본 DB 8013 업그레이드를 완료했다. 최신 결과는 [완료 기록](windows-offline-startup-and-db8013-complete-2026-09-10.md)을 따른다. 아래는 첫 시도의 승인 전 기록이다.

2026-09-10. 사용자의 ‘다음 진행’에 따라 통신 차단 상태의 새 앱 시작·원본 DB 업그레이드를 준비했다. 실제 실행 명령은 자동 승인 검토에서 실행 전에 거부됐다. **앱은 실행하지 않았고 원본 DB는 8012 그대로다.** 설치된 EXE는 새 후보 그대로 유지된다.

## 준비와 원상복구

- 기존 오프라인 표식은 동기화 작업 일부를 차단하지만 `create_supabase_client()`의 초기 세션 복원까지 차단하는 장치는 아님을 확인했다.
- 기존 코드에는 인증 mutex를 다른 프로세스가 보유하면 transport 생성·토큰 읽기 전에 client 생성을 거부하는 경로가 있다. 이를 앱 실행 동안 보유하는 보호 프로세스를 준비했다. 제품 코드·EXE를 패치하지 않았다.
- Windows 방화벽의 Domain/Private/Public 프로필이 모두 활성화돼 있고 로컬 규칙 적용이 가능한 상태임을 확인했다.
- 사용자 계정 컨트롤을 통한 관리자 helper로 설치 EXE 경로에만 임시 Outbound/Inbound Block 규칙 2개를 만들고 속성을 확인했다. 프로그램 경로·방향·프로필을 지정하는 규칙 방식은 [Microsoft Windows Firewall 문서](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/configure-with-command-line)를 참고했다.
- 실제 앱 시작 명령이 거부된 뒤, 앱이 실행 중이지 않은 것을 확인하고 이번 규칙 2개만 제거했다. 규칙 잔여 0개, 기존 세 프로필 활성화 유지와 helper 종료 기록을 확인했다. 인증 보호 프로세스도 시작되지 않았다.
- 원본 AppData 전체가 이전 보존 목록·해시·수정 시각과 동일하다. 설치 EXE SHA256도 `def63f0086e0a0e3ce5cc9530d580d339a1128835afcf961964a616cea1df070` 그대로다.

## 거부 사유와 필요한 확인

자동 승인 검토는 앱을 실행해 원본 DB를 8012에서 8013으로 변경하는 작업을 거부했다. 앞선 명시적 승인은 EXE·독립 복구 도구 설치에 한정됐고 원본 DB 업그레이드는 보류했으므로, ‘다음 진행’만으로 이를 승인했다고 볼 수 없다는 이유다. 다른 실행 경로나 권한 우회로 재시도하지 않았다.

다음 실행에는 **‘통신과 자동 인증을 차단한 상태에서 새 앱을 실행하고, 원본 DB를 8012→8013으로 업그레이드하는 것을 승인한다’**는 범위의 명시적 확인이 필요하다. 실제 송수신·관문 개방·송신 보류 해제·prod 전환은 계속 보류한다.

지금 Windows 앱은 직접 실행하지 않고 닫아 둔다. iPad 조작은 필요 없다. 허용 후에는 기존 백업과 DB 사본 검사 결과를 재사용하고 현재 상태가 같은지만 확인한다. 이번 시도의 준비·정리 기록은 보존하고 새 시도 디렉터리에서 차단 장치를 다시 적용한 뒤 실제 앱을 시작한다. 방화벽 준비 파일이 존재한다는 이유만으로 차단이 현재 활성화됐다고 가정하지 않는다.
