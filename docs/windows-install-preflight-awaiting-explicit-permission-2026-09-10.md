# Windows 설치 전 자료 보존·DB 사본 검증 완료

후속 상태: 이후 사용자님의 명시적 설치 승인을 받아 EXE와 독립 복구 도구 설치를 완료했다. 최신 결과는 [설치 완료·일반 실행 전 기록](windows-candidate-installed-not-started-2026-09-10.md)을 따른다. 아래 내용은 승인 전 시점의 기록으로 보존한다.

2026-09-10. 사용자님의 ‘진행’ 후 자료 보존·실제 DB 사본 검증·설치 전 점검을 완료했다. EXE 교체와 복구 도구 추가 명령은 자동 승인 검토에서 실행 전에 거부됐다. **설치는 수행하지 않았다.**

## 완료한 작업

- 사용자가 미저장 원고·AI 응답 저장 및 정상 종료를 확인했고, Windows 프로세스 종료도 확인했다.
- 기존 바로가기는 기본 설치 EXE를 가리키며 추가 실행 인자가 없다.
- 설치 폴더 692개 파일과 AppData 7개 파일, 총 **699개 파일**을 별도 비공개 로컬 폴더에 보존했다. 원본을 읽는 동안 DB 파일의 쓰기·삭제를 막는 읽기 핸들을 유지했다. WAL은 없었다.
- 복사 파일의 크기·SHA256 및 복사 전후 원본 목록·해시·수정 시각이 모두 일치했다. 원고·설정·DB 내용을 출력하지 않았고 Windows 자격 증명 저장소는 추출하지 않았다.
- 비공개 사본 경로: `_evidence/windows-candidate-install-20260910/private/backup/`. `private/.gitignore`로 사본과 사적인 파일 목록을 Git에서 제외했고 적용 여부도 확인했다. iPad 전달 ZIP에는 넣지 않는다.
- 보존본에서 별도 DB 검사 사본을 만들어, 후보 EXE와 소스 일치가 검증된 store 초기화 코드로 **8012→8013** 업그레이드를 확인했다. Qt·주 앱·인증·SyncManager를 불러오지 않았고 Python audit hook으로 네트워크와 하위 프로세스를 차단했다. SQLite 연결은 검사 사본 경로로 제한했다.
- 업그레이드 전후 무결성·외래키 검사 통과. 기존 **28개 테이블·4,173행**의 컬럼과 전체 행 집합이 그대로다. 기존 schema 객체의 변경은 의도한 mode/epoch trigger 하나뿐이다. 새 관측·permit 테이블은 비어 있고 재초기화해도 결과가 같다.
- 보호된 성공 회차 1개·이벤트 24개·영수증 1개 등 기존 기록을 보존했다. 프로젝트 16개, 열린 관문 0개가 유지됐으며 지정 시험 작품은 사본에서도 LEGACY/epoch 0/관문 0 그대로다. checkpoint 수용이나 서버 전환을 수행하지 않았다.
- 실제 설치 폴더와 AppData를 최종 대조했다. 모두 보존 직후와 같고, 실제 DB는 **8012 그대로**다. 후보 설치 임시 파일·복구 폴더·설치 정보 파일도 생성되지 않았다.

## 설치가 보류된 이유

자동 승인 검토는 ‘기존 설치 EXE를 교체하고 복구 도구를 추가하는 실제 설치’를 거부했다. 원래 사용자님의 명시적 설치 금지와 충돌하며, 이후의 모호한 ‘진행’만으로 설치를 승인했다고 볼 수 없다는 이유다. 실행 경로를 바꾸거나 승인 거부를 우회하지 않았다.

기존 설치 EXE SHA256은 `cd7ccebf125864b63ac8a9552585c44221e1086d0e6fc3e2617c6fa89a12fd89`다. 설치 대기 후보는 `def63f0086e0a0e3ce5cc9530d580d339a1128835afcf961964a616cea1df070`이며, 이전 후보 빌드·기능 검사를 다시 수행하지 않았다.

## 사용자 다음 행동

이 후보로 기존 EXE를 교체하고 독립 복구 도구를 설치하려면 **해당 설치에 한해 기존 설치 금지를 해제한다는 명시적 허용**이 필요하다. 일반 실행·원본 DB 업그레이드·실제 송신·관문 개방·prod 전환은 여전히 보류한다.

설치를 이어갈 경우 Windows 앱은 닫아 둔다. iPad 조작은 필요 없다. 재개 시 원본·사본·후보가 그대로이고 앱이 종료돼 있는지만 다시 확인한다. 상태가 같다면 완료한 백업과 DB 사본 업그레이드 검사를 반복하지 않는다.
