# S2 결과·계획 초과 기록 및 수동 후속 진행안

**iPad 보고상 S2 최종 데이터와 대상 batch 완료는 확인됐지만, 실행안 준수는 통과가 아닙니다.** 추가 본문 저장 1회와 빈 자동 수신 13주기(허용 6주기 대비 7주기 초과)를 그대로 기록합니다. 원인이나 실행 승인 범위를 사후에 바꿔 설명하지 않습니다. Windows는 아직 S2를 수신하지 않았습니다.

확인할 최종 상태는 `T=[A수정,B]`, `A수정=[]`, `B=[E,R]`입니다. R은 I1 **45바이트·본문 revision 4·구조 revision 4**, E는 **0바이트·본문 revision 4·구조 revision 6**입니다. 정렬 revision은 T=2, A=7, B=5로 보고됐습니다. E의 임시 본문 17→18→0바이트 작업 3개를 포함해 대상 wire 9개 모두 완료, 대상 미완료 batch/preparation·적용 대기 snapshot·이번 충돌은 0입니다. iPad journal 361개와 종료 전후 원본을 보존했다는 보고입니다. Windows 대조 전에는 양측 일치로 확대하지 않습니다.

현재 iPad는 **HTTP 199/520·Auth 8/16·쓰기 9/26**, Windows는 **HTTP 175/280·Auth 24/30·쓰기 19/21**입니다. 양측 자동 꺼짐·앱 종료로 대기하며 공통 만료 **15:00 KST**를 유지합니다. 사용한 요청은 모두 차감된 값으로 이어갑니다.

## 제안하는 재개 범위

사용자가 위 계획 초과를 인지한 상태에서 후속 진행을 승인하면, **양측 자동 동기화를 계속 끈 채 기존 남은 단계만 수동으로 진행**합니다. 완료된 S1/receipt 조회·S2 송신을 반복하지 않고, 기존 실행 ID·원본 요청/본문·카운터·checkpoint·진단 이력을 유지합니다. 기존 한도 증액이나 추가 빈 자동 주기는 포함하지 않습니다.

| 순서 | 진행 | Windows 추가 요청 예상 |
|---|---|---:|
| 1 | Windows S2 수신 1회 및 위 최종 상태 대조 | HTTP 7 / Auth 1 / 쓰기 0 |
| 2 | iPad S3 E 삭제 → B 삭제 완료 후 Windows 수신 1회 | HTTP 7 / Auth 1 / 쓰기 0 |
| 3 | iPad S4 B 복원 완료 후 Windows 수신 1회 | HTTP 7 / Auth 1 / 쓰기 0 |
| 4 | Windows S5 W2 저장·송신 1회 및 수신 1회 → iPad 정상 수신 | HTTP 15 / Auth 2 / 쓰기 1 |
| 5 | 기존 S6 순서로 Windows 마지막 본문 송신 1회 → iPad 충돌 관찰 | HTTP 8 / Auth 1 / 쓰기 1 |
| 6 | 양측 S7 보존·정상 종료, 서버 정리 삭제 없음 | HTTP 0 |

Windows 추가 정상 예상은 **44 HTTP·Auth 6·쓰기 2**, 최종 **HTTP 219/280·Auth 30/30·쓰기 21/21**입니다. Auth 여유는 없으므로 추가 로그인 갱신·재시도 소요가 생기면 기존 한도 안에 완료 가능한지 다시 확인해야 합니다. 현재 Windows 토큰 유효 시각은 **14:08:18 KST**이며 시험 만료와 별개입니다. S5 진입 전 잔여 한도 조건도 기존대로 대조합니다. iPad는 보고된 잔여 **321 HTTP·Auth 8·쓰기 17**에서 기존 S3~S6 소요를 계속 차감합니다.

자동 제한 초과 자체는 보존할 결과이며 이 진행안으로 소급 승인하거나 검사 통과로 바꾸지 않습니다. 이번 문서는 재개 범위를 구체화한 것이며 **아직 재개 승인·실제 앱 실행·서버 수신·설정 변경은 없습니다.** 당초 승인한 최종 실행안의 예상 밖 상태 중단 원칙에 따라 후속 재개 여부만 확인합니다.
