실제 sender는 쓰기 호출 전에 HTTP 시도를 먼저 영속 기록한다. 이 순서와 시도 0 기록, 서버 SELECT의 빈 원장 결과를 함께 근거로 쓰기 HTTP 전 중단으로 판단한다. 이는 영구 서버 거절이나 응답 유실/uncertain 사례가 아니다. 현재 관문은 닫혀 있지만 중간에 제품이 관문을 일시 사용했는지는 단계 기록이 없어 단정하지 않는다.

검토된 동일 SELECT를 재실행한 결과 batches/results/operations/attempts/new_folders는 모두 빈 배열이다. 기존 원고 순서 `68c1a7b5-0dda-49ba-bc9a-42e92ce2b758`만 revision 1, `[1권,2권]`으로 조회됐다. 로컬에도 새 3권은 없고 대상 계약 송신 배치 및 활성 작업은 0개다. DB는 WAL 부재를 확인한 immutable read-only로 조회했으며 읽기 전후 크기·수정 시각이 같았다. 원고 본문이나 자격 증명은 읽지 않았다.

**원인 대조와 한계**

`contract_preparation.py`의 `_reverse_local_metadata()`는 다음 상태를 묶어서 `CONTRACT_PREPARATION_NOT_READY`로 반환한다: 컨텍스트 불일치, 허용되지 않은 관문 상태, fresh handshake 부재, 구조/작품 상태 확인 불충족, 인증 차단, 종료 중, 문서 worker 존재, 구조 worker 존재, 다른 서버 작업 실행 중. 실제 송신 경로는 `executing=True`를 사용하므로 관문이 열렸다는 사실만으로 여기서 중단되지는 않는다.

이 검사는 실행 중 여러 경계에서 호출된다. 현재 실행 테이블에는 실패 단계나 조건별 값이 저장되지 않고 UI도 종합 코드만 표시한다. 따라서 “일반 수신이 겹쳤다”, “권한이 없었다”, “제품 오류다” 중 하나로 확정할 근거는 없다. 이후 `contract_validated_at=21:38:51.827318 KST`가 갱신됐다는 관찰 역시 실패 순간의 handshake 상태를 증명하지 않는다. 해당 시간대의 선별 일반 진단 조회에는 조건별 실패 근거가 없었다.

새 오류에 한정해 합성 SQLite·디렉터리·계정·요청 ID와 가짜 RPC로 세 조건을 각각 재현했다. (1) 구조 authority unknown, (2) 다른 서버 작업 1개, (3) 문서 worker 존재가 각각 동일한 오류, stopped/0, 쓰기 RPC 0, 닫힌 관문, 원본 보존을 만들었다. 세 재현은 모두 통과했지만 실제 발생 원인을 특정하는 시험은 아니다. 앞선 288개 시험이나 완료한 첫 계약·설치는 반복하지 않았다.

**다음 검토 범위안 — 실제 실행과 분리**

원본 및 stopped 기록을 유지한 상태로, 실패 단계와 위 조건별 판정을 비밀정보 없이 기록하는 진단 및 claim/송신을 호출하지 않는 준비 상태 조회가 필요하다. 일반 수신/다른 작업과의 조정이 필요한지는 그 근거로 판정한다. 현재 방어 조건을 제거하거나 저장된 stopped 기록을 pending으로 바꾸는 안은 포함하지 않는다.

이번 실행 승인은 1회만 허용했고 실제 진입 기록이 생겼다. HTTP 0이어도 같은 버튼을 다시 누르거나 DB를 지워 재개하지 않는다. 진단 개발 및 중단 요청의 복구 정책은 양쪽 검토로 별도 범위를 정해야 하며, 이후 실제 실행도 별도 승인이 필요하다. 이번 회신에서 제안만 했고 제품 소스·스키마·빌드·설치는 변경하지 않았다.
