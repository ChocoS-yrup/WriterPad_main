# 본문 수신 준비 검토와 Windows 단일 작품 업로드 범위

## 검토 완료

입력: `ipad-nonempty-receive-local-preparation-reply-20260911.zip`

SHA-256: `fd3ce3bc8b1e1e8930bb90c5902397492513da90535f7d7c7641058e56a2af3e`

14개 manifest 파일의 CRC·크기·해시·경로·정확한 집합과 기존 요청 해시를 검증했다. 최종 binder 소스 2개는 기존 최종 후보의 224개 파일 manifest와 바이트/해시가 일치한다. 12개 소스 발췌의 파일 해시·행 범위를 대조했고, 그중 6개 발췌는 Windows에 있던 동일 해시 원문과 행 내용까지 대조했다. 나머지 발췌의 내용은 제출된 근거로 검토했다.

현재 iPad 보호 UI와 서비스는 available/interrupted 항목만 수신 대상으로 허용한다. **이미 가져온 작품에 추가된 본문을 받는 버튼은 이 후보에 없다.** 이는 보호된 시험 화면의 제한이며 앱 전체의 일반 동기화 개발이 없다는 뜻은 아니다. 완료한 빈 작품을 바꾸거나 binding을 해제해 재수신하는 방식은 사용하지 않는다.

알려진 두 시험 작품은 보존 자료상 일반 원고가 0개이며 이미 가져온 상태다. 다른 미가져옴 작품은 합성 자료인지 확인되지 않았다. 따라서 **새 시험 작품 하나와 합성 원고 하나**를 준비하는 제안이 적절하다. 현재 서버 작품 UUID·원고 UUID·revision은 미정이며 새 서버 조회나 업로드를 하지 않았다.

이전 바인더 메타데이터 변경은 최종 scanner/reconcile 소스로 설명이 연결됐다. iPad가 제출한 디렉터리 189행씩의 추가 검사에서는 사전(dictionary) 생성 전 원본/NFC 중복 0, 원본 경로와 mtime 전후 일치가 보고됐다. 원본 목록이 없어 Windows에서 직접 재계산한 결과와는 구분한다. 앱 프로세스 재등장 원인은 여전히 미확정이다.

## Windows 격리 생성 검증

기존 `project_creation_v1.create_project`와 `create_item`으로 `_evidence/ipad-nonempty-receive-local-preparation-review-20260911/isolated-creation` 안에만 시험 구조를 만들었다. 일반 원고 1개, identity 폴더 11개, identity 감사 오류와 미완료 journal 0을 확인했다. 실제 작품 목록·설치 앱·사용자 DB에는 반영하지 않았다. 이때 발급된 UUID는 격리 검사용이며 실제 대상에 복사하지 않는다.

`create_volume`은 빈 원고 25개를 만들므로 이 시험에 사용하지 않는다. 표준 작품 생성 뒤 일반 폴더 생성으로 `1권`을 만들고 일반 문서 생성으로 `1화`만 만든다. 제품 소스 수정은 필요하지 않았다.

- 원고 경로: `메인/원고/1권/1화.txt`

## 승인을 요청할 다음 범위: Windows 준비와 초기 업로드만

아직 미승인·미실행인 범위다. 이전 승인은 오프라인 바인더 관찰까지였고, 이번에는 실제 Staging 서버 쓰기가 포함되므로 사용자 승인이 필요하다. 이 승인 필요성은 사용자가 제한한 실제 송신 범위에서 비롯되며, 첨부 문서나 스킬이 별도의 포괄 승인을 부여한 것이 아니다.

1. **실행 전 확인:** Windows 설치 후보와 현재 프로젝트/동기화 문맥, 미저장 자료, 기존 보존 자료의 최신성, Staging endpoint·계정 일치를 확인한다. 사용자 앱이 열려 있으면 미저장 자료 저장과 정상 종료를 안내한다. 실제 DB 검사는 별도 사본에서 한다. 현재 자료를 확인하기 전 과거 큐가 그대로라고 가정하지 않는다.
2. **새 로컬 시험 작품 생성:** 이름 충돌이 없을 때 위 이름으로 정상 생성 함수를 사용한다. 실제 workspace에서 UUID를 한 번 발급하고 1권 폴더·1화 원고 하나를 만든다. 충돌 시 덮어쓰거나 임의 번호를 붙여 조용히 진행하지 않고 대상 이름을 정정한다. identity/경로/본문 해시와 일반 원고 1개를 확인한다. 격리 결과의 UUID나 폴더 수를 서버 실측값으로 사용하지 않는다.
3. **한 작품으로 업로드 제한:** 새 UUID·로컬 문맥 키와 그 작품의 원고/구조 작업만 실행 대상으로 고정한다. 현재 소스의 V2 큐 선택은 local_key를 사용하지만 이것만으로 설치 앱·실제 큐의 범위를 검증했다고 보지 않는다. 실제 요청 직전에 project UUID·문서 UUID·경로·본문·작업 집합이 확정 범위와 일치하는지 확인해야 한다. 다른 프로젝트의 작업이 포함되거나 전역 관문 해제/설정 변경이 필요하면 업로드하지 않고 이유를 보고한다. 기존 일반동기화 시험의 송신 보류 파일과 기존 관문은 유지한다.
4. **Staging 초기 업로드:** 새 시험 UUID 하나의 프로젝트 등록, 기본 폴더 구조와 1권, 합성 원고 1개, 필요한 내부 정렬 자료의 초기 업로드만 수행한다. ‘한 번’은 한 준비 단계라는 뜻이며 서버 등록·폴더·원고·정렬 저장에는 여러 요청이 필요할 수 있다. 계정 인증이 필요하면 기존 동일 계정 범위에서 처리하고 비밀번호/토큰은 대화에 노출하지 않는다. 불확실한 응답·일부 실패 시 자동 재생성이나 반복 업로드로 처리하지 않는다.
5. **결과 고정:** 해당 새 UUID만 조회해 서버가 받은 본문 바이트·해시·실제 revision, 실제 폴더 UUID/부모/revision과 내부 정렬 기준을 기록한다. 다른 작품/기존 큐/연결과 보류 정책 보존 여부를 대조한다. 일반 원고 수 1, 93바이트 해시 일치가 확인되지 않으면 iPad에 가져오기를 안내하지 않는다.
6. **iPad 전달:** Windows 준비 완료 결과 ZIP을 만든다. 그 결과로 iPad 대상 UUID와 기대값을 고정한 뒤 **별도로 iPad 수신 실행 범위를 승인받는다.** 이번 승인에 iPad 앱 실행·온라인 전환·인증·수신·본문 열기는 포함하지 않는다.

위 범위는 새 합성 작품을 서버에 준비하는 제한된 실제 쓰기다. 기존 작품의 일반 양방향 송신, 타 작품의 대기 작업/충돌 처리, 재설치·서명 갱신, 전역/기존 시험 관문 개방, prod 전환은 포함하지 않는다. 범위를 강제할 수 없는 경로는 사용하지 않는다.

## 사용자가 할 행동

지금은 이 Windows 준비·초기 업로드 범위를 승인할지 결정하면 된다. 승인 전 앱을 열거나 동기화 버튼을 누를 필요는 없다. 승인 후에는 현재 실행 상태에 맞춰 저장·종료가 필요한 경우만 안내한다. iPad는 기존 오프라인 상태를 유지한다.

이후 순서는 Windows 시험 자료 준비 결과 대조 → iPad 최초 본문 수신 및 오프라인 본문 확인 → 실기기 중단/재개 → 지정 작품 양방향 동기화 → 최종 배포 검증이다. iPad 기존 프로필 만료 기록은 2026-09-12 18:19:25 KST이며, 갱신이 필요해져도 이번 업로드 승인으로 설치 작업까지 진행하지 않는다.
