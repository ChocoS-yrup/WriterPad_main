이번 iPad 문서의 3절은 실행 직전 점검 절차이며, 현재 iPad의 새 handshake·로컬 지문·큐가 전부 재확인됐다는 결과 보고는 아니다. 문서에 있는 ‘전송 범위를 제시할 수 있다’는 문장도 사용자의 실제 전송 승인으로 해석하지 않았다.

## 1. 이번에 해소된 항목

- ZIP manifest 9개 항목 모두 크기/SHA256 일치.
- 준비 요청 파일과 installation.json은 이전 검토본과 바이트 단위로 동일하다. 요청을 재발급·변경하지 않았다.
- 추가된 `project.pbxproj` 전체 SHA256은 `844bf07ac0ea30073c4068ec38a93998574742e47a2c17e89f65f2ac815875cc`로 기존 설치 기록과 일치한다.
- 이전에 검증한 8개 소스/시험/스키마 파일과 합쳐 **설치 기록의 9개 파일 모두 전체 해시를 독립 대조**했다.

- WriterPad/Debug dylib 해시는 기존 제출 설치 기록과 같으며, 기기 실행 바이너리 추출 검증이 아니라는 한계도 유지한다.

## 3. 결과 조회 SQL과 서버 상태

첨부 `first_contract_review_result_readonly.sql`의 내용을 검토했다. 하나의 WITH/SELECT 문이며 배치·결과·작업·시도·새 폴더·새 순서의 선별 정보만 읽는다. 쓰기 함수나 DDL은 없다. 원장 요청 payload나 원고 본문을 읽지 않는다. `results.response`는 이 구조 요청의 영수증 대조용이다.

Windows에서도 해당 SQL을 Staging `mhpnszcorfzrvhyondxr`에 **읽기 전용으로 실행**했다. 17:56:55 KST 정상 응답의 batches/results/operations/attempts/new_folders/new_orders는 모두 빈 배열이었다. 조회 수단이 동작함을 확인한 것이며 한 번의 빈 결과를 향후 미전송 확정·재전송 허가로 해석하지 않는다.

별도 17:57:00 KST SELECT에서 작품 active, 폴더 11개, 문서 26개, tree_order 0개를 확인했다. 준비 코드와 같은 구조 열·canonical 정렬로 계산한 지문은 `93de0096e7854f808db0becce48c1d123c1f1c98cb2ba250d9e7327d1561d2b4`로 고정 요청의 서버 지문과 일치한다. 결과 원장 조회와 구조 조회는 서로 다른 statement이므로 같은 원자 snapshot이라고 보고하지 않는다.

관리자 SELECT는 실제 iPad 로그인 계정의 권한·handshake 검사를 대신하지 않는다. 서버가 성공했는데 응답이 유실된 경우, 현재 iPad에는 이 관리자 조회 결과를 로컬 receipt로 가져오는 전용 UI가 없다는 설명도 확인했다. 서버 성공과 로컬 완료를 구분해 기록하는 절차는 적절하다.
