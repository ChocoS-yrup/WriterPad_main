## 서버 사전 점검 확정 결과

- 환경: WriterPad Staging, project ref `mhpnszcorfzrvhyondxr`.
- 계약: `0.2.0`, protocol `3`.
- digest: `416c1b99edb9bda694731dee4b25688d9d82d1f32610aa23ddfda571ec3c7670`.
- 2026-09-06 11:44~11:45 KST 조회 기준, 0.2.0 allowlist는 **이미 enabled=true**였다. 이번 작업에서 켠 것이 아니다. 0.3.0은 비활성이고 범위 밖이다.
- 서버 11개 작품은 모두 LEGACY/0. 이 계약은 해당 모드에서도 지원되므로 mode/epoch 변경이 선행 조건은 아니다.
- Windows 기본 프로필 15개 작품의 계약 관문은 모두 닫힘. iPad 제출 설치 기록도 열린 관문 0개. 서버 allowlist와 기기 관문은 별개다.
- 이전 시험 작품 최종검증02/03은 active이나 계약용 최상위 tree_order가 없다. 두 작품 중 어느 것도 이번 실제 전송 대상으로 확정되지 않았다.
- 기존 작품을 택하면 tree_order 존재 여부와 base revision을 새로 확인한다. 부재라면 새 ID/base_revision=0을 사용하고, 기존 최상위 자식 집합을 누락하는 순서 덮어쓰기를 피한다.
- 배포 함수에서 인증/권한, 활성 작품, revision, 원자적 구조 적용, 동일 요청 재전송 및 요청 변조 거절 경로를 확인했다. 공식 변경 RPC들이 같은 작품 트랜잭션 잠금을 사용한다.
- 서버에 저장된 영구 거절 결과와 로컬 미전송 차단을 구별한다. 저장된 거절 배치의 payload/revision을 고쳐 동일 batch ID로 재사용하지 않는다.
- **읽기 전용 정의/메타데이터 검토**였다. 실제 사용자 인증 RPC·계약 쓰기·재전송·동시성 실행 검증을 대신하지 않는다. 실제 계약 전송 성공 증거는 아직 없다.
- prod SQL, 서버 설정·allowlist·계약 파일·digest·mode/epoch·관문 변경은 하지 않았다.

## iPad 회신에서 확인할 항목

1. 시험 작품 1개와 양쪽 연결, 실제 로그인 사용자 권한, 새 active/handshake 결과 및 시각.
2. 양쪽 설치 식별, Staging/계약/LEGACY/0 일치.
3. 새 폴더 ID·부모·충돌 없는 시험 이름·base_revision=0.
4. 부모 tree_order ID·존재 여부·실제 revision·기존 자식 집합 보존.
5. 정확히 2개 순서 있는 작업, batch ID·operation IDs·payload hashes·batch digest·device ID·client_build_id.
6. 구조 기준 승인, 미해소 blocked/conflict 없음, 기존 대기 배치와 시험 배치 구분, Windows 관문 닫힘 및 동시 편집 방지.
7. 성공/거절/응답 유실 각각의 후속 행동. 재전송이나 결과 조회도 실제 시험 승인 범위에 명시. 같은 요청의 중복 적용 방지를 결과/revision/원장으로 확인할 방법.

명세 준비를 이유로 관문을 열거나 임시 쓰기를 하지 않는다. 서버 상태는 시간에 따라 바뀌므로 선택된 작품의 필요한 메타데이터만 최신 확인한다. 폴더 이동·삭제·복원·원고 계약 전송·prod로 범위를 확대하지 않는다.
