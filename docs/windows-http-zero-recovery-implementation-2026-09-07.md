# Windows HTTP 0 복구 구현·격리 검증 결과

2026-09-07 KST. 사용자 `진행`은 iPad 회신 범위의 구현·격리 검증에 적용했다. 실제 복구 실행 승인은 아니다.

**Windows의 별도 복구 경로와 닫힌 관문의 읽기 전용 진단을 구현했다. 최종 관련 검증 139개가 통과했다. 실제 설치·원본 요청·stopped/HTTP 0·닫힌 관문은 보존됐다. 서버 원장 조회 증명 API는 제안 단계이므로 실제 복구 준비 완료는 아니다.**

## 구현 내용

- 원본 preparation 및 기존 실행 전체 행의 확인된 해시를 고정했다. 요청 batch/hash와 두 원본의 식별이 모두 일치하고, 기존 실행이 stopped/HTTP 0/영수증 없음인 경우에만 로컬 후보로 판정한다. HTTP 1, uncertain, committed/rejected, 불완전·누락·변조 이력은 허용하지 않는다.
- SQLite 소스 스키마를 8010에서 8011로 올렸다. 새 `sync_reviewed_recoveries`는 원본 실행을 참조하며 preparation별 UNIQUE로 추가 회차 한 건만 허용한다. 새 승인과 원본 두 행의 해시를 보존하고, 진행 사건 및 영수증은 각각 별도 append-only 테이블에 연결한다. 원본 PK·상태·승인·본문은 수정하지 않는다. 실제 DB에는 이 마이그레이션을 적용하지 않았다.
- 별도 승인은 kind, 새 approval ID, batch/request hash, 원본 두 행의 해시, account marker, 승인 시각, 명시적 true를 요구한다. 원래 승인, 일반 boolean 승인, 현재 조건 충족을 새 승인으로 사용하지 않는다. 승인 시각은 원래 종료 이후이며 접수 시 5분 이내여야 한다. 승인 없이 회차·HTTP·관문 setter 호출은 없다.
- 기존 sender의 공통 경로에 별도 adapter를 연결하여 두 원격 검사, 로컬 전체 기준, 기존 C9와 single-flight를 재사용했다. HTTP 직전 새 회차의 시도 1과 사건을 같은 트랜잭션으로 영속화한다. 새 서버 batch/operation/entity ID나 새 payload를 만들지 않는다. 로컬 회차 ID는 `http0-…`이며 서버에 요청 ID로 보내지 않는다.
- 복구 중 다시 HTTP 전에 멈추어도 재시작·새 승인·중복 클릭으로 새 회차를 만들지 않는다. 다른 프로세스가 열린 준비를 관찰하면 stopped/uncertain으로 종료하며 관문을 닫고 자동 재개하지 않는다. 서로 다른 실제 두 프로세스의 동시 claim에서도 회차는 하나만 생성됐다.
- 성공·거절 영수증은 복구 회차에 저장한다. 응답 유실/잘못된 영수증은 uncertain이다. 늦은 응답은 원래 저장소로 보존한다. 이미 다른 프로세스가 uncertain으로 남긴 관찰은 바꾸지 않고 별도 receipt_status로 늦은 영수증을 표시한다. 일반 자동·수동 재시도 큐로 넣지 않고 구조 반영은 일반 수신에 맡긴다.
- 전용 UI 진입과 기본값 No인 별도 승인 창을 추가했다. 기존 준비 상태 조회/내보내기는 원래 stopped 실행과 복구 회차·로컬 후보·승인 기록·HTTP 시도·영수증 상태를 구분한다. 조회의 execution_authorized는 계속 false이며 서버 확인을 포함하지 않는다. 조회 도중 연결 변경도 stale로 표시한다.

## 서버 의존 사항 — 실제 실행 전 대조 필요

기존에 확보한 서버 정의와 일반 테이블 조회만으로는 원장 전체를 읽을 권한을 증명할 수 없다. Windows는 제안된 읽기 전용 `get_contract_recovery_preflight` 응답의 인증·완전성·네 count·nonce·요청·계정·시각을 엄격히 검사한다. 미지원/실패/불완전 결과를 0건으로 대체하는 fallback은 없다.

**이 서버 API는 이번에 구현·배포·호출하지 않았다.** 합성 응답으로 Windows의 성공·차단 동작을 검증했으며, 서버가 해당 보증을 실제 제공하는지는 아직 검증되지 않았다. 범위를 넓혀 서버 권한을 변경하거나 관리자 키·관리자 SQL 파일로 이를 대신하지 않았다. 별첨 `windows-http-zero-recovery-ledger-contract-2026-09-07.md`의 응답 의미와 최소 권한을 iPad/서버 측과 먼저 합의해야 한다.

Python 3.11, Qt offscreen, 합성 작품·요청·임시 DB·파일과 가짜 RPC를 사용했다. 두 프로세스 시험도 합성 임시 DB에서 수행했다. 새 소스와 직접 영향받는 기존 경계만 검증했으며 이미 완료한 일반 오프라인 수신 시험은 반복하지 않았다.

확인한 실패 경계: 승인 없음/기존 승인/다른 hash/오래된 승인, 원본 변경 및 불완전 이력, 원장 존재/권한·완전성 누락/조회 실패, 중복 클릭/연결/프로세스/재열기, 두 번째 원장 검사에서 기록 출현, C9의 blocked→해소 이력, 로컬 순서·관문·연결 변경, HTTP 표식 전후 크래시, 성공/거절/유실/잘못된 응답/늦은 응답, 읽기 전용 조회 및 자동·수동 재시도 제외, 8010 마이그레이션의 기존 행 보존. 진단 실패 사건이 트랜잭션 롤백 뒤에도 복구 회차에 남는 것을 확인했다.

## 실제 환경의 읽기 전용 보존 확인

2026-09-07 **01:20:21 KST** 메타데이터 확인. SQLite immutable 읽기 전용 연결을 사용했고 WAL 없음과 DB 크기·수정 시각 불변을 확인했다. 실제 저장소 객체를 초기화하지 않았다.

- 실제 DB 스키마 **8010**, 준비 1개/실행 1개, 원래 `stopped` / `http_attempts=0`.

- 준비 행 목록 SHA256: `1f887f310b33ef2805335ddc2c2d36ab049a7e010ea4192a6e517f0aeb54cda4`.

- 원래 export SHA256: `83e58abdd93e23064bd2ca90fab18c0b19a09ff4f49a71cc22c20f79c8947bbc`.

위 행 해시는 전체 행을 선별 JSON 목록으로 직렬화한 해시다. 전체 DB나 원고 본문의 해시가 아니다. 이번에 서버에 접속하거나 실제 계약·복구 RPC를 호출하지 않았다. 과거 `CONTRACT_PREPARATION_NOT_READY`의 실패 조건은 여전히 미상이다.

## 이후 실제 실행·결과 확인 절차 제안

1. 이 전달본을 iPad 측에서 대조하고, 서버 원장 증명 API의 제공 방식·권한·입출력·읽기 전용 보장을 확정한다. API 미지원 상태에서 실제 회차를 만들면 복구 기회가 소모되므로 지금 버튼을 사용하지 않는다.
2. 필요한 서버/클라이언트 변경과 별도 격리 검증을 대조한 후 빌드·설치 범위를 확정한다. 원본 두 행·닫힌 관문·요청 bytes를 설치 전후에 읽기 전용으로 비교한다.
3. 실제로 실행할 때만 사용자에게 고정 원요청의 **별도 복구 1회**를 새로 승인받는다. 양쪽 편집 정지, 같은 계정·기기·빌드·작품, 원래 stopped/0, 복구 회차 없음, 충분한 권한으로 확인한 최신 원장, 로컬 전체 기준·새 3권 부재·순서 rev1·큐·기존 두 경계/C9가 필요하다. 이번 구현 승인을 실제 실행에 재사용하지 않는다.
4. 승인된 한 번의 조작 후 원래 stopped/0과 별도 회차의 상태·시도·단계 사건·영수증·관문을 함께 확인한다. 성공이면 두 operation 결과 revision 1/2와 고정 요청 식별을 대조하고 일반 수신으로 빈 3권과 순서를 확인한다. 그 외 중단/거절/유실이면 재전송하지 않고 증거를 내보낸다. 관리자 조회로 원래 실행을 완료 처리하지 않는다.
