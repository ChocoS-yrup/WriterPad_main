- 최초 실행 전체 행 목록 SHA256 `e18cf5940e6e222f74c2a2733471a22a28071452edad1e99fdb08db4b00588e4`.

## 저장 방식과 공통 처리

제안 스키마는 **8012**다. 기존 테이블의 열·PK·UNIQUE를 바꾸지 않고 다음 세 테이블만 추가한다.

| 테이블 | 용도 |
|---|---|
| sync_post_coordination_resumes | 새 회차와 고정 정책·부모 해시·새 승인·실행 설치 SHA256·상태·HTTP 횟수 |
| sync_post_coordination_resume_events | 새 회차의 영속 사건 |
| sync_post_coordination_resume_receipts | 새 회차의 검증된 영수증 |

새 회차 테이블의 preparation_id와 parent_recovery_id는 각각 UNIQUE이고 policy는 고정값 CHECK로 제한한다. claim은 BEGIN IMMEDIATE 트랜잭션에서 원본·부모·승인·기존 새 회차 없음·닫힌 관문을 검증하고 한 번만 INSERT한다. 두 프로세스가 동시에 요청해도 하나만 성공한다. 새 회차 ID는 로컬 기록이며 서버 batch/operation ID로 쓰지 않는다.

`ResumeLedger`는 기존 HTTP 0 복구의 저장 처리에 고정 테이블과 이력 검사를 연결하는 어댑터다. HTTP 영속 시도, stop, 다른 프로세스의 중단 복구, 영수증 검증·보존을 공통 코드로 사용한다. 기존 복구 경로는 이전 테이블을 그대로 사용한다. 상태 초기화 금지와 사건/영수증 수정 금지 트리거 생성도 공통으로 사용하며, 새 부모·정책·해시·설치 식별은 불변 열에 포함한다. 기존의 명시적 작품 purge 보호 규칙을 유지하고 이 재개 경로에는 삭제 동작이 없다.

claim 뒤 실패는 stopped/0 또는 uncertain/1로 남고 자동 재개하지 않는다. HTTP 시작 전 attempted/1과 사건을 영속화한다. 늦은 유효 응답은 별도 영수증에 저장하되 이미 확정된 uncertain 행을 덮어쓰지 않는다. 추가 회차도 한 번 소모되면 이 정책으로 더 만들 수 없다. 기존 dispatcher 및 일반 retry 큐에는 넣지 않는다.

## 읽기·승인·송신 경계

- 기존 준비 상태 JSON에 `post_coordination_resume`을 추가했다. 원본/부모 보존, 로컬 후보, 새 회차 상태·영수증 상태를 선별해 내보내며 execution_authorized는 false다. 기존 11개 조건과 coordination 진단을 유지한다.
- **조정 후 원장 조회 · 회차 생성 없음** 및 별도 내보내기를 추가했다. 소모된 부모를 검증하면서 새 회차가 없는 경우 기존 현재 로그인 읽기 함수와 `read_server_ledger`를 재사용한다. 캡처 JWT의 get_user와 새 nonce 원장 RPC만 수행하는 공통 경로이며, claim·세션 갱신·관문 setter·DB 쓰기는 없다. nonzero는 조회 결과로 보존하지만 실행 허가는 아니다. 인증 세대가 바뀐 조회도 stale로 처리하도록 공통 읽기 검사를 보강했다.
- **조정 후 고정 요청 · 추가 1회 승인**의 확인창에서 명시적 Yes를 받은 뒤에만 새 approval ID를 만든다. 취소·조회·재시작은 회차를 만들지 않는다. 이전 승인 종류/ID, 잘못된 부모/정책/해시/계정, 5분을 지난 승인 또는 부모 중단보다 이른 승인은 거절한다.
- 승인과 새 회차에는 향후 실행 중인 frozen EXE 파일의 SHA256을 기록하고 대조한다. 소스 인터프리터 실행은 실제 설치 식별로 인정하지 않는다. 원요청의 기존 client_build_id는 고정 payload의 일부로 유지한다. **현재 설치 해시를 향후 새 빌드 해시라고 주장하지 않는다.** 이 식별은 EXE 파일 해시이며 실행 메모리 전체 검증은 아니다.
- 기존 `_send_reviewed_once`를 공유한다. 같은 lock에서 수신 우선이면 claim 전에 거절한다. 새 경로는 11개 준비 조건과 로컬 기준 비교도 claim 전에 수행한다. 검토 우선이면 기존 조정 코드가 수신 요청을 보류하고 종료 후 현재 세대에서 재개한다.
- claim 후 현재 로그인/active/handshake, 로컬·원격 기준, 새 nonce 원장 검사 두 경계, 기존 C9와 HTTP 직전 영속 시도를 유지한다. 서버 원장 nonzero/불완전/오래된 증명, 권한 오류, revision 차이는 쓰기 전에 중단한다. 종료 시 캡처한 작품 관문을 닫는다.

서버 API·SQL 함수·Production 설정은 변경하지 않았다. `handshake_lifecycle.py`와 `sync_manager.py`의 C9/수신 조정 코드는 설치 검토본과 바이트가 같다. 실제 실행 승인·설치 단계는 이번 구현 요청에 포함되지 않는다.

## 검증 결과와 한계

**140개 검사 통과: 신규 30개 + 필요한 영향 회귀 110개.** 공통 저장/읽기/송신/진단 경로를 변경했으므로 해당 기존 복구·독립 읽기·reviewed sender·진단·수신 조정·C9 영향 검사만 함께 실행했다. 이전 전체 142개를 그대로 반복하거나 새 검사 수에 합산하지 않았다.

신규 검사는 합성 원본/부모 해시와 임시 SQLite, 합성 로그인/RPC를 사용한다. 고정 생산 식별자는 실제 실행에 쓰지 않았다. 두 프로세스 원자 claim, 8011→8012 이행, 과거 기록 및 사건 보존, 잘못된 승인·부모·해시·계정·HTTP1·영수증 거절, 읽기/취소 비소모, UI의 명시적 승인 전달, 준비/수신 우선 claim 0, 검토 우선 수신 보류, 원장 nonzero/누락/오래됨, 두 번째 경계의 서버 기록 발생, 실제 기준 revision 차이, C9 무효화, 종료·재열기·응답 유실·늦은 영수증, 불변 트리거와 일반 dispatcher 제외를 검사했다.

마지막으로 이행 검사를 다른 프로세스 소유자로 강화하고, 수신 우선 검사에서 실제 새 claim 클래스에 대한 호출 감시를 강화했다. 해당 기존 신규 검사 2개만 다시 실행해 통과했다(`strengthened-tests.log`). 서로 다른 검사 수는 계속 140개다. 변경 파일 구문 및 diff 공백 검사를 통과했다. 임시 디렉터리의 증분 패치 재적용으로 변경 후 전체 텍스트도 대조한다.

이 검증은 실기기 종단 송신·실제 로그인 조회·새 EXE 패키징 결과가 아니다. 과거 실제 중단 호출자를 새로 확정하지 않는다. 향후 설치본에서는 실제 실행 전에 새 빌드 식별과 비송신 조회를 먼저 검토해야 한다.
