# 본문 최초 수신 실패 검토·Windows 보조 코드 수정

## 결론

**전체 가져오기는 미완료이며 본문 화면 관찰도 미실행이다.** 일반 원고의 실제 바이트와 폴더 수신은 통과했지만 내부 정렬 문서의 UUID가 잘못돼 iPad가 수신을 중단했다.

이 문제는 **이 작업에서 작성한 Windows 단일 작품 업로드 보조 코드의 누락**이다. 설치된 제품의 `SyncManager.record_tree_order`는 이미 UUIDv5 규칙을 구현하고 있다. 보조 코드가 일반 `enqueue`를 직접 사용하면서 그 사전 등록을 빠뜨려 내부 문서에 UUIDv4가 발급됐다. 앞선 HTTP 요청 제한 검사는 ‘계획대로만 전송하는가’를 확인했지만 계획 자체의 제어 문서 UUID 규칙을 검증하지 못했다. Windows 전송·본문 바이트 검증의 성공을 iPad 전체 수신 준비 완료로 판단했던 범위를 정정한다.

| 항목 | 확인 결과 |
| --- | --- |
| 작품 UUID | `9a78c51c-7de9-43a8-be54-d25a22d08a28` |
| 일반 원고 UUID | `502cdbe7-814c-42f8-8ed4-81c40cd94902` |
| 본문/폴더 | 93바이트·기준 SHA-256 일치, 폴더 11개 및 로컬 부모 일치 |
| 내부 경로 | `__antigravity__/tree-order.json` |
| 잘못 업로드한 UUID | `6df5660a-c1ae-492f-bb1d-26b582508074` |
| 규칙상 UUIDv5 | `ef6e1de1-a3d0-5959-96be-58f87a683cc0` |
| 내부 문서 | revision 1, 385바이트, 적용 실패·merge marker에 보존 |
| 현재 iPad 결과 | 수신 journal 1개, 원고/폴더 부분 저장, 공개 작품 목록 미게시 |

내부 문서 hash는 `1cfe9438a3ff000c3af3b5593f973554b2966e9fd8c29e704e73143fda27b5be`다. 일반 원고 hash는 기존 `cdfcc92e4b06906d9c54e11b4ad263cf913105fdff7669ac5b69b1f42bb7f96d`와 같다. 일반 원고 UUID 및 서버 구조 필드 null은 이번 원인이 아니다.

## 증거 대조

회신 ZIP SHA-256 `48787d9bc42779947a508a73982b0f03ed4308272c0f3bf6fccdceecc6bd4bbb`, manifest 33개 파일의 CRC·경로·크기·해시·정확한 집합을 검증했다. iPad 사전 상태는 이전 바인더 사후 상태와 정확히 일치한다. Windows가 실제 사용했던 요청 계획과 수신된 잘못된 UUID·본문·내부 정렬 hash를 직접 대조했고 Python UUIDv5로 올바른 값을 독립 계산했다.

최종 iPad 소스는 잘못된 UUID 또는 삭제된 내부 제어 문서를 `invalidLocalHierarchy`로 보존하고, mergeRequired가 남으면 가져오기 완료를 거부한다. 후보 manifest 해시 및 확보한 원문/발췌와 해당 조건을 대조했다. iPad가 보고한 Swift assertion 2개는 Windows에서 다시 실행하지 않았다.

63개 검사는 실패 자료·부분 저장·기존 자료 보존 검사다. 원시 iPad DB가 없으므로 Windows는 결과와 감사 소스를 검토했으며 실제 DB로 재실행하지 않았다. 기존 원고·큐/연결/정책은 보존됐고 대상 신규 송신 큐는 0이다. ContractReviews 디렉터리 mtime 1개 변경은 별도로 남긴다. 그 내부 기존 파일 바이트와 준비/큐는 동일하며 atomic export 때문이라는 설명은 추론이다. 프로세스 재등장 원인은 여전히 미확정이다.

## 이번에 완료한 수정

`_evidence/windows-nonempty-initial-upload-20260911/scoped_upload.py`의 변경 전 원문을 이번 검토 폴더에 보존했다. 보조 코드의 새 생성 경로는 제품과 같은 UUIDv5로 제어 문서를 명시 등록한 후 enqueue한다. 요청 계획을 만들 때와 HTTP 보호 객체를 만들 때 제어 문서의 개수·UUID·삭제 여부·작품 범위를 검사한다. 이미 잘못된 ID가 있는 로컬 문서는 자동 교정하지 않고 중단한다.

격리 검증 6개 통과: 실제 잘못된 계획 차단, 올바른 고정 UUID 허용, 내부 삭제 문서 차단, 내부 문서 누락/중복 차단, 새 DB와 요청의 UUIDv5 일치. 기존 범위 검사도 계획 14개 허용·범위 밖 5개 차단을 확인했다. 네트워크 호출은 0이다. 원고 1개 생성 조건을 유지한다.

실제 Windows 작품/DB, 서버 문서, iPad journal/marker, 설치 파일은 이번 검토에서 변경하지 않았다. 원래 업로드를 반복하지 않았다. 이 로컬 수정만으로 이미 올라간 잘못된 서버 ID가 고쳐지지는 않는다.

## 다음 단계와 사용자 행동

다음은 **교정 전 로컬 재개 검토**다. iPad 담당에게 함께 만든 요청 ZIP을 전달해, 올바른 서버 제어 문서로 바뀌었을 때 기존 journal/부분 저장을 유지한 재개가 가능한지 격리 검증하도록 한다. 서버 교정 SQL과 Windows 로컬 장부의 변경 범위는 그 결과 및 참조 관계를 확인한 뒤 확정한다.

잘못된 제어 문서를 tombstone으로 남기고 새 UUID를 추가하면 iPad의 제어 문서 삭제 거부 조건에 다시 걸릴 수 있다. 단순 삭제·재업로드, 작품 재생성, 일반 원고 UUID 변경, iPad 보호 검사 완화로 우회하지 않는다. 실제 교정·marker 정리·재개는 아직 승인되지 않았다.

사용자는 **양쪽 앱을 열거나 가져오기 재개/동기화 버튼을 누르지 말고**, 교정 전 검토 요청 ZIP만 iPad 작업에 전달한다. 이후 구체적인 실제 교정 범위를 제시해 승인을 받는다.
