WriterPad iPad divergence 구현·검증 안내서
대상: 개발을 처음 해 보는 사람
작성 기준일: 2026-08-20

============================================================
0. 이 문서에서 확인하려는 것
============================================================

이 검사는 iPad 동기화 장부 안의 두 기록이 서로 같은 말을 하는지 확인한다.

첫 번째 기록:
  sync_operations 표의 status 칸

두 번째 기록:
  sync_operation_events 표에 시간순서대로 쌓인 사건들

예를 들어 마지막 사건이 committed라면, 사건으로 계산한 상태는 completed이다.
이때 status도 completed여야 한다.

두 값이 다르면 divergence(상태 어긋남)라고 부른다.

중요:
  divergence가 0건이라고 해서 되감기 불변성까지 통과한 것은 아니다.

  divergence 검사는 “상태 칸과 사건 열이 같은가?”를 본다.
  되감기 불변성 검사는 “원래 작업을 덮어쓰지 않고 새 작업을 만들었는가?”를 본다.

핸드셰이크를 검토하려면 두 검사 모두 통과해야 한다.


============================================================
1. 절대로 하지 말아야 할 것
============================================================

1) sync-contract 폴더를 수정하지 않는다.
2) 계약 핸드셰이크를 켜거나 배선하지 않는다.

5) 보존용 DB 원본을 SQLite나 앱으로 직접 열지 않는다.
6) 실패한 결과를 고치려고 DB의 status나 사건을 직접 수정하지 않는다.
7) git reset --hard, 강제 푸시, 브랜치 삭제를 하지 않는다.

실수했는지 모르겠다면 아무것도 더 누르지 말고 현재 화면을 캡처한다.

============================================================
5. 사건 이름을 상태로 바꾸는 규칙
============================================================

아래 규칙은 Windows와 iPad에서 같은 뜻이어야 한다.

  enqueued             -> pending
  dispatch_started     -> inflight
  retry_scheduled      -> retry_wait
  blocked              -> blocked
  conflict_detected    -> conflict
  committed            -> completed
  replayed             -> completed
  cancel_requested     -> cancelled
  superseded           -> cancelled

마지막 사건이 committed인데 status가 pending이면 divergence 1건이다.
마지막 사건이 conflict_detected인데 status가 conflict이면 정상이다.

11. 실제 DB의 무결성과 divergence를 읽기 전용으로 검사한다
============================================================

이 단계는 반드시 감사용 복사본에서 한다.

11-1. 터미널에 다음을 입력하되 아직 Enter는 누르지 않는다.

  sqlite3 -readonly 

끝에 공백 하나를 둔다.

11-2. 감사용 sync-v2.sqlite3 파일을 터미널로 끌어다 놓는다.

11-3. Enter를 누른다.

정상이라면 sqlite>라는 표시가 나타난다.

11-4. 아래 명령을 한 줄씩 입력하고 Enter를 누른다.

  .headers on
  .mode column
  PRAGMA integrity_check;

정상 출력:

  integrity_check
  ---------------
  ok

ok가 아니면 즉시 멈춘다.
DB를 고치려고 하지 말고 나온 문구를 그대로 보존한다.

11-5. 사건 번호가 1부터 빠짐없이 이어지는지 검사한다.

아래 SQL 전체를 복사해 sqlite> 뒤에 붙여넣는다.
마지막 세미콜론까지 붙여넣어야 실행된다.

  SELECT operation_id,
         MIN(event_sequence) AS first_sequence,
         MAX(event_sequence) AS last_sequence,
         COUNT(*) AS event_count,
         COUNT(DISTINCT event_sequence) AS distinct_count
  FROM sync_operation_events
  GROUP BY operation_id
  HAVING MIN(event_sequence) <> 1
     OR MAX(event_sequence) <> COUNT(*)
     OR COUNT(*) <> COUNT(DISTINCT event_sequence);

정상 출력:
  아무 행도 나오지 않는다.

한 줄이라도 나오면:
  그 operation_id의 사건 번호가 빠졌거나 겹쳤다는 뜻이다.
  결과를 그대로 보존하고 핸드셰이크로 넘어가지 않는다.

11-6. divergence를 검사한다.

  WITH ranked AS (
      SELECT operation_id,
             event_type,
             event_sequence,
             ROW_NUMBER() OVER (
                 PARTITION BY operation_id
                 ORDER BY event_sequence DESC
             ) AS row_number
      FROM sync_operation_events
  ),
  derived AS (
      SELECT operation_id,
             CASE event_type
                 WHEN 'enqueued' THEN 'pending'
                 WHEN 'dispatch_started' THEN 'inflight'
                 WHEN 'retry_scheduled' THEN 'retry_wait'
                 WHEN 'blocked' THEN 'blocked'
                 WHEN 'conflict_detected' THEN 'conflict'
                 WHEN 'committed' THEN 'completed'
                 WHEN 'replayed' THEN 'completed'
                 WHEN 'cancel_requested' THEN 'cancelled'
                 WHEN 'superseded' THEN 'cancelled'
                 ELSE NULL
             END AS derived_status
      FROM ranked
      WHERE row_number = 1
  )
  SELECT operations.operation_id,
         operations.status AS stored_status,
         derived.derived_status
  FROM sync_operations AS operations
  LEFT JOIN derived
    ON derived.operation_id = operations.operation_id
  WHERE operations.status IS NOT derived.derived_status
  ORDER BY operations.queue_id;

정상 출력:
  아무 행도 나오지 않는다.

이것을 보고서에는 다음처럼 적는다.

  divergence_count: 0
  divergences: []

한 줄이라도 나오면:
  1) operation_id를 기록한다.
  2) stored_status를 기록한다.
  3) derived_status를 기록한다.
  4) DB를 수정하지 않는다.
  5) 핸드셰이크로 넘어가지 않는다.

============================================================
13. 되감기 불변성을 별도로 확인한다
============================================================

이 검사는 divergence 검사와 다르다.

올바른 되감기:

  원본 operation_id
    내용과 base revision이 바뀌지 않음
    conflict_detected 사건이 남음
    마지막에 superseded 사건이 남음

  새 operation_id
    원본과 다른 UUID
    첫 사건 enqueued
    supersedes 관계가 원본을 가리킴
    이후 dispatch_started와 committed로 진행

잘못된 되감기:

  같은 operation_id를 유지한 채
  content 또는 base revision을 새 값으로 덮어씀

Xcode에서 다음 테스트 이름을 검색한다.

  testRebaseMutatesOperationInPlace_CONTRACT_VIOLATION_PINNED

매우 중요한 해석:

  이 테스트가 존재하고 통과한다는 것은 올바른 계약이 통과했다는 뜻이 아니다.
  현재의 “제자리 덮어쓰기 계약 위반”이 아직 존재함을 고정해서 보여 주는 시험이다.

따라서 이 테스트가 현재 형태로 남아 있으면:

  iPad divergence 검사는 통과할 수 있음
  iPad 되감기 불변성은 미통과
  핸드셰이크는 금지

불변성을 고친 뒤에는:

  1) 원본 행이 그대로인지 검사하는 테스트가 있어야 한다.
  2) 새 operation_id가 생겼는지 검사해야 한다.
  3) 원본의 마지막 사건이 superseded인지 검사해야 한다.
  4) 새 작업의 첫 사건이 enqueued인지 검사해야 한다.
  5) operationStateDivergences()가 빈 목록인지 검사해야 한다.
